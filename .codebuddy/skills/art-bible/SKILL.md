# 艺术圣经技能

## 技能概述

创建设觉规范，定义艺术风格指南，为游戏建立一致的视觉语言。

## 使用方式

- 通过 Agent 触发：当用户说「艺术圣经」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：```/skill art-bible [参数]```

## 工作流

### 阶段 0：解析参数和上下文检查

解析审查模式（一次性，为此运行的所有门控生成存储）：
1. 如果传递了 `--review [full|lean|solo]` → 使用其值
2. 否则读取 `production/review-mode.txt` → 使用其值
3. 否则 → 默认为 `lean`

参见 `.claude/docs/director-gates.md` 获取完整检查模式。

读取 `design/gdd/game-concept.md`。如果不存在，失败并显示：
> "未找到游戏概念。首先运行 `/brainstorm` — 艺术圣经在游戏概念批准后才编写。"

从 game-concept.md 提取：
- 游戏标题（工作标题）
- 核心幻想和电梯演讲
- 游戏支柱（所有支柱）
- **视觉识别锚点**部分（如果存在，来自 brainstorm 阶段 4 艺术主管输出）
- 目标平台（如果注明）

**改造模式检测**：全局搜索 `design/art/art-bible.md`。如果文件存在：
- 完整读取它
- 对于 9 个章节中的每一个，检查正文是否包含真实内容（不仅仅是 `[待设计]` 占位符或类似内容）vs. 为空/占位符
- 构建章节状态表：

```
章节 | 状态
------|--------
1. 视觉识别声明 | [完成 / 为空 / 占位符]
2. 色彩调色板 | ...
3. 光照与氛围 | ...
4. 角色艺术方向 | ...
5. 环境与关卡艺术 | ...
6. UI 视觉语言 | ...
7. VFX 与粒子风格 | ...
8. 资源标准 | ...
9. 风格禁忌 | ...
```

- 向用户展示此表：
  > "在 `design/art/art-bible.md` 找到现有艺术圣经。[N] 个章节已完成，[M] 个需要内容。我将只处理未完成章节 — 不会触及现有内容。"

- 仅处理状态为"为空"或"占位符"的章节。不要重新编写已完成的章节。

如果文件不存在，这是一个全新的编写会话 — 正常继续。

如果存在，读取 `.claude/docs/technical-preferences.md` — 提取性能预算和引擎以进行资源标准约束。

---

### 阶段 1：框架

在编写任何内容之前，展示会话上下文并询问两个问题：

使用带两个选项卡的 `AskUserQuestion`：
- 选项卡 **"范围"** — "今天需要编写哪些章节？"
  选项：`完整圣经 — 所有 9 个章节` / `视觉识别核心（仅章节 1-4）` / `仅资源标准（章节 8）` / `恢复 — 填充缺失章节`
- 选项卡 **"参考"** — "你有定义视觉方向参考游戏、电影或艺术吗？"
  （自由文本 — 让用户键入特定标题。不要在此处预设选项。）

如果 game-concept.md 有视觉识别锚点部分，注意它：
> "从 brainstorm 找到视觉识别锚点：'[锚点名称] — [单行规则]'。我将使用它作为艺术圣经的基础。"

---

### 阶段 2：视觉识别基础（章节 1-4）

这四个章节定义核心视觉语言。**所有其他章节都从中流出。** 在移动到下一个之前，编写每个章节并写入文件。

#### 章节 1：视觉识别声明

**目标**：一条单行视觉规则加上 2-3 个支持原则，解决视觉歧义。

如果从 game-concept.md 存在视觉锚点：展示它并询问：
- "直接从此锚点构建？"
- "在扩展之前修订它？"
- "用新选项重新开始？"

**Agent 委派（必需）**：通过 Task 生成 `art-director`：
- 提供：游戏概念（电梯演讲、核心幻想）、完整支柱集、平台目标、阶段 1 框架的任何参考游戏/艺术、视觉锚点（如果存在）
- 询问："为此游戏起草视觉识别声明。提供：（1）可以解决任何视觉决策歧义的单行视觉规则，（2）2-3 个支持视觉原则，每个都有一句设计测试（'当 X 有歧义时，此原则说选择 Y'）。将所有原则直接锚定在 stated 支柱中 — 每个原则必须服务于特定支柱。"

向用户展示艺术主管的草稿。使用 `AskUserQuestion`：
- 选项：`[A] 锁定此` / `[B] 修订单行` / `[C] 修订支持原则` / `[D] 描述我自己的方向`

立即将批准的章节写入文件。

#### 章节 2：氛围与情绪

**目标**：按游戏状态的情感目标 — 具体 enough，照明艺术家可以据此工作。

对于每个主要游戏状态（例如，探索、战斗、胜利、失败、菜单 — 适应此游戏的状态），定义：
- 主要情绪/氛围目标
- 光照特征（一天中的时间、色温、对比度级别）
- 大气描述符（3-5 个形容词）
- 能量级别（狂热 / 测量 / 沉思 / 等）

**Agent 委派**：通过 Task 使用视觉识别声明和支柱集生成 `art-director`。询问："为此游戏中的每个主要游戏状态定义氛围和大气目标。要具体 — '黑暗和预兆' 是不够的。命名确切的情感目标、光照特征（暖/冷、高/低对比、一天中的时间方向）和至少一个携带氛围的视觉元素。每个游戏状态必须在视觉上与其他状态区分开。"

立即将批准的章节写入文件。

#### 章节 3：形状语言

**目标**：使此游戏的世界在视觉上连贯和可区分的几何词汇。

涵盖：
- 角色剪影哲学（在缩略图尺寸处如何可读？每个原型的区分特征？）
- 环境几何（有角/弯曲/有机/几何 — 哪个占主导地位以及为什么？）
- UI 形状语法（UI 是否呼应世界美学，或者它是独特的 HUD 语言？）
- 英雄形状 vs. 支持形状（什么吸引眼球，什么后退？）

**Agent 委派**：通过 Task 使用视觉识别声明和氛围目标生成 `art-director`。询问："为此游戏定义形状语言。将每个形状原则连接回视觉识别声明和特定游戏支柱。解释这些形状选择如何在情感上向玩家传达信息。"

立即将批准的章节写入文件。

#### 章节 4：色彩系统

**目标**：服务美学和通信需求的完整、可复现调色板系统。

涵盖：
- 主调色板（5-7 种颜色带角色 — 不仅仅是十六进制代码，而是每种颜色在这个世界中意味着什么）
- 语义颜色使用（红色传达什么？金色？蓝色？白色？建立颜色词汇）
- 每生物群系或每区域色温规则（如果游戏有不同区域）
- UI 调色板（可能与世界调色板不同 — 显式定义分叉）
- 色盲安全：哪些语义颜色需要形状/图标/声音备份

**Agent 委派**：通过 Task 使用视觉识别声明和氛围目标生成 `art-director`。询问："为此游戏设计色彩系统。必须解释每个语义颜色分配 — 为什么这种颜色在这个世界中意味着危险/安全/奖励？识别哪些颜色对可能使色盲玩家失败，并指定需要什么备份提示。"

立即将批准的章节写入文件。

---

### 阶段 3：生产指南（章节 5-8）

这些章节将视觉识别转换为具体生产规则。它们应该足够具体，以至于外包团队可以在没有额外简报的情况下遵循它们。

#### 章节 5：角色设计方向

**Agent 委派**：通过 Task 使用章节 1-4 生成 `art-director`。询问："为此游戏定义角色设计方向。涵盖：玩家角色（如果有）的视觉原型、每角色类型的区分特征规则（玩家如何一目了然地区分敌人/NPC/盟友？）、表情/姿势风格目标（僵硬/富有表现力/现实主义/夸张）和 LOD 哲学（在游戏摄像机距离处保留多少细节？）"

将批准的章节写入文件。

#### 章节 6：环境设计语言

**Agent 委派**：通过 Task 使用章节 1-4 生成 `art-director`。询问："为此游戏定义环境设计语言。涵盖：建筑风格及其与世界文化/历史的关系、纹理哲学（绘制 vs. PBR vs. 风格化 — 为什么为此游戏选择此选择？）、道具密度规则（稀疏/密集 — 什么驱动每区域类型的选择？）和环境叙事指南（什么视觉细节应该在没有文本的情况下讲述故事？）"

将批准的章节写入文件。

#### 章节 7：UI/HUD 视觉方向

**Agent 委派**：并行生成：
- **`art-director`**：UI 的视觉风格 — 叙事 vs. 屏幕空间 HUD、排版方向（字体个性、粗细、大小层次）、图标样式（扁平/轮廓/插图/照片现实主义）、UI 元素的动画感觉
- **`ux-designer`**：UX 对齐检查 — 视觉方向是否支持此游戏所需的交互模式？标记艺术方向和可读性/可访问性需求之间的任何冲突。

收集两者。如果它们冲突（例如，艺术主管想要精心设计的叙事 UI，但 UX 设计师标记它会降低战斗可读性），显式表面冲突与两个位置。不要静默解决 — 使用 `AskUserQuestion` 让用户决定。

将批准的章节写入文件。

#### 章节 8：资源标准

**Agent 委派**：并行生成：
- **`art-director`**：文件格式首选项、命名约定方向、纹理分辨率层级、LOD 级别预期、导出设置哲学
- **`technical-artist`**：引擎特定硬约束 — 每资源类别的多边形计数预算、纹理内存限制、材质槽计数、导入器约束、`.claude/docs/technical-preferences.md` 中性能预算的任何内容

如果任何艺术首选项与技术约束冲突（例如，艺术主管想要 4K 纹理，但性能预算需要移动设备为 2K），显式解决冲突 — 注意理想标准和约束标准，并解释权衡。资源标准中的歧义是生产成本的诞生地。

将批准的章节写入文件。

---

### 阶段 4：参考方向（章节 9）

**目标**：特定关于从每个来源采取什么和避免什么的策展参考集。

**Agent 委派**：通过 Task 使用完成的章节 1-8 生成 `art-director`。询问："为此游戏编译参考方向。提供 3-5 个参考来源（游戏、电影、艺术风格或特定艺术家）。对于每个：命名它，准确指定要从它提取什么视觉元素（不是'一般美学' — 特定技术、颜色选择或构图规则），并指定要显式避免或分歧什么（以防止'尝试复制 X'读取）。参考应该是附加的 — 没有两个参考应该指向完全相同的方向。"

将批准的章节写入文件。

---

### 阶段 5：艺术主管签署

**审查模式检查** — 在生成 AD-ART-BIBLE 之前应用：
- `solo` → 跳过。注意："AD-ART-BIBLE 已跳过 — 单人模式。" 继续阶段 6。
- `lean` → 跳过（不是阶段门控）。注意："AD-ART-BIBLE 已跳过 — 精简模式。" 继续阶段 6。
- `full` → 正常生成。

所有章节完成后（或阶段 1 的范围集完成后），通过 Task 使用门 **AD-ART-BIBLE** (`.claude/docs/director-gates.md`) 生成 `creative-director`。

传递：艺术圣经文件路径、游戏支柱、视觉识别锚点。

按 `director-gates.md` 中的标准规则处理判定。在艺术圣经的状态标头中记录判定：
`> **Art Director Sign-Off (AD-ART-BIBLE)**: APPROVED [日期] / CONCERNS (accepted) [日期] / REVISED [日期]`

---

### 阶段 6：关闭

在展示下一步之前，检查项目状态：
- `design/gdd/systems-index.md` 是否存在？→ map-systems 已完成，跳过该选项
- `.claude/docs/technical-preferences.md` 是否包含已配置引擎（不是 `[TO BE CONFIGURED]`）？→ setup-engine 已完成，跳过该选项
- `design/gdd/` 是否包含任何 `*.md` 文件？→ design-system 已运行，跳过该选项
- `design/gdd/gdd-cross-review-*.md` 是否存在？→ review-all-gdds 已完成
- GDD 是否存在（检查上面）？→ 包含 /create-architecture 选项

使用 `AskUserQuestion` 获取下一步。仅包括上面状态检查真正下一步的选项：

**选项池 — 仅包括如果尚未完成：**
- `[_] 运行 /map-systems — 在编写 GDD 之前将概念分解为系统`（如果 systems-index.md 不存在则跳过）
- `[_] 运行 /setup-engine — 配置引擎（引擎设置后可能需要重新访问资源标准）`（如果引擎已配置则跳过）
- `[_] 运行 /design-system — 开始第一个 GDD`（如果任何 GDD 存在则跳过）
- `[_] 运行 /review-all-gdds — 跨 GDD 一致性检查（技术设置门控之前必需）`（如果 gdd-cross-review-*.md 存在则跳过）
- `[_] 运行 /asset-spec — 从批准的 GDD 生成每资源视觉规格和 AI 生成提示`（如果 GDD 存在则包括）
- `[_] 运行 /consistency-check — 根据艺术圣经扫描现有 GDD 的视觉方向冲突`（如果 GDD 存在则包括）
- `[_] 运行 /create-architecture — 编写主架构文档（下一个技术设置步骤）`
- `[_] 在此处停止`

仅向实际包括的选项分配字母 A、B、C...。将最合逻辑管道推进选项标记为 `(recommended)`。

> **始终包括** `/create-architecture` 和在此处停止作为选项 — 一旦艺术圣经完成，这些始终有效下一步。

## 协作协议

每个章节遵循：**问题 → 选项 → 决策 → 草稿（来自艺术主管代理）→ 批准 → 写入文件**

- 在没有首先生成相关代理的情况下，永远不要起草章节
- 批准后立即将每个章节写入文件 — 不要批处理
- 向用户表面所有代理分歧 — 永远不要静默解决艺术主管和技术艺术家之间的冲突
- 艺术圣经是一个约束文档：它交换视觉连贯性的解决方案空间缩小。每个章节应该感觉像它富有成效地缩小解决方案空间。

---

## 推荐下一步

艺术圣经批准后：
- 运行 `/map-systems` 在编写 GDD 之前将概念分解为游戏系统
- 如果引擎尚未配置，运行 `/setup-engine`（引擎选择后可能需要重新访问资源标准）
- 运行 `/design-system [first-system]` 开始编写每系统 GDD
- 一旦 GDD 存在，运行 `/consistency-check` 根据艺术圣经验证它们
- 运行 `/create-architecture` 生成主架构文档
