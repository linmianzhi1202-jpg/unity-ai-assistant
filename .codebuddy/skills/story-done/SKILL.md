# 故事完成技能

## 技能概述

验证完成定义，归档已完成工作。此技能关闭设计和实施之间的循环。在每个故事实施结束时运行它。它确保在实际将故事标记为完成之前验证每个验收标准，GDD 和 ADR 偏差被明确记录而不是静默引入，代码审查被提示而不是遗忘，并且故事文件反映实际完成状态。

**输出:** 更新的故事文件（Status: Complete）+ 呈现的下一个故事。

## 使用方式

- 通过 Agent 触发：当用户说「故事完成」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：```/skill story-done [参数]```

---

## 阶段 0: 解析参数

解析审查模式（一次设置，用于存储此次运行的所有门生成）：
1. 如果传递了 `--review [full|lean|solo]` → 使用那个值
2. 否则读取 `production/review-mode.txt` → 使用那个值
3. 否则 → 默认为 `lean`

有关完整的检查模式，请参见 `.claude/docs/director-gates.md`。

---

## 阶段 1: 查找故事

**如果提供了文件路径**（例如 `/story-done production/epics/core/story-damage-calculator.md`）：
直接读取该文件。

**如果未提供参数：**

1. 检查 `production/session-state/active.md` 查找当前活跃故事。
2. 如果那里未找到，读取 `production/sprints/` 中最近的文件并查找标记为 IN PROGRESS 的故事。
3. 如果找到多个进行中的故事，使用 `AskUserQuestion`：
   - "我们要完成哪个故事？"
   - 选项：列出进行中故事文件名。
4. 如果找不到故事，请用户提供路径。

---

## 阶段 2: 读取故事

读取完整故事文件。在上下文中提取并保留：

- **故事名称和 ID**
- **GDD 需求 TR-ID**（例如 `TR-combat-001`）
- **清单版本** 嵌入在故事标头中（例如 `2026-03-10`）
- **ADR 引用**
- **验收标准** — 完整列表（每个复选框项目）
- **实施文件** — 在"要创建/修改的文件"下列出的文件
- **故事类型** — 故事标头中的 `Type:` 字段（Logic / Integration / Visual/Feel / UI / Config/Data）
- **引擎注释** — 注意的任何引擎特定约束
- **完成定义** — 如果存在，故事级 DoD
- **预估与实际范围** — 如果注意了预估

还要读取：
- `docs/architecture/tr-registry.yaml` — 查找故事中的每个 TR-ID。
  从注册表条目读取*当前* `requirement` 文本。这是 GDD 需求的事实来源——不要使用可能内联在故事中的任何需求文本（可能已过时）。
- 引用的 GDD 部分 — 仅验收标准和关键规则，不是完整文档。使用此对照注册表文本是否仍然准确。
- 引用的 ADR — 仅 Decision 和 Consequences 部分
- `docs/architecture/control-manifest.md` 标头 — 提取当前 `Manifest Version:` 日期（用于阶段 4 过期检查）

---

## 阶段 3: 验证验收标准

对于故事中的每个验收标准，尝试使用三种方法之一进行验证：

### 自动验证（无需询问即可运行）

- **文件存在检查**：`Glob` 故事说将创建的文件。
- **测试通过检查**：如果提到测试文件路径，通过 `Bash` 运行它。
- **无硬编码值检查**：`Grep` 游戏代码中的数字字面量，这些路径应该在配置文件。
- **无硬编码字符串检查**：`Grep` `src/` 中应该是本地化文件的玩家面向字符串。
- **依赖检查**：如果标准说"依赖于 X"，检查 X 是否存在。

### 手动验证与确认（使用 `AskUserQuestion`）

- 关于主观品质的标准（"感觉响应"、"动画正确播放"）
- 关于游戏玩法的标准（"玩家受到伤害时..."、"敌人响应..."）
- 性能标准（"在 Xms 内完成"）— 询问是否已分析或接受为假设

将最多 4 个手动验证问题批处理到单个 `AskUserQuestion` 调用中：

```
question: "[标准]？"
options: "是 — 通过", "否 — 失败", "尚未测试"
```

### 不可验证（标记而不阻塞）

- 需要完整游戏构建来测试的标准（端到端游戏场景）
- 标记为：`DEFERRED — 需要试玩会话`

### 测试-标准可追踪性

完成上述通过/失败/延迟检查后，将每个验收标准映射到覆盖它的测试：

对于故事中的每个验收标准：

1. 询问：是否有测试——单元、集成或确认的手动试玩——直接验证此标准？
   - **单元测试**：检查 `tests/unit/` 查找匹配标准主题（subject）的测试文件或函数名称（使用 `Glob` 和 `Grep`）
   - **集成测试**：类似地检查 `tests/integration/`
   - **手动确认**：如果标准通过上述 `AskUserQuestion` 验证并回答"是 — 通过"，将其计入手动测试

2. 生成可追踪性表：

```
| 标准 | 测试 | 状态 |
|-----------|------|--------|
| AC-1: [标准文本] | tests/unit/test_foo.gd::test_bar | COVERED |
| AC-2: [标准文本] | 手动试玩确认 | COVERED |
| AC-3: [标准文本] | — | UNTESTED |
```

3. 应用这些升级规则：

   - 如果 **>50% 的标准是 UNTESTED**：升级为**阻塞**——测试覆盖不足，无法确认故事实际完成。阶段 6 中的判定在完成之前无法完成。
   - 如果**一些（≤50%）标准**是 UNTESTED：保持建议性——不阻塞完成，但必须出现在完成备注中。
   - 如果**所有标准都是 COVERED**：除了在报告中包含表之外，无需操作。

4. 对于任何建议性未测试标准，在阶段 7 的完成备注中添加：
   `"未测试标准：[AC-N 列表]。建议在后续故事中添加测试。"`

### 测试证据要求

根据阶段 2 提取的故事类型，检查必需的证据：

| 故事类型 | 必需证据 | 门级别 |
|---|---|---|
| **Logic** | `tests/unit/[system]/` 中的自动化单元测试 | 阻塞 |
| **Integration** | `tests/integration/[system]/` 中的集成测试或试玩文档 | 阻塞 |
| **Visual/Feel** | `production/qa/evidence/` 中的截图 + 签核 | 建议性 |
| **UI** | `production/qa/evidence/` 中的手动走查文档或交互测试 | 建议性 |
| **Config/Data** | `production/qa/smoke-*.md` 中的冒烟检查通过报告 | 建议性 |

**对于 Logic 故事**：首先读取故事的**测试证据**部分以提取确切必需的文件路径。使用 `Glob` 检查确切路径。如果未找到确切路径，还要广泛搜索 `tests/unit/[system]/`（文件可能放置在稍微不同的位置）。如果这两个位置都未找到测试文件：
- 标记为**阻塞**："Logic 故事没有单元测试文件。故事在 `[测试证据部分的确切路径]` 需要它。在将此故事标记为完成之前创建并运行测试。"

**对于 Integration 故事**：读取故事的**测试证据**部分以获取确切必需路径。使用 `Glob` 首先检查确切路径，然后广泛搜索 `tests/integration/[system]/`，然后检查 `production/session-logs/` 查找引用此故事的试玩记录。
如果未找到：标记为**阻塞**（与 Logic 相同规则）。

**对于 Visual/Feel 和 UI 故事**：glob `production/qa/evidence/` 查找引用此故事的文件。如果没有：标记为**建议性**——
"未找到手动测试证据。使用 test-evidence 模板创建 `production/qa/evidence/[story-slug]-evidence.md` 并在最终关闭之前获得签核。"

**对于 Config/Data 故事**：检查任何 `production/qa/smoke-*.md` 文件。
如果没有：标记为**建议性**——"未找到冒烟检查报告。运行 `/smoke-check`。"

**如果未设置故事类型**：标记为**建议性**——
"故事类型未声明。将 `Type: [Logic|Integration|Visual/Feel|UI|Config/Data]` 添加到故事标头，以便在未来的故事中启用测试证据门强制执行。"

任何阻塞测试证据差距都会阻止阶段 6 中的完成判定。

## 阶段 4: 检查偏差

将实施与设计文档进行对比。

自动运行这些检查：

1. **GDD 规则检查**：使用从 `tr-registry.yaml` 查找的故事的 TR-ID 的当前需求文本，检查实施是否反映 GDD 现在实际要求的内容——而不是故事编写时的要求。
   `Grep` 实施文件中的关键函数名称、数据结构或类名称，这些在当前的 GDD 部分中提到。

2. **清单版本过期检查**：将嵌入在故事标头中的 `Manifest Version:` 日期与当前 `docs/architecture/control-manifest.md` 标头中的 `Manifest Version:` 日期进行比较。
   - 如果它们匹配 → 静默通过。
   - 如果故事的版本较旧 → 标记为建议性：
     `建议性：故事是针对清单 v[故事日期] 编写的；当前清单是 v[当前日期]。运行 /story-readiness 进行检查。`
   - 如果 control-manifest.md 不存在 → 跳过此检查。

3. **ADR 约束检查**：读取引用的 ADR 的 Decision 部分。检查 `docs/architecture/control-manifest.md`（如果存在）中明确禁止的模式。在 ADR 中 `Grep` 明确禁止的模式。

4. **硬编码值检查**：`Grep` 游戏逻辑中应该是数据文件中的数字字面量。

5. **范围检查**：实施是否触及了故事所述范围之外的文件？（"要创建/修改的文件"中未列出的文件）

对于每个发现的偏差，分类：

- **阻塞** — 实施与 GDD 或 ADR 矛盾（在标记为完成之前必须修复）
- **建议性** — 实施与规范略有偏差，但在功能上等效（记录，用户决定）
- **超出范围** — 附加文件在所述的边界之外被触及（标记以提高意识——可能是有效的或范围蠕变）

---

## 阶段 4b: QA 覆盖门控

**审查模式检查**——在生成 QL-TEST-COVERAGE 之前应用：
- `solo` → 跳过。注意："QL-TEST-COVERAGE 已跳过——单人模式。"继续到阶段 5。
- `lean` → 跳过（不是 PHASE-GATE）。注意："QL-TEST-COVERAGE 已跳过——精简模式。"继续到阶段 5。
- `full` → 正常生成。

完成阶段 4 中的偏差检查后，通过 Task 使用门控 **QL-TEST-COVERAGE**（`.claude/docs/director-gates.md`）生成 `qa-lead`。

传递：
- 故事文件路径和故事类型
- 阶段 3 期间找到的测试文件路径（确切路径，或"未找到"）
- 故事的 `## QA Test Cases` 部分（故事创建时的预写测试规范）
- 故事的 `## Acceptance Criteria` 列表

qa-lead 审查测试是否实际覆盖了指定的内容——而不仅仅是文件是否存在。

应用判定：
- **充分** → 继续到阶段 5
- **有差距** → 标记为**建议性**："QA lead 识别出覆盖差距：[列表]。故事可以完成，但差距应该在后续故事中解决。"
- **不充分** → 标记为**阻塞**："QA lead：关键逻辑未测试。在覆盖改善之前，判定无法完成。具体差距：[列表]。"

跳过此阶段对于 Config/Data 故事（不需要代码测试）。

---

## 阶段 5: 主程序员代码审查门控

**审查模式检查**——在生成 LP-CODE-REVIEW 之前应用：
- `solo` → 跳过。注意："LP-CODE-REVIEW 已跳过——单人模式。"继续到阶段 6（完成报告）。
- `lean` → 跳过（不是 PHASE-GATE）。注意："LP-CODE-REVIEW 已跳过——精简模式。"继续到阶段 6（完成报告）。
- `full` → 正常生成。

通过 Task 使用门控 **LP-CODE-REVIEW**（`.claude/docs/director-gates.md`）生成 `lead-programmer`。

传递：实施文件路径、故事文件路径、相关 GDD 部分、管理的 ADR。

向用户展示判定。如果 CONCERNS，通过 `AskUserQuestion` 提出它们：
- 选项：`修订标记的问题` / `接受并继续` / `进一步讨论`
如果 REJECT，在问题解决之前不要继续到阶段 6 判定。

如果故事还没有实施文件（判定正在实施完成之前运行），跳过此阶段并注意："LP-CODE-REVIEW 已跳过——未找到实施文件。实施完成后再运行。"

## 阶段 6: 展示完成报告

在更新任何文件之前，展示完整报告：

```markdown
## 故事完成: [故事名称]
**故事**: [文件路径]
**日期**: [今天]

### 验收标准: [X/Y 通过]
- [x] [标准 1] — 自动验证（测试通过）
- [x] [标准 2] — 已确认
- [ ] [标准 3] — 失败：[原因]
- [?] [标准 4] — 延迟：需要试玩

### 测试-标准可追踪性
| 标准 | 测试 | 状态 |
|-----------|------|--------|
| AC-1: [文本] | [测试文件::测试名称] | COVERED |
| AC-2: [文本] | 手动确认 | COVERED |
| AC-3: [文本] | — | UNTESTED |

### 测试证据
**故事类型**: [Logic | Integration | Visual/Feel | UI | Config/Data | 未声明]
**必需证据**: [单元测试文件 | 集成测试或试玩 | 截图 + 签核 | 走查文档 | 冒烟检查通过]
**找到的证据**: [是 — `[路径]` | 否 — 阻塞 | 否 — 建议性]

### 偏差
[无] 或：
- 阻塞: [描述] — [GDD/ADR 引用]
- 建议性: [描述] — 用户接受 / 标记技术债务

### 范围
[所有更改都在所述范围内] 或：
- 触及的附加文件：[列表] — [注意是否有效或范围蠕变]

### 判定: 完成 / 附备注完成 / 已阻塞
```

**判定定义：**
- **完成**：所有标准通过，无阻塞偏差
- **附备注完成**：所有标准通过，建议性偏差已记录
- **已阻塞**：失败标准或阻塞偏差必须先解决

如果判定是**已阻塞**：不要继续到阶段 7。列出必须修复的内容。提供帮助修复阻塞项。

## 阶段 7: 更新故事状态

在写入之前询问："我可以更新故事文件将其标记为完成并记录完成备注吗？"

如果是，编辑故事文件：

1. 更新状态字段：`Status: Complete`
2. 在底部添加 `## Completion Notes` 部分：

```markdown
## Completion Notes
**已完成**: [日期]
**标准**: [X/Y 通过] ([任何延迟项目列表])
**偏差**: [无] 或 [建议性偏差列表]
**测试证据**: [Logic: 测试文件在路径 | Visual/Feel: 证据文档在路径 | 不需要 (Config/Data)]
**代码审查**: [待定 / 完成 / 已跳过]
```

3. 如果存在建议性偏差，询问："我应该将这些记录为 `docs/tech-debt-register.md` 中的技术债务吗？"

4. **更新 `production/sprint-status.yaml`**（如果存在）：
   - 查找匹配此故事文件路径或 ID 的条目
   - 设置 `status: done` 和 `completed: [今天日期]`
   - 更新顶级 `updated` 字段
   - 这是静默更新——上面已批准，不需要额外批准

### 会话状态更新

更新故事文件后，静默附加到 `production/session-state/active.md`：

```
 ## 会话提取 — /story-done [日期]
  - 判定: [完成 / 附备注完成 / 已阻塞]
  - 故事: [故事文件路径] — [故事标题]
  - 技术债务已记录: [N 个项目，或"无"]
  - 下一个推荐: [下一个准备故事标题和路径，或"未识别"]
```

如果 `active.md` 不存在，使用此块作为初始内容创建它。

在对话中确认："会话状态已更新。"

---

## 阶段 8: 呈现下一个故事

完成后，帮助开发者保持动量：

1. 从 `production/sprints/` 读取当前冲刺计划。
2. 查找符合以下条件的故事：
   - 状态：READY 或 NOT STARTED
   - 不被其他未完成故事阻塞
   - 在 Must Have 或 Should Have 层中

展示：

```
### 接下来
以下故事已准备好拾取：
1. [故事名称] — [1 行描述] — 预估：[X 小时]
2. [故事名称] — [1 行描述] — 预估：[X 小时]

在开始前运行 `/story-readiness [路径]` 确认故事已准备好实施。
```

如果此冲刺中没有更多 Must Have 故事（全部完成或已阻塞）：

```
### 冲刺关闭序列
所有 Must Have 故事都已完成。在推进之前需要 QA 签核。
按顺序运行这些：

1. `/smoke-check sprint` — 验证关键路径仍然端到端工作
2. `/team-qa sprint` — 完整 QA 循环：测试用例执行、错误分类、签核报告
3. `/gate-check` — 一旦 QA 批准就推进到下一阶段
```

在 `/team-qa` 返回批准或附条件批准之前，不要运行 `/gate-check`。

如果仍有 Should Have 故事未开始，在关闭序列旁边展示它们，以便用户可以选择：现在关闭冲刺，或首先拉入更多工作。

如果没有更多故事准备好，但 Must Have 故事仍在进行中（不是完成）：
"没有更多故事准备好开始——[N] 个 Must Have 故事仍在进行中。在开始冲刺关闭之前继续实施那些。"

## 协作协议

- **没有用户批准永远不要将故事标记为完成**——阶段 7 在任何文件编辑之前需要明确的"是"。
- **永远不要自动修复失败标准**——报告它们并询问要做什么。
- **偏差是事实，不是判断**——中立地展示它们；用户决定它们是否可接受。
- **阻塞判定是建议性**——用户仍然可以覆盖并无论如何将故事标记为完成；如果他们这样做，明确记录风险。
- 使用 `AskUserQuestion` 进行代码审查提示和批处理手动标准确认。
