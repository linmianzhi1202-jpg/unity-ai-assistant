# 团队音频技能

## 技能概述

协调多代理音频实现。此技能通过结构化管道协调音频团队，生成音频设计文档、Sound SFX 规范、技术实现说明和音频集成验证。

**适用场景**：
- 新功能或区域的音频设计
- 协调音频导演、声音设计师、技术艺术家和游戏玩法程序员
- 验证音频集成和可访问性合规

## 使用方式

- 通过 Agent 触发：当用户说「团队音频」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill team-audio [参数]`

---

## 阶段 0: 解析参数

**参数**: `$ARGUMENTS[0]` (空白 = 询问用户）

从参数确定模式：

- **功能名称**（例如 `combat`、`main menu`）→ 为此功能设计音频
- **区域名称**（例如 `forest biome`、`boss encounter`）→ 为此区域设计音频
- **无参数** → 使用 `AskUserQuestion`：
  ```
  你想为哪个功能或区域设计音频？
  - 选项："特定功能（输入名称）"、"特定区域（输入名称）"、"显示当前冲刺的所有音频故事"
  ```

---

## 阶段 1: 加载上下文

在生成任何内容之前，加载参考文档：

1. **读取当前冲刺计划** 从 `production/sprints/`（如果适用）
2. **读取音频设计文档** 在 `design/gdd/sound-bible.md`（如果存在）
3. **读取现有音频资产列表** 在 `assets/audio/` 中
4. **读取技术参考** 从 `.claude/docs/technical-preferences.md` 获取引擎特定音频 API
5. **读取可访问性要求**（如果项目需要）

报告找到了什么："音频设计文档：[找到/未找到]。引擎：[引擎名称]。现有音频资产：[计数]。"

---

## 阶段 2: 音频方向（音频导演）

**生成音频导演代理** 使用 Task 生成 `audio-director`：

传递：
- 功能/区域描述
- 情感 tone 和音频调色板
- 音乐方向（自适应层、主干、转换）
- 音频优先级和混合目标
- 任何现有的音频设计文档部分

**音频导演生成**：

```
## 音频方向：[功能/区域名称]

### 声音身份
[定义此功能/区域的独特音频特征]

### 情感 Tone
[描述音频应该唤起的感觉]

### 音频调色板
[列出关键音频元素和其特征]

### 音乐方向
[自适应层、主干，触发条件]

### 音频优先级
[列出优先级层次结构]

### 混合目标
[目标音量级别、闪避规则]
```

**在继续之前等待用户批准**。如果拒绝，则迭代。

---

## 阶段 3: 声音设计和 SFX 规范（声音设计师 + 可访问性专家）

**并行生成** 两个代理：

### 声音设计师代理

**生成声音设计师代理** 使用 Task 生成 `sound-designer`：

传递：
- 音频方向文档
- 功能/区域描述
- 现有音频资产列表

**声音设计师生成**：

```
## Sound SFX 规范：[功能/区域]

### 音频事件列表
| 事件 ID | 描述 | 触发器条件 | 优先级 |
|---------|------|--------------|----------|
| [event_id] | [描述] | [何时触发] | [高/中/低] |

### SFX 参数
| 参数 | 默认值 | 范围 | 说明 |
|-----------|-----------|--------|----------|
| [parameter] | [value] | [min-max] | [description] |

### 混合组
[定义混合组和闪避规则]

### 衰减设置
[距离衰减模型、最大距离]
```

### 可访问性专家代理

**生成可访问性专家代理** 使用 Task 生成 `accessibility-specialist`：

传递：
- 音频事件列表
- 功能/区域描述
- 可访问性要求（如果已知）

**可访问性专家生成**：

```
## 音频可访问性需求

### 关键游戏玩法音频
[列出必须有的视觉替代的音频事件]

### 字幕要求
[哪些音频事件需要字幕、文本格式、屏幕上持续时间]

### 音频敏感度检查
[标记潜在问题的音频事件：高频警报、突然的大声事件]
```

**并行运行两个代理**，然后使用 `AskUserQuestion` 展示结果：

```
question: "声音设计和可访问性规范已就绪。继续？"
options:
  - "是的，继续到技术实现"
  - "需要修订声音设计"
  - "需要修订可访问性需求"
```

---

## 阶段 4: 技术实现（技术艺术家 + 引擎专家）

**并行生成** 两个代理：

### 技术艺术家代理

**生成技术艺术家代理** 使用 Task 生成 `technical-artist`：

传递：
- Sound SFX 规范
- 音频方向文档
- 引擎特定 API 参考

**技术艺术家生成**：

```
## 音频技术实现计划

### 音频中间件集成
[Wwise/FMOD 设置、总线结构、路由]

### 音频资产流
[流 vs 预加载策略、内存预算]

### 平台特定注意事项
[控制台特定音频限制、移动音频优化]
```

### 引擎专家代理

**生成引擎专家代理**（如果引擎已配置）使用 Task 生成 `[engine]-specialist`：

传递：
- 技术实现计划
- 引擎特定音频 API 从 `.claude/docs/technical-preferences.md`

**引擎专家验证**：

```
## 引擎音频集成验证

### API 使用合规性
[验证建议的实现是否符合引擎最佳实践]

### 性能影响
[音频系统对帧率的影响、内存使用]
```

**如果引擎未配置**，跳过此代理并记录"引擎未配置——跳过引擎特定验证。在 `/setup-engine` 后重新运行此阶段。"

**并行运行两个代理**，然后展示结果并询问批准。

---

## 阶段 5: 代码集成（游戏玩法程序员）

**生成游戏玩法程序员代理** 使用 Task 生成 `gameplay-programmer`：

传递：
- 音频事件列表
- Sound SFX 规范
- 技术实现计划
- 引擎特定集成验证

**游戏玩法程序员生成**：

```
## 音频管理器实现计划

### 音频管理器系统
[类设计、职责、接口]

### 游戏玩法触发器集成
[如何将音频事件绑定到游戏玩法事件]

### 自适应音乐系统
[如果指定，实现自适应音乐逻辑]

### 单元测试
[音频事件触发的测试、集成测试]
```

**在继续之前等待批准**。展示实现计划并询问："音频管理器实现计划已就绪。开始实施？"

---

## 阶段 6: 编译音频设计文档

编译所有代理输出到单个文档：

```markdown
# 音频设计：[功能/区域名称]

**生成日期**: [今天]
**版本**: 1.0

## 音频方向
[来自音频导演的输出]

## Sound SFX 规范
[来自声音设计师的输出]

## 可访问性需求
[来自可访问性专家的输出]

## 技术实现
[来自技术艺术家和引擎专家的输出]

## 代码集成
[来自游戏玩法程序员的输出]

## 音频事件清单
[所有音频事件的完整列表，带有参数]

## 下一步
[实施前需要完成的任务列表]
```

**询问**："我可以写入此音频设计文档到 `design/gdd/audio-[feature].md` 吗？"

仅在批准后写入。

---

## 阶段 7: 下一步

写入音频设计文档后，建议后续步骤：

- 运行 `/story-readiness [story-path]` 以在实施前验证故事准备情况
- 运行 `/dev-story [story-path]` 以开始实施音频管理器
- 如果音频设计需要更新，运行 `/reverse-document` 从现有音频代码生成文档
- 运行 `/scope-check [feature]` 以验证音频范围符合原始史诗范围

---

## 协作协议

此技能遵循协作设计原则：

1. **首先生成方向**：首先建立音频方向，然后派生规范
2. **并行生成**：在阶段 3 和 4 中并行运行代理以节省时间
3. **展示发现**：在继续之前，展示每个代理的输出以获取反馈
4. **用户决定**：用户选择方向、批准规范、决定实施顺序
5. **获取批准**：在写入任何文件之前始终询问
6. **记录决策**：在音频设计文档中记录所有决策及其原因
