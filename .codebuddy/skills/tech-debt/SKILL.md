# 技术债务技能#

## 技能概述#

识别技术债务，优先偿还，防止积累。技术债务不一定是坏事 — 它可以是工具。注册表跟踪有意识的决策。

**适用场景**：
- 定期扫描代码库以捕获新债务
- 手动添加新债务条目（原型、截止日期决策）
- 重新优先级排序现有债务注册表
- 生成债务状态报告以跟踪趋势

**输出**：债务注册表更新或摘要报告（对话中）

## 使用方式#

- 通过 Agent 触发：当用户说「技术债务」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill tech-debt [子命令]`

**子命令模式**：
- `/tech-debt scan` — 扫描代码库中的债务指标
- `/tech-debt add` — 手动添加新债务条目
- `/tech-debt prioritize` — 重新优先级排序现有债务注册表
- `/tech-debt report` — 生成当前债务状态摘要报告
- 无参数 — 输出用法并停止。判定：**失败** — 缺少必需的子命令。

## 阶段 0: 解析子命令#

**参数**: `$ARGUMENTS[0]` (空白 = 输出用法并停止）

从参数确定模式：

| 参数 | 模式 | 操作 |
|----------|------|----------|
| `scan` | 扫描模式 | 扫描代码库的债务指标 |
| `add` | 添加模式 | 提示债务详细信息并添加到注册表 |
| `prioritize` | 优先级模式 | 重新优先级排序现有注册表 |
| `report` | 报告模式 | 生成摘要统计和趋势 |
| 无参数 | 用法 | 输出用法并停止 |

## 阶段 1: 扫描模式#

扫描代码库的债务指标：

### 债务指标#

搜索代码库以查找债务指标：

- `TODO` 注释（计数并按类别分类）
- `FIXME` 注释（这些是伪装成债务的 Bug）
- `HACK` 注释（需要正确解决方案的权宜之计）
- `@deprecated` 标记（已弃用的 API 或方法）
- 重复代码块（多个文件中的相似模式）
- 超过 500 行的文件（潜在的 God 对象）
- 超过 50 行的函数（潜在的复杂性）

### 债务分类#

将每个发现分类：

| 类别 | 描述 | 修复方向 |
|-------|-------------|---------------|
| **架构债务** | 错误的抽象、缺失的模式、耦合问题 | 重构为正确模式 |
| **代码质量债务** | 重复、复杂性、命名、缺失类型 | 代码质量改进 |
| **测试债务** | 缺失的测试、不稳定的测试、未测试的边缘情况 | 测试覆盖改进 |
| **文档债务** | 缺失的文档、过时的文档、未记录的 API | 文档更新 |
| **依赖债务** | 过时的包、已弃用的 API、版本冲突 | 依赖项更新 |
| **性能债务** | 已知的慢路径、未优化的查询、内存问题 | 性能优化 |

## 阶段 2: 添加模式#

提示用户输入：

### 输入收集#

提示以下内容：
- **描述**：债务是什么？
- **类别**：架构 / 代码质量 / 测试 / 文档 / 依赖 / 性能
- **受影响的文件**：哪些文件受此债务影响？
- **估算修复工作量**：S（小）、M（中）、L（大）、XL（特大）
- **如果未修复的影响**：不修复会发生什么？
- **添加日期**：今天
- **冲刺**：安排修复的冲刺编号，或"待办"如果未安排

### 展示新条目#

向用户展示新条目：

```

| ID | 类别 | 描述 | 文件 | 工作量 | 影响 | 优先级 | 添加日期 | 冲刺 |
|----|----------|-------------|-------|--------|--------|----------|----------|-------|
| [TD-XXX] | [类别] | [描述] | [文件] | [S/M/L/XL] | [高/中/低] | [分数] | [日期] | [冲刺] |
```

询问："我可以将此条目附加到 `docs/tech-debt-register.md` 吗？"

如果是：附加条目。判定：**完成** — 条目已添加到注册表。
如果否：在此处停止。判定：**已阻止** — 用户拒绝写入。

## 阶段 3: 优先级排序模式#

读取 `docs/tech-debt-register.md` 中的债务注册表。

### 计算优先级分数#

为每个条目计算优先级分数：

```
优先级分数 = (如果未修复的影响 × 遭遇频率) / 修复工作量
```

其中：
- **影响**：高 = 3，中 = 2，低 = 1
- **频率**：每次冲刺 = 3，每月 = 2，很少 = 1
- **工作量**：S = 1，M = 2，L = 4，XL = 8

### 重新排序注册表#

按优先级分数降序重新排序注册表。

向用户展示重新优先级排序的注册表：

```
## 重新优先级排序的技术债务注册表#

| ID | 类别 | 描述 | 工作量 | 影响 | 优先级 | 添加日期 | 冲刺 |
|----|----------|-------------|--------|--------|----------|----------|-------|
| TD-003 | 架构债务 | [描述] | M | 高 | 6.0 | [日期] | [冲刺] |
| TD-001 | 测试债务 | [描述] | S | 中 | 4.0 | [日期] | [冲刺] |
| TD-002 | 文档债务 | [描述] | L | 低 | 0.5 | [日期] | 待办 |
```

询问："我可以将重新优先级排序的注册表写回 `docs/tech-debt-register.md` 吗？"

如果是：写入更新的文件。判定：**完成** — 注册表已重新优先级排序并保存。
如果否：在此处停止。判定：**已阻止** — 用户拒绝写入。

## 阶段 4: 报告模式#

读取债务注册表。生成摘要统计：

### 报告内容#

生成包含以下内容的报告：

```
## 技术债务状态报告#

**生成日期**: [今天]
**自上次报告以来的变化**: [N] 个新条目，[N] 个已解决条目

### 摘要统计#

- **总条目**: [N]
- **按类别**:
  - 架构债务: [N]
  - 代码质量债务: [N]
  - 测试债务: [N]
  - 文档债务: [N]
  - 依赖债务: [N]
  - 性能债务: [N]

- **按优先级**:
  - 高（分数 > 4.0): [N] 个条目
  - 中（分数 2.0-4.0): [N] 个条目
  - 低（分数 < 2.0): [N] 个条目

- **总估算修复工作量**: [所有条目的 T 恤尺码总和]

### 趋势方向#

- **增长**: 新条目 > 已解决条目
- **稳定**: 新条目 ≈ 已解决条目
- **缩减**: 新条目 < 已解决条目

### 旧条目标志#

[在注册表中超过 3 个冲刺的条目]

### 下一步建议#

- 在下一个冲刺中安排 [N] 个高优先级条目
- 考虑安排 [N] 个中优先级条目
- 审查 [N] 个旧条目 — 修复或 consciously 接受并记录原因
```

**注意**：此模式是只读的 — 不修改注册表。仅生成报告。

判定：**完成** — 债务报告已生成。

## 阶段 5: 下一步#

- 运行 `/sprint-plan` 以将高优先级债务条目安排到下一个冲刺中
- 运行 `/tech-debt report` 在每个冲刺开始时以跟踪债务随时间的变化趋势
- 在原型制作期间使用 `/tech-debt add` 记录有意识的债务决策

## 债务注册表格式#

```markdown
## 技术债务注册表#

最后更新: [日期]
总条目: [N] | 总估算工作量: [T 恤尺码总和]

| ID | 类别 | 描述 | 文件 | 工作量 | 影响 | 优先级 | 添加日期 | 冲刺 |
|----|----------|-------------|-------|--------|--------|----------|----------|-------|
| TD-001 | [类别] | [描述] | [文件] | [S/M/L/XL] | [低/中/高] | [分数] | [日期] | [冲刺编号] 或 ["待办"] |
```

### 规则#

- 技术债务本质上并不坏 — 它是一个工具。注册表跟踪有意识的决策。
- 每个债务条目必须解释为什么接受它（截止日期、原型、缺失信息）
- "扫描"应每个冲刺至少运行一次以捕获新债务
- 超过 3 个冲刺而无操作的条目应要么修复，要么 consciously 接受并记录原因

---

## 协作协议#

- **报告发现，不要修复它们** — 此技能扫描并评估；它不修改代码文件
- **有意识的决策** — 注册表中的每个条目应代表有意识的选择，而不是疏忽
- **优先级分数是指导** — 使用判断；有时低分数条目可能值得尽早修复
- **在写入之前询问** — 注册表更新需要明确批准
- **债务是团队问题** — 清楚地展示列表和建议的操作；不要在没有团队知情的情况下静默添加
