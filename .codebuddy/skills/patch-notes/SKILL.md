# 补丁说明技能

## 技能概述

为更新创建玩家友好说明。此技能提供结构化的补丁说明生成工作流程，包括解析参数、收集变更数据、检测基调和模板、分类和翻译、生成补丁说明、审查输出和保存。

## 使用方式

- 通过 Agent 触发：当用户说「补丁说明」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill patch-notes [version] [--style brief|detailed|full]`

---

## Phase 1: 解析参数

- `version`：要生成说明的发布版本（例如 `1.2.0`）
- `--style`：输出风格 — `brief`（要点）、`detailed`（含上下文，默认）、`full`（含开发者评论）
- 如果未提供版本，在继续之前询问用户。

---

## Phase 2：收集变更数据

- 如果存在，读取 `production/releases/[version]/changelog.md` 中的内部变更日志
- 也检查 `docs/CHANGELOG.md` 中的相关版本条目
- 作为回退，运行 `git log` 在前一个发布标签和当前标签/HEAD 之间
- 读取 `production/sprints/` 中的冲刺回顾以获取上下文
- 读取 `design/balance/` 中的任何平衡更改文档
- 如果可用，从 QA 读取错误修复记录

**如果没有可用的变更日志数据**（既不存在 `production/releases/[version]/changelog.md` 或 `docs/CHANGELOG.md` 条目，且 git log 为空或不可用）：

> "未找到 [version] 的变更日志数据。首先运行 `/changelog [version]` 以生成内部变更日志，然后重新运行 `/patch-notes [version]`。"

结论：**已锁定** — 在此处停止而不生成说明。

---

## Phase 2b：检测基调指南和模板

**基调指南检测** — 在起草说明之前，检查写作风格指导：

1. 检查 `.claude/docs/technical-preferences.md` 中是否有 "tone"、"voice" 或 "style" 字段或部分。
2. 如果存在，读取 `docs/PATCH-NOTES-STYLE.md`。
3. 如果存在，读取 `design/community/tone-guide.md`。
4. 如果任何来源包含基调/声音/风格说明，提取它们并将其应用到生成的说明的语言和框架中。
5. 如果任何地方都未找到基调指导，默认为：
   玩家友好、非技术性语言；热情但不过度夸张；关注玩家体验什么，而不是开发者改变了什么。

**模板检测** — 检查是否存在补丁说明模板：

1. 扫描 `docs/patch-notes-template.md` 和 `.claude/docs/templates/patch-notes-template.md`。
2. 如果在任一位置找到，读取它并将其用作 Phase 4 的输出结构，而不是内置样式模板（Brief / Detailed / Full）。用分类数据填充模板的部分。
3. 如果未找到，使用 Phase 4 中定义的内置样式模板。

---

## Phase 3：分类和翻译

将所有更改分类到面向玩家的类别中：

- **新内容**：新功能、地图、角色、物品、模式
- **游戏性更改**：平衡调整、机制更改、进度更改
- **生活质量**：UI 改进、便利功能、可访问性
- **错误修复**：按系统分组（战斗、UI、网络等）
- **性能**：玩家可能注意到的优化改进
- **已知问题**：关于未解决问题的透明度

将开发者语言翻译为玩家语言：

- "重构了伤害计算管道" → "改进了命中检测准确性"
- "修复了库存管理器中的空引用" → "修复了打开库存时的崩溃"
- "减少了战斗循环中的 GC 分配" → "改进了战斗性能"
- 删除完全不影响玩家的纯内部更改
- 保留平衡更改的具体数字（伤害：50 → 45）

---

## Phase 4：生成补丁说明

### 简洁风格

```markdown
# 补丁 [版本] — [标题]

**新内容**
- [功能 1]
- [功能 2]

**更改**
- [平衡/机制更改，带之前 → 之后的值]

**修复**
- [错误修复 1]
- [错误修复 2]

**已知问题**
- [问题 1]
```

### 详细风格

```markdown
# 补丁 [版本] — [标题]
*[日期]*

## 亮点
[1-2 句话总结最令人兴奋的更改]

## 新内容
### [功能名称]
[2-3 句话描述该功能以及玩家应该为什么感到兴奋]

## 游戏性更改
### 平衡
| 更改 | 之前 | 之后 | 原因 |
| ---- | ---- | ---- | ---- |
| [物品/能力] | [旧值] | [新值] | [简要理由] |

### 机制
- **[更改]**：[解释什么已更改以及为什么]

## 生活质量
- [含上下文的改进]

## 错误修复
### 战斗
- 修复了 [玩家体验的描述]

### UI
- 修复了 [描述]

### 网络
- 修复了 [描述]

## 性能
- [玩家会注意到的改进]

## 已知问题
- [问题以及可用的解决方法]
```

### 完整风格

包含详细风格的所有内容，加上：

```markdown
## 开发者评论
### [主题]
> [开发者对重大更改的见解 — 为什么这样做、考虑了什么、
> 团队学到了什么。用第一人称团队声音书写。]
```

---

## Phase 5：审查输出

检查生成的说明：

- 无内部行话（用玩家友好的语言替换技术术语）
- 无对内部系统、工单或冲刺编号的引用
- 平衡更改包含之前/之后的值
- 错误修复描述玩家体验，而不是技术原因
- 基调匹配游戏的声音（根据游戏风格调整正式程度）

---

## Phase 6：保存补丁说明

向用户展示完成的补丁说明以及：按类别的更改计数和排除的任何内部更改（用于审查）。

询问："我可以将这些补丁说明写入 `docs/patch-notes/[version].md` 吗？"

如果可以，将文件写入 `docs/patch-notes/[version].md`，必要时创建目录。也写入 `production/releases/[version]/patch-notes.md` 作为内部存档副本。

---

## Phase 7：下一步

结论：**完成** — 补丁说明已生成并保存。

- 在发布之前运行 `/release-checklist` 以验证所有其他发布门控是否满足。
- 在公开发布之前，与社区经理分享补丁说明草案以进行基调审查。
