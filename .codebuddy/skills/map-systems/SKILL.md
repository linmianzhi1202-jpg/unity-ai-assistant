# 映射系统技能

## 技能概述

将游戏概念分解为独立系统，映射依赖关系，生成系统索引文档。

## 使用方式

- 通过 Agent 触发：当用户说「映射系统」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：```/skill map-systems [参数]```

## 工作流

### 参数解析

两种模式：

- **无参数**：`/map-systems` — 运行完整的分解工作流（阶段 1-5），创建或更新系统索引
- **`next`**：`/map-systems next` — 从索引中选择优先级最高的未设计系统，并移交给 `/design-system`（阶段 6）

同时解析审查模式（一次性，为本次运行中的所有门控生成存储）：
1. 如果传递了 `--review [full|lean|solo]` → 使用其值
2. 否则读取 `production/review-mode.txt` → 使用其值
3. 否则 → 默认为 `lean`

---

### 阶段 1：读取概念（必需上下文）

读取游戏概念和任何现有设计工作。这为系统分解提供原始材料。

**必需操作：**
- 读取 `design/gdd/game-concept.md` — **如果缺失，用清晰消息失败**：
  > "在 `design/gdd/game-concept.md` 中未找到游戏概念。请先运行 `/brainstorm` 创建一个，然后再回来将其分解为系统。"

**可选操作（如果存在则读取）：**
- 读取 `design/gdd/game-pillars.md` — 支柱约束优先级和范围
- 读取 `design/gdd/systems-index.md` — 如果存在，**恢复**从中断处继续（更新，不要从头重新创建）
- 全局搜索 `design/gdd/*.md` — 检查哪些系统 GDD 已存在

**如果系统索引已存在：**
- 读取它并向用户展示当前状态
- 使用 `AskUserQuestion` 询问：
  "系统索引已存在，包含 [N] 个系统（[M] 个已设计，[K] 个未开始）。你想做什么？"
  - 选项："用新系统更新索引"、"设计下一个未设计的系统"、"审查和修订优先级"

---

### 阶段 2：系统枚举（协作式）

提取并识别游戏所需的所有系统。这是技能的创意核心 — 它需要人工判断，因为概念文档很少显式枚举每个系统。

#### 步骤 2a：提取显式系统

扫描游戏概念中直接提到的系统和机制：
- 核心机制部分（最显式）
- 核心循环部分（暗示每个循环层由什么系统驱动）
- 技术考虑部分（网络、过程生成等）
- MVP 定义部分（必需功能 = 必需系统）

#### 步骤 2b：识别隐式系统

对于每个显式系统，识别它**隐含的隐藏系统**。游戏总是需要比概念文档提到的更多系统。使用此推理模式：

- "背包" 隐含：物品数据库、装备槽、重量/容量规则、背包 UI、物品序列化（用于保存/加载）
- "战斗" 隐含：伤害计算、生命值系统、命中检测、状态效果、敌人 AI、战斗 UI（血条、伤害数字）、死亡/重生
- "开放世界" 隐含：流式加载/分块、LOD 系统、快速旅行、地图/小地图、兴趣点跟踪、世界状态持久化
- "多人游戏" 隐含：网络层、大厅/匹配、状态同步、防作弊、网络 UI（ping、玩家列表）
- "制作" 隐含：配方数据库、原料收集、制作 UI、成功/失败机制、配方发现/学习
- "对话" 隐含：对话树系统、对话 UI、选择跟踪、NPC 状态管理、本地化钩子
- "进度" 隐含：XP 系统、升级机制、技能树、解锁跟踪、进度 UI、进度保存数据

在对话文本中解释为什么每个隐式系统是必需的（附示例）。

#### 步骤 2c：用户审查

按类别组织展示枚举结果。对于每个系统，显示：
- 名称
- 类别
- 简要描述（1 句话）
- 是显式（来自概念）还是隐式（推断的）

然后使用 `AskUserQuestion` 捕获反馈：
- "此列表中是否缺少系统？"
- "其中是否有系统应该合并或拆分？"
- "是否有列出的系统是此游戏不需要的？"

迭代直到用户批准枚举。

---

### 阶段 3：依赖映射（协作式）

对于每个系统，确定它依赖什么。如果一个系统不能在没有另一个系统存在的情况下运行，则它"依赖于"另一个系统。

#### 步骤 3a：映射依赖关系

对于每个系统，列出其依赖关系。使用这些依赖启发式：
- **输入/输出依赖**：系统 A 产生系统 B 需要的数据
- **结构依赖**：系统 A 提供系统 B 插入的框架
- **UI 依赖**：每个游戏性系统都有相应的 UI 系统依赖于它（但 UI 在游戏性系统之后设计）

#### 步骤 3b：按依赖顺序排序

将系统排列成层：
1. **基础**：零依赖的系统（首先设计和构建）
2. **核心**：仅依赖于基础系统的系统
3. **功能**：依赖于核心系统的系统
4. **表现**：包装游戏性系统的 UI 和反馈系统
5. **打磨**：元系统、教程、分析、可访问性

#### 步骤 3c：检测循环依赖

检查依赖图中的循环。如果发现：
- 向用户高亮显示它们
- 提出解决方案（接口抽象、同时设计、通过定义两个系统之间的契约来打破循环）

#### 步骤 3d：向用户展示

将依赖关系图显示为分层列表。高亮显示：
- 任何循环依赖
- 任何"瓶颈"系统（许多其他系统依赖于它们 — 这些是高风险）
- 任何没有依赖者的系统（叶节点 — 风险较低，可以晚些设计）

使用 `AskUserQuestion` 询问："此依赖顺序看起来正确吗？我是否遗漏或应该移除某些依赖关系？"

**审查模式检查** — 在生成 TD-SYSTEM-BOUNDARY 之前应用：
- `solo` → 跳过。注意："TD-SYSTEM-BOUNDARY 已跳过 — 单人模式。" 继续优先级分配。
- `lean` → 跳过（不是阶段门控）。注意："TD-SYSTEM-BOUNDARY 已跳过 — 精简模式。" 继续优先级分配。
- `full` → 正常生成。

**依赖映射批准后，在继续优先级分配之前，通过 Task 使用门 TD-SYSTEM-BOUNDARY (`.claude/docs/director-gates.md`) 生成 `technical-director`。**

传递：依赖关系图摘要、层分配、瓶颈系统列表、任何循环依赖解决方案。

展示评估。如果 REJECT，在继续优先级分配之前与用户一起修订系统边界。如果 CONCERNS，将它们内联记录在系统索引中并继续。

---

### 阶段 4：优先级分配（协作式）

根据系统所需的里程碑将每个系统分配给优先级层。

#### 步骤 4a：基于概念自动分配

使用这些启发式进行初始分配：
- **MVP**：概念的"MVP 必需"部分提到的系统，加上它们的基础层依赖关系
- **垂直切片**：在一个区域中完整体验所需的系统
- **Alpha**：所有剩余的游戏性系统
- **完整愿景**：打磨、元系统和锦上添花的系统

#### 步骤 4b：用户审查

在表格中展示优先级分配。对于每个层，解释为什么系统放在那里。

使用 `AskUserQuestion` 询问："这些优先级分配是否符合你的愿景？哪些系统应该更高或更低优先级？"

在对话中解释推理："我将 [system] 放在 MVP 中，因为核心循环需要它 — 没有 [system]，30 秒循环无法运行。"

**"为什么"列指导**：解释为什么每个系统放在优先级层时，将技术必要性与玩家体验推理混合。不要使用纯粹的技术理由，如"战斗需要伤害数学" — 在相关时将玩家体验连接起来。

**审查模式检查** — 在生成 PR-SCOPE 之前应用：
- `solo` → 跳过。注意："PR-SCOPE 已跳过 — 单人模式。" 继续写入系统索引。
- `lean` → 跳过（不是阶段门控）。注意："PR-SCOPE 已跳过 — 精简模式。" 继续写入系统索引。
- `full` → 正常生成。

**优先级批准后，在写入索引之前，通过 Task 使用门 PR-SCOPE (`.claude/docs/director-gates.md`) 生成 `producer`。**

传递：每个里程碑层的系统总数、每层估计实现量（系统数 × 平均复杂度）、团队规模、 stated 项目时间表。

展示评估。如果 UNREALISTIC，在写入索引之前提供修订优先级层分配。如果 CONCERNS，注意它们并继续。

#### 步骤 4c：确定设计顺序

结合依赖排序 + 优先级层来生成最终设计顺序：
1. MVP 基础系统优先
2. MVP 核心系统第二
3. MVP 功能系统第三
4. 垂直切片基础/核心系统
5. ...以此类推

这是团队应该编写 GDD 的顺序。

---

### 阶段 5：创建系统索引（写入）

#### 步骤 5a：起草文档

使用 `.claude/docs/templates/systems-index.md` 中的模板，用阶段 2-4 的所有数据填充系统索引：
- 填充枚举表格
- 填充依赖关系图
- 填充推荐的设计顺序
- 填充高风险系统
- 填充进度跟踪器（所有系统最初为"未开始"，除非 GDD 已存在）

#### 步骤 5b：批准

展示文档摘要：
- 按类别的系统总数
- MVP 系统计数
- 设计顺序中的前 3 个系统
- 任何高风险项

询问："我可以将系统索引写入 `design/gdd/systems-index.md` 吗？"

等待批准。仅在"是"之后写入文件。

**审查模式检查** — 在生成 CD-SYSTEMS 之前应用：
- `solo` → 跳过。注意："CD-SYSTEMS 已跳过 — 单人模式。" 继续阶段 7 下一步。
- `lean` → 跳过（不是阶段门控）。注意："CD-SYSTEMS 已跳过 — 精简模式。" 继续阶段 7 下一步。
- `full` → 正常生成。

**系统索引写入后，通过 Task 使用门 CD-SYSTEMS (`.claude/docs/director-gates.md`) 生成 `creative-director`。**

传递：系统索引路径、游戏支柱和核心幻想（来自 `design/gdd/game-concept.md`）、MVP 优先级层系统列表。

展示评估。如果 REJECT，在 GDD 编写开始之前与用户一起修订系统集。如果 CONCERNS，将它们作为 `> **Creative Director Note**` 记录在系统索引中相关层部分的顶部。

#### 步骤 5c：更新会话状态

写入后，如果不存在则创建 `production/session-state/active.md`，然后更新它：
- 任务：系统分解
- 状态：系统索引已创建
- 文件：design/gdd/systems-index.md
- 下一步：设计单个系统 GDD

**判定：COMPLETE** — 系统索引已写入 `design/gdd/systems-index.md`。
如果用户拒绝：**判定：BLOCKED** — 用户未批准写入。

### 阶段 6：设计单个系统（移交给 /design-system）

此阶段在以下情况下进入：
- 用户在对索引说"是"之后说"是"以设计系统
- 用户调用 `/map-systems [system-name]`
- 用户调用 `/map-systems next`

#### 步骤 6a：选择系统

- 如果提供了系统名称，在系统索引中找到它
- 如果使用了 `next`，选择优先级最高的未设计系统（按设计顺序）
- 如果用户刚完成索引，询问：
  "你想现在开始设计单个系统吗？设计顺序中的第一个系统是 [name]。或者你更愿意在这里停止并稍后回来吗？"

使用 `AskUserQuestion`："现在开始设计 [system-name]，选择不同的系统，还是在这里停止？"

#### 步骤 6b：移交给 /design-system

选择系统后，调用 `/design-system [system-name]` 技能。

`/design-system` 技能处理完整的 GDD 编写过程：
- 从游戏概念、系统索引和依赖关系 GDD 收集上下文
- 立即创建文件骨架
- 一次遍历所有 8 个必需部分（协作式、增量式）
- 交叉引用现有文档以防止矛盾
- 路由到领域专家代理
- 一旦批准就立即将每个部分写入文件
- 完成后运行 `/design-review`
- 更新系统索引

**不要在此处复制 /design-system 工作流。** 此技能拥有系统*索引*；`/design-system` 拥有单个系统 *GDD*。

#### 步骤 6c：循环或停止

`/design-system` 完成后，使用 `AskUserQuestion`：
- "继续下一个系统（[next system name]）？"
- "选择不同的系统？"
- "在此会话中在此处停止？"

如果继续，返回步骤 6a。

---

### 阶段 7：建议下一步

创建系统索引后（或在设计一些系统之后），使用 `AskUserQuestion` 展示下一步操作：

- "系统索引已写入。你想下一步做什么？"
  - [A] 开始设计 GDD — 运行 `/design-system [first-system-in-order]`
  - [B] 首先要求主管审查索引 — 要求 `creative-director` 或 `technical-director` 在承诺到 10+ GDD 会话之前验证系统集
  - [C] 在此会话中在此处停止

**主管审查选项（[B]）值得高亮显示**：在开始 GDD 编写之前让创意主管或技术主管审查完成的系统索引，可以在它们被锁定到许多文档之前捕获范围问题、缺失系统和边界问题。它是可选的，但推荐用于新项目。

在任何单个 GDD 完成后：
- "在新鲜会话中运行 `/design-review design/gdd/[system].md` 以验证质量"
- "当所有 MVP GDD 完成时运行 `/gate-check systems-design`"

## 协作协议

此技能在每个阶段都遵循协作设计原则：

1. **问题 -> 选项 -> 决策 -> 草稿 -> 批准** 在每个步骤
2. **AskUserQuestion** 在每个决策点（解释 -> 捕获模式）：
   - 阶段 2："缺失系统？合并或拆分？"
   - 阶段 3："依赖顺序正确吗？"
   - 阶段 4："优先级分配符合你的愿景吗？"
   - 阶段 5："我可以写入系统索引吗？"
   - 阶段 6："开始设计、选择不同的或停止？" 然后移交给 `/design-system`
3. **"我可以写入 [filepath] 吗？"** 在每次文件写入之前
4. **增量写入**：在每个系统设计后更新系统索引
5. **移交**：单个 GDD 编写由 `/design-system` 拥有，它处理增量部分写入、交叉引用、设计审查和索引更新
6. **会话状态更新**：在每个里程碑（索引创建、系统设计、优先级更改）之后写入 `production/session-state/active.md`

**永远不要**自动生成完整系统列表并在没有审查的情况下写入。
**永远不要**在没有用户确认的情况下开始设计系统。
**始终**显示枚举、依赖关系和优先级供用户验证。
