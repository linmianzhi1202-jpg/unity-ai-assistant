# 团队叙事技能

## 技能概述

协调多代理团队开发叙事内容，包括故事弧线、角色设计、对话编写、世界观构建和环境叙事。

## 使用方式

- **通过 Agent 触发**：当用户说「团队叙事」或相关需求时，Agent 应自动加载此 Skill
- **手动触发**：`/skill team-narrative [叙事内容描述]`
- **使用示例**：`/skill team-narrative boss encounter cutscene`

**无参数时的行为**：如果未提供参数，输出使用指南并退出，不生成任何代理：
> 用法：`/team-narrative [叙事内容描述]` — 描述要处理的叙事内容、场景或叙事区域（例如：`boss encounter cutscene`、`faction intro dialogue`、`tutorial narrative`）。此处不要使用 `AskUserQuestion`；直接输出指南。

**有参数时的行为**：当提供参数时，通过结构化流程编排叙事团队。

**决策点**：在每个阶段转换时，使用 `AskUserQuestion` 向用户呈现子代理的方案作为可选选项。在对话中写入代理的完整分析，然后使用简洁的标签捕获决策。用户必须在继续下一阶段之前批准。

## 团队组成

- **叙事总监（narrative-director）** — 故事弧线、角色设计、对话策略、叙事愿景
- **作家（writer）** — 对话编写、传说条目、物品描述、游戏内文本
- **世界观构建师（world-builder）** — 世界规则、派系设计、历史、地理、环境叙事
- **艺术总监（art-director）** — 角色视觉设计、环境视觉叙事、过场动画/电影色调
- **关卡设计师（level-designer）** — 服务于叙事的关卡布局、节奏、环境叙事节拍
- **本地化负责人（localization-lead）** — i18n 验证、字符串键合规性、翻译余量

## 委托方式

使用 Task 工具生成每个团队成员作为子代理：

- `subagent_type: narrative-director` — 故事弧线、角色设计、叙事愿景
- `subagent_type: writer` — 对话编写、传说条目、游戏内文本
- `subagent_type: world-builder` — 世界规则、派系设计、历史、地理
- `subagent_type: art-director` — 角色视觉配置文件、环境视觉叙事、电影色调
- `subagent_type: level-designer` — 服务于叙事的关卡布局、节奏
- `subagent_type: localization-lead` — i18n 验证、字符串键合规性、翻译余量

**重要**：在每个代理的提示中始终提供完整上下文（叙事简报、传说依赖关系、角色配置文件）。在流程允许的情况下并行启动独立代理（例如，阶段 2 的代理可以同时运行）。

## 工作流程

### 阶段 1：叙事方向

委托给 **叙事总监**：

- 定义此内容的叙事目的：它服务于什么故事节拍？
- 识别涉及的角色、他们的动机，以及这如何适应整体弧线
- 设定情感基调和节奏目标
- 指定此内容引入的任何传说依赖关系或新传说
- **输出**：包含故事需求的叙事简报

### 阶段 2：世界观基础（并行）

**并行委托** — 在等待任何结果之前同时发出所有三个 Task 调用：

- **世界观构建师**：创建或更新与此内容相关的派系、地点和历史的传说条目。对照现有传说检查矛盾。为新条目设置正典级别。
- **作家**：使用声音配置文件起草角色对话。确保所有台词少于 120 个字符，对变量使用命名占位符，并准备好本地化。
- **艺术总监**：为此内容中出现的关键角色定义角色视觉设计方向（剪影、视觉原型、区别特征）。为每个关键空间指定环境视觉叙事元素（道具组成、灯光注释、空间安排）。为任何过场动画或脚本序列定义色调板和电影方向。

### 阶段 3：关卡叙事集成

委托给 **关卡设计师**：

- 审查叙事简报和传说基础
- 在关卡中设计环境叙事元素
- 放置叙事触发器、对话区域和发现点
- 确保节奏服务于游戏玩法和故事

### 阶段 4：审查和一致性

委托给 **叙事总监**：

- 对照角色声音配置文件审查所有对话
- 验证新条目和现有条目之间的传说一致性
- 确认叙事节奏与关卡设计一致
- 检查所有谜团是否有记录的"真实答案"

### 阶段 5：打磨（并行）

**并行委托**：

- **作家**：最终自我审查 — 验证没有台词超过对话边框约束，所有文本使用字符串键（不是原始字符串），占位符变量名称一致
- **本地化负责人**：验证 i18n 合规性 — 检查字符串键命名约定，标记任何无法在翻译中存活的硬编码格式的文本，验证字符限制余量以适应扩展的语言（德语/芬兰语通常 +30%），确认文本中没有需要区域特定变体的文化假设
- **世界观构建师**：最终确定所有新传说条目的正典级别

## 错误恢复协议

如果任何生成的代理（通过 Task）返回 BLOCKED、错误或无法完成：

1. **立即上报**：在继续依赖阶段之前，向用户报告 `[AgentName]: BLOCKED — [reason]`
2. **评估依赖关系**：检查被阻止代理的输出是否被后续阶段需要。如果是，在没有用户输入的情况下不要超过该依赖点。
3. **通过问题确认提供选项**，选择包括：
   - 跳过此代理并在最终报告中注明差距
   - 以更窄的范围重试
   - 停在此处并首先解决阻止程序
4. **始终生成部分报告** — 输出任何已完成的工作。永远不要因为一个代理被阻止而丢弃工作。

常见阻止程序：

- 输入文件缺失（未找到故事、GDD 缺失）→ 重定向到创建它的技能
- ADR 状态为 Proposed → 不要实现；首先运行 `/architecture-decision`
- 范围太大 → 通过 `/create-stories` 拆分为两个故事
- ADR 和故事之间的指令冲突 → 上报冲突，不要猜测

## 文件写入协议

所有文件写入（叙事文档、对话文件、传说条目）都委托给通过 Task 生成的子代理。每个子代理强制执行"我可以写入 [path] 吗？"协议。此编排器不直接写入文件。

## 输出

包含以下内容的总结报告：叙事简报状态、创建/更新的传说条目、编写的对话行数、关卡叙事集成点、一致性审查结果，以及任何未解决的矛盾。

**判定**：**COMPLETE** — 叙事内容已交付。

如果流程因依赖关系未解决而停止（例如，传说矛盾或用户未解决的缺失先决条件）：

**判定**：**BLOCKED** — [原因]

## 下一步

- 对叙事文档运行 `/design-review` 进行一致性验证。
- 对话最终确定后，运行 `/localize extract` 提取新字符串进行翻译。
- 运行 `/dev-story` 在引擎中实现对话触发器和叙事事件。
