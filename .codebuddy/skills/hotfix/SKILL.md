# 热修复技能

## 技能概述

紧急修复流程，快速响应生产问题。此技能提供结构化的热修复工作流程，包括严重性评估、热修复记录创建、分支管理、调查实施、审批收集、QA 门控和部署验证。

**重要**：此技能仅当用户显式请求 `/hotfix` 时才运行，不要基于上下文匹配自动调用。

## 使用方式

- 通过 Agent 触发：当用户说「热修复」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill hotfix [参数]`

---

## Phase 1：评估严重性

读取错误描述或 ID。确定严重性：

- **S1（严重）**：游戏无法游玩、数据丢失、安全漏洞 — 立即热修复
- **S2（重要）**：重要功能损坏，存在临时解决方案 — 24 小时内热修复
- 如果严重性是 S3 或更低，建议改用正常的错误修复工作流程并停止。

---

## Phase 2：创建热修复记录

起草热修复记录：

```markdown
## 热修复：[简短描述]
日期：[日期]
严重性：[S1/S2]
报告者：[谁发现的]
状态：进行中

### 问题
[清楚描述什么损坏以及玩家影响]

### 根本原因
[在调查期间填写]

### 修复
[在实施期间填写]

### 测试
[测试了什么以及如何测试]

### 审批
- [ ] 修复已由主程序员审查
- [ ] 回归测试已通过（QA 测试员）
- [ ] 发布已批准（制作人）

### 回滚计划
[如果修复导致新问题如何回滚]
```

询问："我可以将其写入 `production/hotfixes/hotfix-[date]-[short-name].md` 吗？"

如果可以，写入文件，必要时创建目录。

---

## Phase 3：创建热修复分支

如果 git 已初始化，创建热修复分支：

```
git checkout -b hotfix/[short-name] [release-tag-or-main]
```

---

## Phase 4：调查和实施

专注于解决问题的最小变更。不要重构、清理或在热修复旁边添加功能。

通过运行受影响系统的针对性测试来验证修复。检查相邻系统中的回归。

使用根本原因、修复详细信息和测试结果更新热修复记录。

---

## Phase 5：收集审批

使用 Task 工具并行请求签署：

- `subagent_type: lead-programmer` — 审查修复的正确性和副作用
- `subagent_type: qa-tester` — 在受影响系统上运行针对性回归测试
- `subagent_type: producer` — 批准部署时机和沟通计划

所有三个必须返回 APPROVE 才能继续。如果任何返回 CONCERNS 或 REJECT，不要部署 — 首先提出问题并解决它。

---

## Phase 5b：QA 重新进入门控

审批后，确定在部署热修复之前所需的 QA 范围。通过 Task 生成 `qa-lead`：

- 热修复描述和受影响系统
- Phase 5 的回归测试结果
- 接触更改文件的所有系统列表（使用 Grep 查找调用者）

询问 qa-lead：**冒烟检查是否足够，还是此修复需要针对性的 team-qa 通过？**

应用判定：
- **冒烟检查足够** — 对热修复构建运行 `/smoke-check`。如果通过，继续 Phase 6。
- **需要针对性 QA 通过** — 运行 `/team-qa [affected-system]`，范围仅限于更改的系统。如果 QA 返回 APPROVED 或 APPROVED WITH CONDITIONS，继续 Phase 6。
- **需要完整 QA** — 触及核心系统的 S1 修复可能需要完整的 `/team-qa sprint`。这会延迟部署但防止坏补丁。

不要跳过此门控。破坏其他东西的热修复比原始错误更糟。

---

## Phase 6：更新错误状态和部署

如果原始错误文件存在，更新它：

```markdown
## 修复记录
**修复于**：hotfix/[branch-name] — [commit hash or description]
**修复日期**：[date]
**状态**：已修复 — 待验证
```

在错误文件头部设置 `**状态**: 已修复 — 待验证`。

输出部署摘要：

```
## 热修复准备部署：[short-name]

**严重性**：[S1/S2]
**根本原因**：[一行]
**修复**：[一行]
**QA 门控**：[冒烟检查通过 / Team-QA 已批准]
**审批**：主程序员 ✓ / QA 测试员 ✓ / 制作人 ✓
**回滚计划**：[来自 Phase 2 记录]

合并到：发布分支 AND 开发分支
下一步：部署后使用 `/bug-report verify [BUG-ID]` 确认解决
```

### 规则
- 热修复必须是修复问题的**最小变更** — 无清理，无重构
- 每个热修复在部署前必须有记录的回滚计划
- 热修复分支合并到**发布分支和开发分支**
- 所有热修复需要在 48 小时内进行事后审查
- 如果修复复杂到需要超过 4 小时，升级到 `technical-director`

---

## Phase 7：部署后验证

部署后，运行 `/bug-report verify [BUG-ID]` 以确认修复解决了部署构建中的问题。

如果**已验证修复**：运行 `/bug-report close [BUG-ID]` 正式关闭它。
如果**仍然存在**：热修复失败 — 立即重新打开，评估回滚，并升级。

在 48 小时内使用 `/retrospective hotfix` 安排事后审查。
