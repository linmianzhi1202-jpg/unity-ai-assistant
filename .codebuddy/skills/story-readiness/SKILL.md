# 故事准备技能#

## 技能概述

验证故事文件包含开发者开始实施所需的一切——没有冲刺中期设计中断、没有猜测、没有模糊的验收标准。在分配故事之前运行它。

**此技能是只读的。** 它从不编辑故事文件。它报告发现并询问用户是否需要帮助填补差距。

**输出:** 每个故事的判定（READY / NEEDS WORK / BLOCKED）以及每个未准备好故事的具体差距清单。

## 使用方式

- 通过 Agent 触发：当用户说「故事准备」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：```/skill story-readiness [参数]```

---

## 阶段 0: 解析审查模式

在启动时解析审查模式一次（存储用于此次运行的所有门生成）：

1. 如果技能是用 `--review [full|lean|solo]` 调用的 → 使用该值
2. 否则读取 `production/review-mode.txt` → 使用该值
3. 否则 → 默认为 `lean`

有关完整的检查模式和模式定义，请参见 `.claude/docs/director-gates.md`。

---

## 1. 解析参数

**范围**: `$ARGUMENTS[0]` (空白 = 通过 AskUserQuestion 询问用户):

- **特定路径** (例如 `/story-readiness production/epics/combat/story-001-basic-attack.md`):
  验证单个故事文件。
- **`sprint`**: 从 `production/sprints/` 读取当前冲刺计划（最近的文件），提取它引用的每个故事路径，逐个验证。
- **`all`**: glob `production/epics/**/*.md`，排除 `EPIC.md` 索引文件，验证找到的每个故事文件。
- **无参数**: 询问用户要验证哪个范围。

如果没有给定参数，使用 `AskUserQuestion`:
- "您想验证什么？"
  - 选项: "特定故事文件", "当前冲刺中的所有故事", "production/epics/ 中的所有故事", "特定史诗的故事"

在继续之前报告范围："正在验证 [N] 个故事文件。"

---

## 2. 加载支持上下文

在检查任何故事之前，加载参考文档一次（不是每个故事）：

- `design/gdd/systems-index.md` — 了解哪些系统有批准的 GDD
- `docs/architecture/control-manifest.md` — 了解存在哪些清单规则（如果文件不存在，注意它一次缺失；不要每个故事重新标记）
  还要从标头块提取 `Manifest Version:` 日期（如果文件存在）。
- `docs/architecture/tr-registry.yaml` — 按 `id` 索引所有条目。用于验证故事中的 TR-ID。如果文件不存在，注意它一次；TR-ID 检查将对所有故事自动通过（注册表早于故事，所以缺失注册表意味着故事来自 TR 跟踪引入之前）。
- 所有 ADR 状态字段 — 对于正在检查的故事引用的每个唯一 ADR，读取 ADR 文件并注意其 `Status:` 字段。缓存这些，这样您就不会为每个故事重新读取相同的 ADR。
- 当前冲刺文件（如果范围是 `sprint`）— 识别 Must Have / Should Have 优先级以进行升级决策。

## 3. 故事准备清单

对于每个故事文件，评估下面的每个项目。故事只有所有项目都通过或明确标记为 N/A 并陈述原因时，才是 READY。

### 设计完整性

- [ ] **引用了 GDD 需求**: 故事包含 `design/gdd/` 路径并引用或链接该 GDD 中的特定需求、验收标准或规则——不仅仅是 GDD 文件名。仅链接到文档而没有追踪到特定需求则未通过。
- [ ] **需求是自包含的**: 故事中的验收标准无需打开 GDD 就可理解。开发者不应该需要读取单独文档来理解 DONE 的含义。
- [ ] **验收标准是可测试的**: 每个标准都是一个具体的、可观察的条件——不是"实施 X"或"系统正常工作"。错误示例："实施跳跃机制。" 良好示例："当按住跳跃时，跳跃在 0.3 秒内达到 5 个单位的最大高度。"
- [ ] **没有验收标准需要判断调用**: 像"感觉响应"或"看起来好"这样的标准在没有定义基准的情况下是不可测试的。这些必须替换为具体的可观察条件或试玩协议。

### 架构完整性

- [ ] **引用了 ADR 或陈述了 N/A**: 故事至少引用一个 ADR，或明确陈述"不适用 ADR"并附带简要原因。没有 ADR 引用且没有明确 N/A 注释的故事未通过此检查。
- [ ] **ADR 是已接受的（不是提议的）**: 对于每个引用的 ADR，使用在部分 2 中加载的缓存 ADR 状态检查其 `Status:` 字段。
  - 如果 `Status: Accepted` → 通过。
  - 如果 `Status: Proposed` → **阻塞**: ADR 在接受之前可能会更改，并且故事的实施指导可能是错误的。
    修复：`阻塞：ADR-NNN 是提议的——在实施之前等待接受。`
  - 如果 ADR 文件不存在 → **阻塞**: 引用的 ADR 缺失。
  - 如果故事有明确的"不适用 ADR"N/A 注释，则自动通过。
- [ ] **TR-ID 是有效且活跃的**: 如果故事包含 `TR-[system]-NNN` 引用，在部分 2 中加载的 TR 注册表中查找它。
  - 如果 ID 存在且 `status: active` → 通过。
  - 如果 ID 存在且 `status: deprecated` 或 `status: superseded-by: ...` → 需要工作：需求已被移除或替换。
    修复：更新故事以引用当前需求 ID，或如果不再适用则移除。
  - 如果 ID 在注册表中不存在 → 需要工作：ID 未注册（故事可能早于注册表，或注册表需要 `/architecture-review` 运行）。
  - 如果故事没有 TR-ID 引用或注册表不存在，则自动通过。
- [ ] **清单版本是当前版本**: 如果故事的标头中有 `Manifest Version:` 日期且 `docs/architecture/control-manifest.md` 存在：
  - 如果故事版本与当前清单 `Manifest Version:` 匹配 → 通过。
  - 如果故事版本早于当前清单 → 需要工作：可能适用新规则。修复：审查更改的清单规则，如果任何禁止/必需条目已更改，则更新故事，然后将故事的 `Manifest Version:` 更新为当前版本。
  - 如果故事没有 `Manifest Version:` 字段或清单不存在，则自动通过。
- [ ] **存在引擎注释**: 对于此故事可能触及的任何后置截止引擎 API，包含实施注释或验证需求。如果故事显然不触及引擎 API（例如，它是纯数据/配置更改），"N/A——不涉及引擎 API"是可接受的。
- [ ] **注意到控制清单规则**: 引用了控制清单中的相关层规则，或陈述了"N/A——清单尚未创建"。如果 `docs/architecture/control-manifest.md` 尚不存在，此项目自动通过（不要惩罚在清单创建之前编写的故事）。

### 范围清晰度

- [ ] **存在预估**: 故事包含大小预估（小时、点数或 T 恤尺寸）。没有预估的故事无法计划。
- [ ] **陈述了范围内/范围外边界**: 故事陈述了它不包含的内容，无论是在明确的范围外部分中，还是在使边界明确的语言中。没有这个，实施期间的范围蠕变很可能发生。
- [ ] **列出了故事依赖项**: 如果此故事首先依赖于其他故事 DONE，则列出那些故事 ID。如果没有依赖项，"无"被明确陈述（不仅仅是省略）。

### 未解决问题

- [ ] **没有未解决的设计问题**: 故事在任何验收标准、实施注释或规则陈述中不包含标记为"未解决"、"待定"、"待办"、"?"或等效标记的文本。
- [ ] **依赖故事不在 DRAFT 中**: 对于列为依赖项的每个故事，检查文件是否存在且不具有 DRAFT 状态。依赖于 DRAFT 或缺失故事的故事是阻塞的，不仅仅是需要工作。

### 资产引用检查

- [ ] **引用的资产存在**: 扫描故事文本中的资产路径模式（包含 `assets/` 的路径，或文件扩展名 `.png`、`.jpg`、`.svg`、`.wav`、`.ogg`、`.mp3`、`.glb`、`.gltf`、`.tres`、`.res`）。
  - 对于每个找到的资产路径：使用 Glob 检查文件是否存在。
  - 如果任何引用的资产不存在：**需要工作**——注意缺失的路径。
    （故事引用了尚未创建的资产。要么移除引用，创建占位符，要么将其标记为对资产创建故事的明确依赖项。）
  - 如果所有引用的资产都存在：注意"引用的资产已验证：[计数] 找到。"
  - 如果故事中没有引用资产路径：注意"故事中未找到资产引用——跳过资产检查。"此项目自动通过。
  - 这是存在性检查。不要验证文件格式或内容。

### 完成定义

- [ ] **至少 3 个可测试的验收标准**: 少于 3 个表明故事要么微不足道（应该是故事？），要么规范不足。
- [ ] **适用时注意到性能预算**: 如果此故事触及游戏循环、渲染或物理的任何部分，则存在性能预算或"预期无性能影响——[原因]"注释。
- [ ] **声明了故事类型**: 故事的标头中包含 `Type:` 字段，标识测试类别（Logic / Integration / Visual/Feel / UI / Config/Data）。没有这个，测试证据需求无法在故事关闭时强制执行。
  修复：将 `Type: [Logic|Integration|Visual/Feel|UI|Config/Data]` 添加到故事标头。
- [ ] **测试证据需求是明确的**: 如果设置了故事类型，故事包含 `## Test Evidence` 部分，陈述证据将存储在哪里（Logic/Integration 的测试文件路径，或 Visual/Feel/UI 的证据文档路径）。
  修复：为故事的类型添加具有预期证据位置的 `## Test Evidence`。

## 4. 判定分配

为每个故事分配三个判定之一：

**READY** — 所有清单项目通过或有明确的 N/A 理由。
故事可以立即分配。

**NEEDS WORK** — 一个或多个清单项目失败，但所有依赖故事都存在且不在 DRAFT 中。故事可以在分配之前修复。

**BLOCKED** — 一个或多个依赖故事缺失或处于 DRAFT 状态，或者一个关键设计问题（在标准或规则中标记为未解决）没有负责人。在解决阻塞项之前，无法分配故事。注意：阻塞的故事也可能有需要工作项目——两者都列出。

## 6. 协作协议

此技能是只读的。它从不提议编辑或要求写入文件。

报告发现后，提供：

"您想帮助填补其中任何故事的差距吗？我可以为您批准起草缺失的部分。"

如果用户对一个特定故事说"是"，仅在对话中起草缺失的部分。不要使用写入或编辑工具——用户（或 `/create-stories`）处理写入。

**重定向规则：**

- 如果故事文件完全不存在："此故事文件完全缺失。运行 `/create-epics [layer]` 然后 `/create-stories [epic-slug]` 从 GDD 和 ADR 生成故事。"
- 如果故事没有 GDD 引用且工作看起来很小："此故事没有 GDD 引用。如果更改很小（约 4 小时以内），运行 `/quick-design [description]` 创建快速设计规范，然后在故事中引用该规范。"
- 如果故事的范围超出了其原始大小调整："此故事的范围似乎已扩展。考虑在实施开始之前拆分它或升级到生产者。"

## 7. 下一个故事交接

完成单个故事准备检查（不是 `all` 或 `sprint` 范围）后：

1. 从 `production/sprints/` 读取当前冲刺文件（最近一次）。
2. 查找符合以下条件的故事：
   - 状态：READY 或 NOT STARTED
   - 不是刚刚检查的故事
   - 不被不完整的依赖项阻塞
   - 在 Must Have 或 Should Have 层中

如果找到任何，最多展示 3 个：

```
### 此冲刺中的其他准备故事

1. [故事名称] — [1 行描述] — 预估：[X 小时]
2. [故事名称] — [1 行描述] — 预估：[X 小时]

在开始前运行 `/story-readiness [路径]` 进行验证。
```

如果冲刺文件不存在或未找到其他准备故事，则静默跳过此部分。

## 阶段 8: 主管门控 — 故事准备审查

在生成 QL-STORY-READY 之前应用审查模式解析：

- `solo` → 跳过。注意："QL-STORY-READY 已跳过——单人模式。"继续到关闭。
- `lean` → 跳过。注意："QL-STORY-READY 已跳过——精简模式。"继续到关闭。
- `full` → 正常生成。

通过 Task 使用门控 **QL-STORY-READY**（`.claude/docs/director-gates.md`）生成 `qa-lead`。

传递以下上下文：

- 故事标题
- 验收标准列表（故事的验收标准部分中的所有项目）
- 依赖项状态（列出的所有依赖项及其当前状态：存在 / DRAFT / 缺失）
- 阶段 4 中的总体判定（READY / NEEDS WORK / BLOCKED）

按 `director-gates.md` 中的标准规则处理判定：

- **充分** → 故事已清除。继续到关闭。
- **有差距 [列表]** → 通过 `AskUserQuestion` 向用户提出具体差距：
  选项：`用建议差距更新故事` / `接受并无论如何继续` / `进一步讨论`
- **不充分** → 提出具体差距；询问用户是要更新故事还是无论如何继续。

## 推荐后续步骤

- 故事是 READY 后，运行 `/dev-story [story-path]` 开始实施
- 运行 `/story-readiness sprint` 一次检查当前冲刺中的所有故事
- 如果故事文件完全缺失，运行 `/create-stories [epic-slug]`
