# Bug 报告技能

## 技能概述

创建结构化错误报告，包含复现步骤和预期行为，生成 Bug 跟踪 ID。

## 使用方式

- 通过 Agent 触发：当用户说「Bug 报告」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill bug-report [参数]`

---

## 功能说明

### 阶段 1：解析参数

从参数确定模式：

- 无关键词 → **描述模式**：从提供的描述生成结构化 Bug 报告
- `analyze [path]` → **分析模式**：读取目标文件并识别潜在 Bug
- `verify [BUG-ID]` → **验证模式**：确认报告修复是否实际解决了 Bug
- `close [BUG-ID]` → **关闭模式**：将已验证的 Bug 标记为已关闭

如果未提供参数，在继续之前询问用户 Bug 描述。

---

## 工作流程

### 阶段 2A：描述模式

1. **解析描述** 以获取关键信息：什么损坏、何时、如何复现、预期行为。
2. **搜索代码库** 使用 Grep/Glob 以添加上下文（受影响的系统、可能文件）。
3. **起草 Bug 报告**：
   - 使用结构化格式（见下文）。
   - 包含所有必需部分。
   - 使用清晰、可操作的语言。
4. **获得批准** 然后将报告写入 `docs/bugs/BUG-[NNNN].md`。

### 阶段 2B：分析模式

1. **读取目标文件**（s）。
2. **识别潜在问题**：
   - 空引用风险
   - 边界条件缺失
   - 资源泄漏
   - 逻辑错误
   - 性能问题
3. **为每个问题起草 Bug 报告**：
   - 包含文件引用和行号。
   - 解释为什么是问题。
   - 建议潜在修复。
4. **获得批准** 然后写入报告。

### 阶段 2C：验证模式

1. **读取 Bug 报告**（`docs/bugs/BUG-[ID].md`）。
2. **读取建议的修复文件**。
3. **验证修复**：
   - 问题实际上已修复？
   - 没有引入新问题？
   - 所有边缘情况已处理？
4. **更新 Bug 报告**：
   - 将状态更改为"已验证"。
   - 添加验证注释。
   - 记录修复提交哈希。

### 阶段 2D：关闭模式

1. **读取 Bug 报告**（`docs/bugs/BUG-[ID].md`）。
2. **验证状态** 是"已验证"。
3. **关闭 Bug**：
   - 将状态更改为"已关闭"。
   - 添加解决记录。
   - 记录关闭日期和验证者。

## 输出格式

### Bug 报告格式

```markdown
# Bug 报告

**标题**：[简洁、描述性标题]
**ID**：BUG-[NNNN]
**严重性**：[S1-Critical / S2-Major / S3-Minor / S4-Trivial]
**优先级**：[P1-Immediate / P2-Next Sprint / P3-Backlog / P4-Wishlist]
**状态**：Open / In Progress / Verified / Closed
**报告日期**：[YYYY-MM-DD]
**报告者**：[姓名]
**验证者**：[姓名，如果已验证]

## 分类

- **类别**：[Gameplay / UI / Audio / Visual / Performance / Crash / Network]
- **系统**：[受影响的游戏系统]
- **频率**：[Always / Often (>50%) / Sometimes (10-50%) / Rare (<10%)]
- **回归**：[Yes/No/Unknown -- 这之前工作过吗？]

## 环境

- **构建**：[版本或提交哈希]
- **平台**：[OS、硬件如果相关]
- **场景/关卡**：[在游戏中哪里]
- **设置**：[图形质量、音频设置等]

## 复现步骤

1. [步骤 1 -- 具体且可操作]
2. [步骤 2]
3. [步骤 3]
4. [预期结果]
5. [实际结果]

## 预期行为

[应该发生什么]

## 实际行为

[实际发生什么]

## 根本原因（如果已知）

[为什么发生 -- 添加调查后]

## 建议修复

[潜在解决方案 -- 添加验证后]

## 附件

- [截图/视频链接]
- [日志文件]
- [崩溃转储]

## 注释

- [日期]：[注释内容]
- [日期]：[注释内容]
```

### Bug 跟踪 ID 格式

```
BUG-[NNNN]-[SLUG]
```

示例：`BUG-0042-player-collision-miss`

## 协作协议

**你是协作实现者，不是自主代码生成器。** 用户批准所有决策。

### 问题优先工作流

在提出任何建议之前：

1. **提出澄清问题**：
   - Bug 是间歇性的还是一致可复现的？
   - 什么触发 Bug？
   - 最近有任何更改可能引起它吗？
   - 哪些系统可能相关？
2. **提出 2-4 个选项及推理**：
   - 解释每个选项的优缺点
   - 参考调试和根本原因分析最佳实践
   - 将每个选项与用户陈述的目标对齐
   - 做出推荐，但明确将最终决策推迟给用户
3. **基于用户选择起草**：
   - 迭代地创建 Bug 报告（显示一个部分，获取反馈，优化）
   - 关于歧义进行询问而不是假设
   - 标记潜在问题或边缘情况以征求用户输入
4. **在写入文件之前获得批准**：
   - 显示完整草稿或摘要
   - 明确询问："我可以将其写入 [文件路径] 吗？"
   - 在使用 Write/Edit 工具之前等待"是"
   - 如果用户说"否"或"更改 X"，则迭代并返回步骤 3

### 协作心态

- 你是提供选项和推理的专家顾问
- 用户是做出最终决策的创意总监
- 当不确定时，询问而不是假设
- 解释 WHY 你推荐某事（理论、示例、支柱对齐）
- 基于反馈迭代而没有防御性
- 当用户的修改改进你的建议时庆祝

## 推荐后续步骤

- 如果 Bug 严重性为 S1 或 S2："运行 `/create-stories [epic-slug]` 以为此 Bug 创建故事。"
- 如果根本原因涉及多个系统："首先运行 `/consistency-check` 以验证跨系统一致性。"
- 如果修复需要架构变更："首先运行 `/architecture-decision [标题]` 以记录决策。"
- 如果 Bug 影响发布："运行 `/day-one-patch` 以评估是否应包含在首日补丁中。"
