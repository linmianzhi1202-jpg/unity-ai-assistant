# 审查所有 GDD 技能#

## 技能概述#

批量验证所有 GDD，检测不一致。此技能读取每个系统 GDD 并同时执行两个互补的审查，这些审查无法在隔离的每个 GDD 中完成：

1. **跨 GDD 一致性** — 矛盾、过时引用和所有权冲突
2. **游戏设计整体主义** — 仅当您看到所有系统时才出现的问题：主导策略、破碎的经济、认知超载、支柱漂移、竞争进度循环#

**这与 `/design-review` 不同**，后者审查单个 GDD 的内部完整性。此技能审查所有 GDD 之间的 *关系*。

**何时运行：**
- 所有 MVP 层 GDD 单独批准后
- 生产中后期重大修订任何 GDD 后
- 在 `/create-architecture` 开始前（建立在不一致 GDD 上的架构会继承这些不一致）

**参数模式：**

**焦点：** `$ARGUMENTS[0]`（空白 = `full`）：
- **无参数 / `full`**：一致性和设计理论两次传递
- **`consistency`**：仅跨 GDD 一致性检查（更快）
- **`design-theory`**：仅游戏设计整体主义检查
- **`since-last-review`**：仅自上次审查报告（基于 git）以来修改的 GDD#

## 使用方式#

- **通过 Agent 触发**：当用户说「审查所有 GDD」或相关需求时，Agent 应自动加载此 Skill#
- **手动触发**：`/skill review-all-gdds [参数]```#

## Phase 1：加载所有内容#

### Phase 1a — L0：摘要扫描（快速、低 tokens）#

在完整读取任何文档之前，使用 Grep 从所有 GDD 文件中提取 `## 摘要` 部分：#

```
Grep pattern="## 摘要" glob="design/gdd/*.md" output_mode="content" -A 5
```

向用户显示清单：#
```
找到 [N] 个 GDD。摘要：
  • combat.md — [摘要文本]
  • inventory.md — [摘要文本]
  ...
```

对于 `since-last-review` 模式：运行 `git log --name-only` 以识别自上次审查报告编写以来修改的 GDD。向用户显示基于此清单的范围 GDD（基于摘要） before 进行任何完整读取。仅继续这些 GDD 加上其"关键 deps"中列出的任何 GDD。#

### Phase 1b — 注册表预加载（快速基线）#

在完整读取任何 GDD 之前，检查实体注册表：#

```
读取 path="design/registry/entities.yaml"
```

如果注册表存在且有条目，将其用作 **预构建冲突基线**：已知实体、物品、公式和常量及其权威值和源 GDD。在 Phase 2 中，首先 Grep GDD 以查找注册的名称 — 这比在知道要查找什么之前完整读取所有 GDD 更快。#

如果注册表为空或不存在：无注册表继续。在报告中注意："实体注册表为空 — 一致性检查仅依赖完整 GDD 读取。" 在审查后运行 `/consistency-check` 以填充注册表。#

### Phase 1c — L1/L2：完整文档加载#

完整读取范围内的文档：#

1. `design/gdd/game-concept.md` — 游戏愿景、核心循环、MVP 定义#
2. `design/gdd/game-pillars.md`（如果存在）— 设计支柱和反支柱#
3. `design/gdd/systems-index.md` — 权威系统列表、层、依赖关系、状态#
4. `design/gdd/` 中的每个 **范围内系统 GDD** — 完整读取（跳过 game-concept.md 和 systems-index.md — 这些在上面读取）#

报告："已加载 [N] 个系统 GDD，涵盖 [M] 个系统。支柱：[列表]。反支柱：[列表]。"#

如果少于 2 个系统 GDD 存在，停止：#
> "跨 GDD 审查需要至少 2 个系统 GDD。首先编写更多 GDD，然后重新运行 `/review-all-gdds`。"#

## 并行执行#

Phase 2（一致性）和 Phase 3（设计理论）是独立的 — 它们读取相同的 GDD 输入但生成单独的报告。同时作为并行 Task 代理生成两者，而不是等待 Phase 2 完成后再启动 Phase 3。在继续之前收集两个结果。#

---

## Phase 2：跨 GDD 一致性#

遍历每个对和 GDD 组以查找矛盾和差距。#

### 2a：依赖关系双向性#

对于每个 GDD 的 `## 依赖关系` 部分，检查每个列出的依赖关系是否是相互的：#

- 如果 GDD-A 列出"依赖于 GDD-B"，检查 GDD-B 是否将 GDD-A 列为依赖项#
- 如果 GDD-A 列出"被 GDD-C 依赖"，检查 GDD-C 是否将 GDD-A 列为依赖关系#
- 将任何单向依赖关系标记为一致性问题#



### 2b：规则矛盾#

对于每个在任何 GDD 中定义的游戏规则、机制或约束，检查任何其他 GDD 是否对相同情况定义了矛盾的规则：#

**要扫描的类别：**#
- **下限/上限规则**：任何 GDD 是否为输出定义最小值？任何其他 GDD 是否说不同的系统可以绕过该下限？这些矛盾。#
- **资源所有权**：如果两个 GDD 都定义共享资源如何累积或消耗，它们一致吗？#
- **状态转换**：如果 GDD-A 描述角色死亡时发生什么，GDD-B 对同一事件的描述是否一致？#
- **时机**：如果 GDD-A 说"X 在同一帧发生"，GDD-B 是否假设它是异步的？#
- **堆叠规则**：如果 GDD-A 说状态效果堆叠，GDD-B 是否假设它们不堆叠？#



### 2c：过时引用#

对于每个跨文档引用（GDD-A 提及机制、值或来自 GDD-B 的系统名称），验证被引用的元素在 GDD-B 中是否以相同名称和行为存在：#

- 如果 GDD-A 说"来自战斗系统的连击倍数馈入分数"，检查战斗 GDD 是否实际定义了输出到分数的连击倍数#
- 如果 GDD-A 引用"在 [system].md 中定义的比例曲线"，检查 [system].md 是否实际具有该曲线，而不是不同的比例模型#
- 如果 GDD-A 在 GDD-B 之前编写并假设了 GDD-B 后来不同地设计的机制，将 GDD-A 标记为包含过时引用#



### 2d：数据和调优旋钮所有权冲突#

两个 GDD 不应都声称拥有相同的数据或调优旋钮。跨所有 GDD 扫描所有 `## 调优旋钮` 部分并标记重复项：#



### 2e：公式兼容性#

对于输出一个馈送另一个的输入的连接公式的 GDD，检查上游公式的输出范围是否在下流公式的预期输入范围内：#

- 如果 system-a.md 输出值介于 [min]–[max]，且 system-b.md 设计为接收值介于 [min2]–[max2]，不匹配是故意的吗？#
- 如果经济 GDD 预期资源获取在范围 X 内，且进度 GDD 在范围 Y 生成它，经济将变得微不足道或不可访问 — 这是故意的吗？#

将不兼容性标记为 CONCERNS（设计判断需要，不一定错误）：#



### 2f：验收标准交叉检查#

跨所有 GDD 扫描 `## 验收标准` 部分以查找矛盾：#

- GDD-A 标准："玩家不能从单次击中死亡"#
- GDD-B 标准："Boss 攻击造成 150% 玩家最大生命值"#

这些验收标准不能同时通过。#

## Phase 3：游戏设计整体主义#

通过游戏设计理论和玩家心理学的视角审查所有 GDD 在一起。这些是单个 GDD 审查无法捕获的问题，因为它们需要一次看到所有系统。#

### 3a：进度循环竞争#

游戏应该有一个主导进度循环，玩家感觉是游戏的"重点"，带有馈入它的支持循环。当多个系统作为*主要*进度驱动器等竞争时，玩家不知道游戏是关于什么的。#

扫描所有 GDD 以查找：#
- 奖励玩家主要资源（XP、等级、声望、解锁）的系统#
- 将自己定义为"核心"或"主要"循环#
- 与其他系统相比具有可比深度和时间投资#

示例：#
```


⚠️  竞争进度循环#
combat.md：奖励 XP、解锁能力，被描述为"核心循环"#
crafting.md：奖励 XP、解锁配方，被描述为"主要活动"#
exploration.md：奖励 XP、解锁地图区域，被描述为"主要驱动因素"#
→ 三个系统都声称是主要进度循环并奖励相同主要货币。玩家将优化一个并忽略其他。#
考虑：一个主要循环，其他作为支持系统。#
```#

### 3b：玩家注意力预算#

计算典型会话期间需要多少系统同时吸引玩家注意力。每个主动管理的系统都要付出注意力代价：#

- **主动** = 玩家必须在游戏期间定期做出关于此系统的决策#
- **被动** = 系统自动运行，玩家看到结果但不管理它#


超过 3-4 个同时主动系统会为大多数玩家创建认知超载。呈现计数并在超过 4 个并发主动系统时标记：#



### 3c：主导策略检测#

主导策略使其他策略无关紧要 — 玩家发现它，专门使用它，并发现游戏的其余部分无聊。查找：#

- **资源垄断**：一个策略生成资源显著快于所有其他策略#
- **无风险强大**：既是高奖励又是低风险的策略（如果存在高风险策略，它们需要有比例更高的奖励）#
- **无权衡**：在所有维度上都优于所有其他选择的选项#
- **明显最佳路径**：如果任何进度选择是"明显正确的"，其他不是真正选择#



### 3d：经济循环分析#

识别跨所有 GDD 的所有资源（金币、XP、制作材料、耐力、生命值、法力等）。对于每个资源，映射其 **来源**（玩家如何获得它）和 **沉淀池**（玩家如何花费它）。#

标记危险经济条件：#

| 条件 | 标志 | 风险 |
|-----------|------|------|#
| **无限来源，无沉淀池** | 资源无限累积 | 后期游戏变得微不足道 |
| **沉淀池，无来源** | 资源耗尽至零 | 系统变得不可用 |
| **来源 >> 沉淀池** | 剩余累积 | 资源变得无意义 |
| **沉淀池 >> 来源** | 恒定稀缺性 | 挫败感和门控 |
| **正反馈循环** | 更多资源 → 更容易获得更多 |  runaway 领导者，snowball |
| **无追赶机制** | 落后加速赤字 | 无法恢复状态 |#



### 3e：难度曲线一致性#

当多个系统随玩家进度扩展时，它们必须以兼容的方向和以兼容的速率扩展。不匹配的缩放曲线会创建无意的难度峰值或微不足道化。#

对于每个随进度缩放的系统，提取：#
- 什么缩放（敌人生命值、玩家伤害、资源成本、区域大小）#
- 它如何缩放（线性、指数、步进）#
- 何时缩放（等级、时间、区域）#

比较所有缩放曲线。标记不匹配：#



### 3f：支柱对齐#

每个系统应清楚地为至少一个设计支柱服务。为设计支柱服务"范围蠕变"的系统 — 它在游戏中但不在游戏尝试成为什么的服务中。#

对于每个 GDD 系统，根据其 `## 玩家幻想` 部分对照设计支柱检查。将任何系统标记为其陈述的幻想不匹配任何支柱：#



还要检查反支柱 — 将做什么系统标记为反支柱显式说游戏不会做：#



### 3g：玩家幻想连贯性#

跨所有系统的玩家幻想应该兼容 — 它们应该强化玩家在此游戏中 *是*的一致身份。冲突的玩家幻想会创建身份混淆。#

## Phase 4：跨系统场景演练#

从玩家视角演练游戏以查找仅在多个系统边界出现的问题 — 静态分析单个 GDD 无法呈现的问题。#

### 4a：识别关键多系统时刻#

扫描所有 GDD 并识别 3–5 个最重要的玩家面向时刻，其中多个系统同时激活。具体查找：#

- **战斗 + 经济重叠**：掉落资源的杀敌、战斗期间花费资源、死亡/重生与经济体状态交互#
- **进度 + 难度重叠**：在战斗期间触发等级提升、能力解锁改变战斗生存能力、难度随进度里程碑缩放#
- **叙事 + 游戏玩法重叠**：对话选择锁定/解锁机制、故事节拍中断资源循环、任务完成触发系统状态更改#
- **3+ 系统链**：任何触发系统 A 的玩家动作，馈送到系统 B，触发系统 C（这些是最高风险交互路径）#

在继续之前，用单行描述列出每个识别的场景。#

### 4b：演练每个场景#

对于每个场景，显式单步执行序列：#

1. **触发器** — 什么玩家动作或游戏事件启动此？#
2. **激活顺序** — 哪些系统激活，以什么序列？#
3. **数据流** — 每个系统输出什么，该输出是否是链中下一个系统的有效输入？#
4. **玩家体验** — 玩家在每个步骤看到、听到或感觉到什么？#
5. **失败模式** — 是否存在以下任何情况？#
   - **竞争条件**：两个系统试图同时修改相同状态#
   - **反馈循环**：系统 A 放大系统 B，系统 B 再放大系统 A 且无上限或阻尼器#
   - **破碎状态转换**：系统假设在可能已更改的状态后（例如，"玩家活着"假设在可能导致死亡的战斗步骤之后）#
   - **矛盾消息**：两个系统对相同事件做出反应（例如，"成功"声音 + "失败"UI）#
   - **奖励冲突**：两个系统都对相同触发器做出反应，奖励一起超过预期值（双重浸 dip）#
   - **未定义行为**：GDD 未指定此组合状态发生什么（两个系统的规则都未覆盖它）#



### 4c：标记场景问题#

对于演练期间发现的每个问题，分类严重性：#

- **BLOCKER**：未定义行为、破碎状态转换或矛盾玩家消息 — 此场景中的体验破碎或不连贯#
- **WARNING**：放大峰值、无上限的反馈循环、奖励冲突 — 体验工作但产生无意的后果#
- **INFO**：轻微排序歧义或消息重叠 — 值得注意但不太可能导致玩家可见问题#

## Phase 6：写入报告和标记 GDD#

使用 `AskUserQuestion` 获取写入权限：#
- 提示："我可以将此审查写入 `design/gdd/gdd-cross-review-[date].md` 吗？"#
- 选项：`[A] 是 — 写入报告` / `[B] 否 — 跳过`#

仅在批准后写入。#

如果任何 GDD 被标记为修订，使用第二个 `AskUserQuestion`：#
- 提示："我应该更新系统索引以将这些 GDD 标记为需要修订吗？（[标记的 GDD 列表]）"#
- 选项：`[A] 是 — 更新系统索引` / `[B] 否 — 保持原样`#
- 如果是：将每个标记的 GDD 的 Status 字段在 systems-index.md 中更新为"Needs Revision"。#
  （不要将括号添加到状态值 — 其他技能匹配"Needs Revision"作为精确字符串，括号会破坏该匹配。）#

### 会话状态更新#

## Phase 7：切换#

所有文件写入完成后，使用 `AskUserQuestion` 获取结束小部件。#

在构建选项之前，检查项目状态：#
- 是否有任何警告级别的项目是简单编辑（标记为"30 秒编辑"、"简要添加"或类似）？→ 提供内联快速修复选项#
- systems-index.md 中是否有任何 GDD 处于"标记为修订"状态？→ 为每个提供 `/design-review` 选项#
- 读取 systems-index.md 以获取 `Status: Not Started` 的下一个系统→ 提供 `/design-system` 选项#
- 判定是否为 PASS 或 CONCERNS？→ 提供 `/gate-check` 或 `/create-architecture` 选项#

动态构建选项列表 — 仅包含适用的选项：#

**选项池：**#
- `[_] 应用快速修复：[W-XX 描述] 在 [gdd-name].md 中 — [effort estimate]`（每个简单编辑警告一个选项；仅适用于 WARNING 级别，不是 Blocking）#
- `[_] 运行 `/design-review [标记的-gdd-路径]` — 解决标记的警告`（每个标记的 GDD 一个，如果有的话）#
- `[_] 运行 `/design-system [下一个系统]` — 在设计顺序中下一个`（始终包含，命名实际系统）#
- `[_] 运行 `/create-architecture` — 开始架构（判定为 PASS/CONCERNS）`（如果判定不是 FAIL，则包含）#
- `[_] 运行 `/gate-check` — 验证系统设计阶段门`（如果判定为 PASS，则包含）#
- `[_] 在此停止`#

将字母 A、B、C… 仅分配给包含的选项。将最推进管道的选项标记为 `(推荐)`。#

永远不要以纯文本结束技能。始终以此小部件关闭。#

## 错误恢复协议#

如果任何生成的代理（通过 Task）返回 BLOCKED、错误或无法完成：#

1. **立即上报**：在继续依赖阶段之前，向用户报告 "[AgentName]: BLOCKED — [reason]"#
2. **评估依赖关系**：检查被阻止代理的输出是否被后续阶段需要。如果是，在没有用户输入的情况下不要超过该依赖点。#
3. **通过 AskUserQuestion 提供选项**，选择包括：#
   - 跳过此代理并在最终报告中注明差距#
   - 以更窄的范围重试#
   - 停在此处并首先解决阻止程序#
4. **始终生成部分报告** — 输出任何已完成的工作。永远不要因为一个代理被阻止而丢弃工作。#

常见阻止程序：#
- 输入文件缺失（未找到 GDD、注册表不存在）→ 重定向到创建它的技能#
- GDD 状态不是 Approved → 不要继续；首先运行 `/design-review`#
- 范围太大 → 通过 `/create-stories` 拆分为两个故事#
- 设计理论检查返回需要设计判断的 CONCERN → 向用户呈现选项，不要猜测#

## 协作协议#

1. **静默读取** — 在呈现任何内容之前加载所有 GDD#
2. **显示所有内容** — 在请求任何操作之前呈现完整的一致性和设计理论分析#
3. **区分阻止和咨询** — 不是每个问题都需要阻止架构；清楚哪些需要#
4. **不要做设计决策** — 标记矛盾和选项，但永远不要单方面决定哪个 GDD 是"正确的"#
5. **在写入前询问** — 在写入报告或更新系统索引之前确认#
6. **要具体** — 每个问题必须引用确切的 GDD、部分和文本；无模糊警告#
