# UX 设计技能

## 技能概述

设计用户体验，创建界面流程和线框图。此技能通过协作式、章节逐节的方法生成 UX 规范、HUD 设计和交互模式库，在每个决策点都涉及用户。

**适用场景**：
- 为新屏幕或流程创建 UX 规范
- 设计游戏 HUD（抬头显示）
- 构建交互模式库以供整个团队重用
- 在实施前定义完整的用户体验规范

## 使用方式

- 通过 Agent 触发：当用户说「UX 设计」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill ux-design [参数]`

**参数模式**：
- `hud` → HUD 设计模式，输出到 `design/ux/hud.md`
- `patterns` → 交互模式库模式，输出到 `design/ux/interaction-patterns.md`
- `[屏幕名称]`（例如 `main-menu`、`inventory`）→ 该屏幕或流程的 UX 规范，输出到 `design/ux/[屏幕名称].md`
- 无参数 → 使用 `AskUserQuestion` 询问用户意图

## 阶段 0: 解析参数和确定模式

**参数**: `$ARGUMENTS[0]` (空白 = 询问用户）

从参数确定模式：

| 参数 | 模式 | 输出文件 |
|----------|------|-------------|
| `hud` | HUD 设计 | `design/ux/hud.md` |
| `patterns` | 交互模式库 | `design/ux/interaction-patterns.md` |
| 其他值（例如 `main-menu`、`inventory`） | 屏幕或流程的 UX 规范 | `design/ux/[参数].md` |
| 无参数 | 询问用户 | （见下方） |

**如果未提供参数**，不要失败 — 改为询问。使用 `AskUserQuestion`：
- "今天我们要设计什么？"
  - 选项："特定屏幕或流程（我来命名）"、"游戏 HUD"、"交互模式库"、"我不确定 — 帮我弄清楚"

如果用户输入屏幕名称，将其规范化为 kebab-case 文件名（例如，"Main Menu" 变为 `main-menu`）。

## 阶段 1: 加载上下文（读取阶段）

在询问用户任何问题之前，读取所有相关上下文。**此技能的价值来自于有备而来。**

### 1a: 必需读取

- **游戏概念**：读取 `design/gdd/game-concept.md` — 如果缺失，警告：
  > "未找到游戏概念。首先运行 `/brainstorm` 以在设计 UX 之前建立游戏基础。"
  > 如果用户要求，仍然继续。

### 1b: 玩家旅程

读取 `design/player-journey.md`（如果存在）。对于每个相关部分，提取：
- 此屏幕出现在哪个旅程阶段？
- 玩家到达此屏幕时的情绪状态是什么？
- 此屏幕在旅程中服务于什么玩家需求？
- 此屏幕传达哪些关键时刻（来自旅程地图）？

如果玩家旅程文件不存在，注意缺口并继续：
> "在 `design/player-journey.md` 未找到玩家旅程地图。在没有它的情况下设计意味着我们将对玩家上下文做出假设。考虑在此规范起草后运行玩家旅程会议。"

### 1c: GDD UI 需求

全局搜索 `design/gdd/*.md` 并 grep `UI Requirements` 部分。读取任何按名称或类别引用此屏幕的 GDD 的 UI Requirements 部分。

这些 GDD UI Requirements 是此规范的**需求输入**。将它们收集为规范必须满足的约束列表。

如果设计 HUD，读取所有 GDD UI Requirements 部分 — HUD 聚合来自每个系统的需求。

### 1d: 现有 UX 规范

全局搜索 `design/ux/*.md` 并注意哪些屏幕已有规范。对于将链接到或从此屏幕链接的屏幕，读取其导航/流程部分以找到此规范必须匹配的入口和出口点。

### 1e: 交互模式库

如果 `design/ux/interaction-patterns.md` 存在，读取模式目录索引（模式名称及其单行描述）。不要读取完整模式详情 — 仅目录。这告诉你哪些模式已存在，以便你可以引用它们而不是重新发明。

### 1f: 艺术圣经

检查 `design/art/art-bible.md`。如果找到，读取视觉方向部分。UX 布局必须与已做出的美学承诺保持一致。

### 1g: 可访问性需求

检查 `design/accessibility-requirements.md`。如果找到，读取它。规范必须满足其中承诺的可访问性层级。

### 1h: 输入方法（来自项目配置）

读取 `.claude/docs/technical-preferences.md` 并提取 `## Input & Platform` 部分。存储这些值以在技能中使用 — 它们驱动交互地图并为可访问性需求提供信息：

- **输入方法** — 例如，键盘/鼠标、游戏手柄、触摸、混合
- **主要输入** — 此游戏的主导输入
- **游戏手柄支持** — 完整 / 部分 / 无
- **触摸支持** — 完整 / 部分 / 无
- **目标平台** — 用于安全区域和纵横比决策

如果该部分未配置（`[TO BE CONFIGURED]`），询问一次：
> "输入方法尚未配置。此游戏的目标是什么？"
> 选项："仅键盘/鼠标"、"仅游戏手柄"、"两者（PC + 主机）"、"触摸（移动）"、"以上所有"
>
> （运行 `/setup-engine` 以永久保存此设置，这样就不会再次询问。）

为其余会话存储答案。不要每个部分或每个屏幕再次询问。

### 1i: 展示上下文摘要

在任何设计工作之前，向用户展示简要摘要：

> **设计对象**: [屏幕/流程名称]**
> - 模式: [UX 规范 / HUD 设计 / 模式库]
> - 旅程阶段: [来自 player-journey.md，或 "未知 — 无旅程地图"]
> - 为此规范提供输入的 GDD 需求: [计数和名称，或 "未找到"]
> - 已规范化的相关屏幕: [列表，或 "尚无"]
> - 可用已知模式: [计数，或 "尚无模式库"]
> - 可访问性层级: [来自需求文档，或 "尚未定义"]
> - 输入方法: [来自 technical-preferences.md，或 "上面询问"]

然后询问："在开始之前，我还有什么应该读取的吗，或者我们可以继续？"

## 阶段 2: 改造模式检测

在创建骨架之前，检查目标输出文件是否已存在。

全局搜索 `design/ux/[filename].md`（其中 `[filename]` 是阶段 1 中解析的输出路径）。

**如果文件存在 — 改造模式：**
- 完整读取文件
- 对于每个预期部分，检查正文是否有真实内容（不仅仅是 `[待设计]` 占位符）或为空/占位符
- 向用户展示部分状态表：

> "在 `design/ux/[filename].md` 找到现有 UX 规范。以下是已完成的内容：
>
> | 部分 | 状态 |
> |---------|--------|
> | 概述与上下文 | [完成 / 为空 / 占位符] |
> | 玩家旅程集成 | ... |
> | 屏幕布局和信‎息架构 | ... |
> | 交互模型 | ... |
> | 反馈和状态通信 | ... |
> | 可访问性 | ... |
> | 边缘情况和错误状态 | ... |
> | 开放问题 | ... |
>
> 我将只处理 [N] 个未完成部分 — 不会触及现有内容。"

- 跳过阶段 3（骨架创建）— 文件已存在
- 在阶段 4（部分编写）中，仅处理状态为"为空"或"占位符"的部分
- 使用 `Edit` 就地填充占位符，而不是创建新骨架

**如果文件不存在 — 全新编写模式：**
正常继续到阶段 3（创建文件骨架）。

## 阶段 4: 逐节编写

按顺序遍历每个部分。对于**每个部分**，遵循此循环：

```
上下文  ->  问题  ->  选项  ->  决策  ->  草稿  ->  批准  ->  写入
```

1. **上下文**：说明此部分需要包含的内容，并提出在阶段 1 中收集的上下文中的任何相关约束。
2. **问题**：询问起草此部分需要什么。对受限选择使用 `AskUserQuestion`，对开放式探索使用对话文本。
3. **选项**：在存在设计选择的地方，提供 2-4 种方法及其优缺点。在对话中解释推理，然后使用 `AskUserQuestion` 捕获决策。
4. **决策**：用户选择方法或提供自定义方向。
5. **草稿**：在对话中编写部分内容以供审查。显式标记临时假设。
6. **批准**："这捕获到了吗？在我将其写入文件之前有任何更改吗？"
7. **写入**：使用 `Edit` 将批准的 `[待设计]` 占位符替换为批准的内容。确认写入。

写入每个部分后，更新 `production/session-state/active.md`。

### 部分指南: UX 规范模式

#### 部分 A: 目的和玩家需求

此部分是基础。所有其他决策都从中流出。

**要询问的问题**：
- "此屏幕服务于什么玩家目标？玩家想在这里做什么？"
- "如果此屏幕不存在或难以使用，会发生什么错误？"
- "完成这个句子：'玩家到达此屏幕时想要 ___。'"

交叉引用在阶段 1 中收集的玩家旅程上下文。所述目的必须与旅程阶段和情绪状态保持一致。

#### 部分 B: 到达时的玩家上下文

**要询问的问题**：
- "玩家在游戏中何时首次遇到此屏幕？"
- "他们在到达此屏幕之前立即在做什么？"
- "设计应该假设什么情绪状态？（平静、紧张、好奇、时间紧迫）"
- "玩家是自愿到达此屏幕，还是游戏将他们发送到这里？"

如果玩家旅程文档存在，提供将其与旅程阶段进行映射的选项。

#### 部分 B2: 导航位置

此屏幕位于游戏的导航层次结构中的什么位置？这是一个单段落方向地图 — 不是完整的流程图。

**要询问的问题**：
- "此屏幕是从主菜单、暂停、游戏玩法内还是从另一个屏幕访问的？"
- "它是顶级目标（始终可达）还是依赖于上下文的目标（仅在某些状态下可访问）？"
- "玩家可以从游戏中的多个位置到达此屏幕吗？"

展示为："此屏幕位于：[根] → [父级] → [此屏幕]" 加上任何替代入口路径。

#### 部分 B3: 入口和出口点

映射玩家可以到达和离开此屏幕的所有方式。

**要询问的问题**：
- "玩家可以到达此屏幕的所有方式是什么？"（列出每个触发器：按钮按下、游戏事件、从另一个屏幕重定向等）
- "玩家可以做什么来退出？当他们这样做时会发生什么？"（返回按钮、确认操作、超时、游戏事件）
- "是否有任何单向出口 — 玩家在不重新开始的情况下无法返回此屏幕？"

展示为两个表：

| 入口来源 | 触发器 | 玩家携带的上下文 |
|---------|---------|---------------------|
| [屏幕/事件] | [如何] | [他们到达时的状态/数据] |

| 出口目的地 | 触发器 | 备注 |
|-----------|---------|-------|
| [屏幕/事件] | [如何] | [任何不可逆的状态更改] |

#### 部分 C: 布局规范

这是最大和最交互的部分。在子部分中完成工作：

**子部分 1 — 信息层次结构**（在任何布局之前建立此部分）：
- 要求用户列出此屏幕必须传达的每条信息。
- 然后要求他们排序项目："玩家需要首先看到的最重要的事情是什么？第二是什么？什么可以被发现而不是立即可见？"
- 在移动到区域之前展示结果层次结构以供批准。

**子部分 2 — 布局区域**：
- 基于信息层次结构，提出粗略的屏幕区域（页眉、内容区域、操作栏、侧边栏等）。
- 为每个区域提供 2-3 种区域布置及其基本原理。引用来自游戏概念的平台和输入上下文。
- 询问："其中任何一个与你的心理图像匹配吗，还是我们构建自定义布置？"

**子部分 3 — 组件清单**：
- 对于每个区域，列出它包含的 UI 组件。对于每个组件，注意：
  - 组件类型（按钮、列表、卡片、统计显示、输入字段等）
  - 它显示的内容
  - 它是否是交互式的
  - 它是否使用库中的现有模式（按模式名称引用）
  - 它是否引入了新模式（标记为稍后添加到库）

**子部分 4 — ASCII 线框图**：
- 提供基于区域布局和组件列表生成 ASCII 线框图。
- 使用 `AskUserQuestion`："要在规范中包含 ASCII 线框图吗？"
  - 选项："是，包含一个"、"否，我将附加单独的文件"
- 如果是，首先在对话中生成线框图。在写入文件之前征求反馈。

#### 部分 D: 状态和变体

引导用户超越快乐路径。

**要询问的问题**（一次处理一个）：
- "玩家第一次看到此屏幕时它看起来像什么，当还没有数据时？（空状态）"
- "当出现问题时会怎样 — 错误、失败的操作、缺失的资源？（错误状态）"
- "此屏幕上是否有加载等待？如果是，它显示什么？（加载状态）"
- "是否有任何改变此屏幕显示内容的玩家进度状态？例如，锁定的内容、高级内容或教程模式覆盖？"
- "此屏幕在任何支持的平台上的行为是否不同？（平台变体）"

将收集的状态展示为表以供批准：

| 状态 / 变体 | 触发器 | 更改内容 |
|-----------------|---------|--------------|
| 默认 | 正常加载 | — |
| 空 | 无可用数据 | [内容区域描述] |
| [等] | [触发器] | [更改] |

#### 部分 E: 交互地图

对于布局规范中标识的每个交互式组件，定义：
- 操作（点击、单击、按下、按住、滚动、拖动）
- 触发它的平台输入（鼠标点击、游戏手柄 A、键盘回车）
- 即时反馈（视觉、音频、触觉）
- 结果（导航目标、状态更改、数据写入）

使用在阶段 1h 中从 `technical-preferences.md` 加载的输入方法 — 不要再次询问用户。 upfront 说明它们：
"为以下对象映射交互：[技术首选项中的输入方法]。覆盖 [游戏手柄支持] 游戏手柄支持。"

逐个组件工作，而不是一次询问所有组件。对于导航操作（转到另一个屏幕），验证目标是否与现有 UX 规范匹配，或将其记为规范依赖项。

#### 部分 E2: 触发的事件

对于交互地图中的每个玩家操作，记录相应的事件，游戏或分析系统应触发 — 或显式注意"无事件"（如果不适用）。

**要询问的问题**：
- "对于每个操作，游戏是否应该触发分析事件、触发游戏状态更改，或两者兼而有之？"
- "是否有任何不应触发事件的操作 — 这是 deliberate 选择吗？"

与交互地图一起展示为表：

| 玩家操作 | 触发的事件 | 负载 / 数据 |
|-----------|---------------|--------------|
| [操作] | [事件名称] 或无 | [随事件传递的数据] |

标记任何修改持久游戏状态（保存数据、进度、经济）的操作 — 这些需要架构团队的明确关注。

#### 部分 E3: 过渡和动画

指定屏幕如何进入和退出，以及如何响应状态更改。

**要询问的问题**：
- "此屏幕如何出现？（淡入、从右侧滑入、即时弹出、从按钮缩放）"
- "它如何关闭？（淡出、滑回、剪切）"
- "是否有任何屏幕内状态过渡需要动画？（加载旋转器、成功状态、错误闪烁）"
- "是否有任何可能导致晕动病的动画 — 游戏是否有减少动作选项？"

最低要求：
- 屏幕进入过渡
- 屏幕退出过渡
- 如果屏幕有多个状态，则至少一个状态更改动画

#### 部分 F: 数据需求

交叉引用在阶段 1 中收集的 GDD UI Requirements 部分。

对于屏幕显示的每条信息，询问：
- "此数据来自哪里？哪个系统拥有它？"
- "此屏幕是否需要将数据写回，还是只读？"
- "其中任何数据是否对时间敏感或实时？（血条、冷却计时器）"

将任何情况下 UI 需要拥有或管理游戏状态标记为架构问题。UX 规范定义 UI 需要什么；它们不指示如何传递数据。这是架构决策。

将数据需求展示为表：

| 数据 | 源系统 | 读取 / 写入 | 备注 |
|------|--------------|--------------|-------|
| [项目] | [系统] | 读取 | — |
| [项目] | [系统] | 写入 | [任何关注] |

#### 部分 G: 可访问性

交叉引用 `design/accessibility-requirements.md`（如果存在）。

遍历此屏幕的 ux-designer 代理的标准检查清单：
- 所有交互式元素的仅键盘导航路径
- 游戏手柄导航顺序（如果适用）
- 文本对比度和最小可读字体大小
- 独立于颜色（不单独通过颜色传达信息）
- 任何非文本元素的屏幕阅读器考虑
- 任何需要减少动作替代的动动作或动画

使用 `AskUserQuestion` 提出有关可访问性层级的开放问题：
- "是否为此项目承诺了可访问性层级？"
  - 选项："是，从需求文档读取"、"尚未 — 让我们将其标记为问题"、"现在跳过可访问性部分"

#### 部分 H: 本地化考虑

记录当文本被翻译时影响此屏幕行为的约束。

**要询问的问题**：
- "此屏幕上的哪些文本元素最长？适合布局的最大字符计数是多少？"
- "是否有任何文本长度对布局至关重要的元素 — 例如，必须保持在一行的按钮标签？"
- "是否有任何显示数字、日期或货币的元素需要特定于区域设置的格式？"

注意：旨在标记任何 40% 文本扩展（从英语翻译成德语或法语时常见）会破坏布局的元素。将这些标记为本地化工程师的高优先级。

#### 部分 I: 验收标准

编写至少 5 个具体的、可测试的标准，QA 测试人员可以在不读取任何其他设计文档的情况下验证这些标准。这些成为 `/story-done` 的通过/失败条件。

**格式**：使用复选框。每个标准必须可由人类测试人员验证：

```
- [ ] 屏幕在 [触发器] 后 [X]ms 内打开
- [ ] [元素] 在 [最小值] 和 [最大值] 值下正确显示
- [ ] [导航操作] 正确路由到 [目标屏幕]
- [ ] 当 [条件] 时出现错误状态并显示 [特定消息或图标]
- [ ] 键盘/游戏手柄导航以逻辑顺序到达所有交互式元素
- [ ] [可访问性需求] 得到满足 — 例如，"所有交互式元素都有焦点指示器"
```

**最低要求**：
- 1 个性能标准（加载/打开时间）
- 1 个导航标准（至少验证一个入口或出口路径）
- 1 个错误/空状态标准
- 1 个可访问性标准（每个承诺的层级）
- 1 个特定于此屏幕核心目的的标准

询问用户以确认："这些标准是否涵盖了使此屏幕对您的 QA 流程'完成'的实际内容？"

### 部分指南: HUD 设计模式

HUD 设计遵循与 UX 规范模式不同的顺序。从理念开始；在信息架构完成之前不要触及布局。

#### 部分 A: HUD 理念

要求用户用 1-2 句话描述游戏与屏幕上信息的关系。

提供框架示例以帮助：
- "几乎无 HUD — 氛围需要不受阻碍的沉浸感（例如，《空洞骑士》、《火监视》）"
- "最小但存在 — 仅关键信息可见，其他所有内容都是上下文的（例如，《黑暗之魂》）"
- "信息密集 — 所有决策相关数据始终可见（例如，《暗黑破坏神 IV》、《星际争霸 II》）"
- "自适应 — HUD 密度响应战斗状态、探索模式、菜单（例如，《战神》）"

此理念成为每个后续 HUD 决策的设计约束。如果提议的元素与所述理念冲突，提出该冲突。

#### 部分 B: 信息架构

在完成任何布局工作之前完成此操作。不要跳过它。

**步骤 1 — 完整信息清单**：
拉取在阶段 1 中收集的 GDD UI Requirements 部分中的所有信息。展示完整列表：
"这些是你的游戏系统说他们需要在屏幕上向玩家传达的所有事情。"

**步骤 2 — 分类**：
对于每个项目，要求用户对其进行分类：

| 类别 | 描述 |
|----------|-------------|
| **必须显示** | 始终可见，玩家需要它来做核心决策 |
| **上下文的** | 仅在相关时可见（在战斗中、在可交互对象附近等） |
| **按需** | 玩家必须主动请求它（切换、按住按钮） |
| **隐藏** | 通过世界/音频传达，从不通过屏幕上的文本 |

使用 `AskUserQuestion` 以 3-4 个为一组逐步处理项目，而不是一次处理所有项目。

这是 HUD 中最重要的设计决策 — 不要急于完成它。

**冲突检查**：如果信息理念（部分 A）说"几乎无 HUD"，但必须显示列表越来越长，显式提出冲突：
> "当前的必须显示列表有 [N] 个项目。这可能与无 HUD 理念冲突。选项：减少必须显示列表、修订理念，或定义探索和战斗时 HUD 不存在的混合方法。"

#### 部分 C: 布局区域

仅在信息架构批准后，设计布局区域。

基于：
- 哪些项目是必须显示（它们驱动永久区域决策）
- 游戏玩法期间玩家注意力自然去哪里（动作游戏的中心屏幕、策略游戏的角落）
- 平台和纵横比目标

提供 2-3 种区域布置。包括基于 HUD 理念和来自部分 B 的分类的基本原理。

#### 部分 D: HUD 元素

对于布局中的每个元素，指定：
- 元素名称和类别（必须显示 / 上下文的 / 按需）
- 显示的内容
- 视觉形式（条、数字、图标、计数器、地图）
- 更新行为（实时、事件驱动、玩家查询）
- 上下文触发器（如果不是很可见）
- 动画行为（低时是否脉冲？淡入？砰地一声进入？）

逐个元素工作。引用交互模式库（如果存在用于状态显示、资源条或冷却指示器的相关模式）。

### 部分指南: 交互模式库模式

模式库编写是加法的和目录驱动的，不是线性的。

#### 阶段 1: 编目现有模式

全局搜索 `design/ux/*.md`（排除 `interaction-patterns.md`）并读取每个规范的组件清单和交互地图部分。提取使用的每个交互模式。

展示提取的列表："基于现有 UX 规范，这些模式已在游戏中使用："
- [模式名称]：用于 [屏幕]、[屏幕]
- [等]

询问："是否有你知道存在但尚未在现有规范中的模式？现在列出任何其他模式。"

#### 阶段 2: 形式化每个模式

对于每个模式（现有或新），记录：

```markdown
### [模式名称]

**类别**: 导航 / 输入 / 反馈 / 数据显示 / 模态 / 覆盖 / [其他]
**用于**: [屏幕列表]

**描述**: [一段解释此模式是什么以及何时使用它的文字]

**规范**:
- [组件行为]
- [输入映射]
- [视觉/音频反馈]
- [此模式的可访问性需求]

**何时使用**: [此模式合适的情况]
**何时不使用**: [另一种模式更合适的情况]

**参考**: [屏幕截图路径或 ASCII 示例（如果可用）]
```

以组为单位处理模式。提供："我应该根据我在现有规范中找到的内容起草第一批，还是你想逐一定义它们？"

#### 阶段 3: 识别缺口

编目已知模式后，询问：
- "是否有计划的需要尚未在此库中的模式的屏幕或交互？"
- "现有规范中是否有任何模式彼此不一致并应该合并？"

在缺口部分记录缺口以供跟进。

---

## 阶段 5: 交叉引用检查

在将规范标记为准备好审查之前，运行这些检查：

**1. GDD 需求覆盖**：引用此屏幕的每个 GDD UI 需求在此规范中是否有相应元素？展示任何缺口。

**2. 模式库对齐**：此规范中使用的所有交互模式是否都按名称引用？如果在此规范会话期间发明了新模式，将其标记为添加到模式库：
> "此规范使用 [模式名称]，它还不在模式库中。
> 想现在添加它，还是将其标记为缺口？"

**3. 导航一致性**：此规范中的入口/出口点是否与任何相关规范中的导航地图匹配？标记不匹配。

**4. 可访问性覆盖**：规范是否解决了 `design/accessibility-requirements.md` 中承诺的可访问性层级？如果没有，标记开放问题。

**5. 空状态**：每个依赖数据的元素是否都定义了空状态？标记任何没有的元素。

展示检查结果：

> **交叉引用检查: [屏幕名称]**
> - GDD 需求: [N of M 已覆盖 / 全部覆盖]
> - 要添加到库的新模式: [列表或 "无"]
> - 导航不匹配: [列表或 "无"]
> - 可访问性缺口: [列表或 "无"]
> - 缺失的空状态: [列表或 "无"]

## 阶段 6: 移交

当所有部分都获得批准并写入时：

### 6a: 更新会话状态

使用以下信息更新 `production/session-state/active.md`：
- 任务：[屏幕名称] UX 规范
- 状态：完成（或审查中）
- 文件：`design/ux/[filename].md`
- 部分：全部写入
- 下一步：[建议]

### 6b: 建议下一步

在展示选项之前，清楚地说明：

> "此规范应在进入实施管道之前使用 `/ux-review` 进行验证。
> 预生产门控要求所有关键屏幕规范都有审查判定。"

然后使用 `AskUserQuestion`：
- "现在运行 `/ux-review [filename]`，还是先做一些其他事情？"
  - 选项：
    - "现在运行 `/ux-review` — 验证此规范"
    - "先设计另一个屏幕，然后一起审查所有规范"
    - "使用此规范中的新模式更新交互模式库"
    - "在此处停止此会话"

如果用户选择"先设计另一个屏幕"，添加注释：
"提醒：在运行 `/gate-check pre-production` 之前，对所有已完成的规范运行 `/ux-review`。"

### 6c: 交叉链接相关规范

如果其他 UX 规范链接到或从此屏幕链接，注意应该引用此规范的规范。不要在没有询问的情况下编辑这些文件 — 只需命名它们。

## 阶段 7: 恢复和恢复

如果会话被中断（压缩、崩溃、新会话）：

1. 读取 `production/session-state/active.md` — 它记录当前屏幕和哪些部分已完成。
2. 读取 `design/ux/[filename].md` — 具有真实内容的部分已完成；具有 `[待设计]` 的部分仍需要工作。
3. 从下一个未完成部分恢复 — 无需重新讨论已完成的部分。

这就是为什么增量写入很重要：每个批准的部分都能经受任何中断。

## 阶段 8: 专家代理路由

此技能使用 `ux-designer` 作为主要代理（在 frontmatter 中设置）。对于特定子主题，可能需要额外的上下文或协调：

| 主题 | 与...协调 |
|-------|----------------|
| 视觉美学、颜色、布局感觉 | `art-director` — UX 规范定义区域；艺术定义它们的外观 |
| 实施可行性（引擎约束） | `ui-programmer` — 在最终确定组件清单之前 |
| 游戏玩法数据需求 | `game-designer` — 当数据所有权不清楚时 |
| UI 中可见的叙述/传说 | `narrative-director` — 用于风味文本、项目名称、传说面板 |
| 可访问性层级决策 | 由此次会话处理 — 由 ux-designer 拥有 |

通过 Task 工具委托给另一个代理时：
- 提供：屏幕名称、游戏概念摘要、需要专家输入的特定问题
- 代理将分析返回到此会话
- 此会话将代理的输出呈现给用户
- 用户决定；此会话写入文件
- 代理不直接写入文件 — 此会话拥有所有文件写入

## 协作协议

此技能在每个步骤都遵循协作设计原则：

1. **问题 → 选项 → 决策 → 草稿 → 批准** 对于每个部分
2. **在每个决策点使用 `AskUserQuestion`**（解释 → 捕获模式）：
   - 阶段 2："准备好开始，还是需要更多上下文？"
   - 阶段 3："我可以创建骨架吗？"
   - 阶段 4（每个部分）：设计问题、方法选项、草稿批准
   - 阶段 5："运行交叉引用检查？下一步是什么？"
3. **"我可以写入 [文件路径] 吗？"** 在骨架之前和每个部分写入之前
4. **增量写入**：每个部分在批准后立即写入文件
5. **会话状态更新**：在每个部分写入之后

**美学 deferment**：当布局或视觉选择取决于个人品味时，展示选项并询问。不要因为"标准"而选择布局 — 始终确认。用户是创意总监。

**冲突表面**：当 GDD 需求和可用屏幕空间冲突时，表面冲突并提供解决选项。永远不要静默删除需求。永远不要静默扩展布局而不标记它。

**永远不要**自动生成完整规范并将其作为既成事实呈现。
**永远不要**在没有用户批准的情况下写入部分。
**永远不要**在没有标记冲突的情况下与现有批准的 UX 规范相矛盾。
**始终**显示决策的来源（GDD 需求、玩家旅程、用户选择）。

判定：**完成** — UX 规范已编写并获得逐节批准。
