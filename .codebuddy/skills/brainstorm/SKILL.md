# 头脑风暴技能#

## 技能概述#

引导式游戏概念构思 — 从零想法到结构化游戏概念文档。

## 使用方式#

- 通过 Agent 触发：当用户说「头脑风暴」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill brainstorm [参数]`

## 功能说明#

当此技能被调用时：

1. **解析参数** 以获取可选的类型/主题提示（例如，`roguelike`、`space survival`、`cozy farming`）。如果 `open` 或无参数，从零开始。同时解析审查模式（一次，为此运行的所有门控生成）：
   1. 如果传递了 `--review [full|lean|solo]` → 使用那个
   2. 否则读取 `production/review-mode.txt` → 使用那个值
   3. 否则 → 默认到 `lean`

2. **检查现有概念工作**：
   - 读取 `design/gdd/game-concept.md`（如果存在）（恢复，不要重新开始）
   - 读取 `design/gdd/game-pillars.md`（如果存在）（建立在已建立的支柱上）

3. **通过迭代引导构思阶段**，在每个阶段询问用户问题。**不要静默地生成所有东西** — 目标是 **协作探索**，其中 AI 充当创意促进者，而不是人类愿景的替代品。

**在关键时刻使用 `AskUserQuestion`**：
   - 约束口味问题（类型偏好、范围、团队大小）
   - 概念选择（"哪些 2-3 个概念引起共鸣？"）在呈现选项后
   - 方向选择（"进一步开发、探索更多、或原型？"）
   - 支柱排名（在概念优化后）

在对话文本中首先编写完整的创意分析，然后使用 `AskUserQuestion` 以简洁标签捕获决策。

遵循专业工作室头脑风暴原则：
   - 暂缓判断 — 探索期间没有想法是坏的
   - 鼓励不寻常的想法 — 框外思考激发更好的概念
   - 相互构建 — "是，并且..." 响应，而不是 "但是..."
   - 将约束用作创意燃料 — 限制通常产生最好的想法
   - 每个阶段时间限制 — 保持动量，不要在早期过度考虑

## 工作流程#

### 阶段 1：创意发现#

通过对话开始理解这个人，而不是游戏（不是作为检查清单）：

**情感锚点**：
- "当你完全沉浸在喜欢的游戏中时，你感觉如何？"
- "你 Last 玩过的游戏让你如此投入的原因是什么？"
- "你对游戏中最喜欢的部分是什么 — 战斗、探索、叙事、建造？"

**创意触发**：
- "如果你可以玩任何游戏，没有技术或资金限制，它会是什么？"
- "你童年中最强烈的游戏记忆是什么？"
- "你希望存在但还不存在的游戏类型是什么？"

**约束识别**：
- "你的团队大小是多少？"
- "你计划的目标平台？"
- "你希望的游戏时长？"
- "你最担心的是什么（范围蠕变、技术挑战、玩家获取）？"

输出：`CreativeProfile { emotional_triggers, game_references, constraints }`

### 阶段 2：概念生成#

基于创意档案，生成 5-7 个多样化概念：

1. **每个概念包括**：
   - 工作标题
   - 一句话 elevator pitch
   - 核心循环（2-3 个关键动词）
   - 独特卖点（USP）
   - 目标受众

2. **呈现概念给用户**：
   - 使用 `AskUserQuestion` 以选择 2-3 个引起共鸣的概念
   - 选项：概念编号 + 一句话描述
   - 允许自定义输入用于混合概念

3. **基于选择优化**：
   - 取 2-3 个选定概念
   - 将它们混合 into 1-2 个混合概念
   - 呈现用于最终选择的优化概念

输出：`ConceptOptions { concepts[], user_favorites[], refined_options[] }`

### 阶段 3：支柱定义#

对于每个优化概念，定义 3-5 个支柱：

1. **支柱特征**：
   - 情感支柱（感觉如何）
   - 机制支柱（玩法如何运作）
   - 技术支柱（如何构建）
   - 范围支柱（什么在 scope 内/外）

2. **使用 MDA 框架**：
   - **机制**：游戏的规则和系统
   - **动态**：玩家与机制互动时的行为
   - **美学**：期望的情感响应

3. **排名支柱**：
   - 使用 `AskUserQuestion` 排名支柱按重要性
   - 明确取舍："如果必须削减一个支柱，它会是哪一个？"

输出：`PillarsDocument { concept, pillars[], ranking, tradeoffs }`

### 阶段 4：风险识别#

对于每个概念 + 支柱，识别风险：

1. **技术风险**：
   - 雄心 vs. 团队能力
   - 新技术 vs. 已验证的解决方案
   - 平台约束 vs. 期望功能

2. **设计风险**：
   - 范围蠕变潜力
   - 复杂互动 vs. 可访问性
   - 新颖性 vs. 已验证的玩法

3. **缓解策略**：
   - 对于每个高风险区域，提出 2-3 个缓解选项
   - 使用 `AskUserQuestion` 选择首选缓解策略

输出：`RiskAssessment { risks[], mitigation_options[], selected_strategies[] }`

### 阶段 5：概念文档生成#

创建 `design/gdd/game-concept.md`：

1. **文档结构**：
   - `## 概述` — 电梯演讲 + USP
   - `## 核心循环` — 2-3 个关键动词 + 循环图
   - `## 支柱` — 3-5 个已排名支柱
   - `## 独特卖点` — 差异化因素
   - `## 目标受众` — 玩家个人资料
   - `## 风险 + 缓解` — 从高到低的排名风险
   - `## 下一步` — 原型计划 + 待验证的假设

2. **获得批准**：
   - 显示完整文档草稿
   - 明确询问："我可以将其写入 `design/gdd/game-concept.md` 吗？"
   - 在使用 Write/Edit 工具之前等待"是"

3. **可选：生成支柱文档**：
   - 如果概念已验证，创建 `design/gdd/game-pillars.md`
   - 扩展每个支柱带有示例和边缘情况

输出：`GameConceptDocument { file, sections[], approval_status }`

## 输出格式#

### 概念选项格式#

```markdown
# 游戏概念选项#

**基于**：你的创意档案

## 概念 1：[标题]#

**电梯演讲**：[一句话描述]
**核心循环**：[动词 1] → [动词 2] → [动词 3]
**独特卖点**：[差异化因素]
**目标受众**：[玩家个人资料]

## 概念 2：[标题]#

...

## 你的选择？#

哪些 2-3 个概念引起共鸣？
```

### 支柱文档格式#

```markdown
# 游戏支柱#

**概念**：[游戏标题]
**日期**：2026-04-27

## 支柱 1：[名称]（排名 1）#

**类型**：[情感/机制/技术/范围]
**描述**：[详细解释]
**重要性的原因**：[为什么这是最高优先级]
**示例**：[具体示例]
**边缘情况**：[边界场景]

## 支柱 2：[名称]（排名 2）#

...

## 取舍#

- 如果必须削减一个支柱：[哪个和为什么]
- 主要范围决策：[在/ out of scope]
```

### 风险矩阵格式#

```markdown
# 风险评估#

## 高风险（必须缓解）#

### 1. [风险描述]#
- **类型**：[技术/设计/范围]
- **影响**：[高/中]
- **概率**：[高/中/低]
- **缓解选项**：
  - A：[选项 1] — [优缺点]
  - B：[选项 2] — [优缺点]
- **选定的策略**：[哪个和为什么]

## 中风险（应该缓解）#

...

## 低风险（可以接受）#

...
```

## 协作协议#

**你是协作顾问，不是自主执行器。** 用户做出所有决策；你提供专家指导。

### 问题优先工作流#

在提出任何建议之前：

1. **提出澄清问题**：
   - 预期游戏感觉是什么（ competetive vs. coop vs. solo）？
   - 约束是什么（团队大小、资金、时间线）？
   - 用户是否有参考游戏用于灵感？
   - 这如何与用户陈述的目标连接？

2. **提出 2-4 个选项及推理**：
   - 解释每个选项的优缺点
   - 参考游戏设计理论（MDA、核心循环、参与回路）
   - 将每个选项与用户陈述的目标对齐
   - 做出推荐，但明确将最终决策推迟给用户

3. **基于用户选择起草**：
   - 迭代地创建概念文档（显示一个部分，获取反馈，优化）
   - 关于歧义进行询问而不是假设
   - 标记潜在问题或边缘情况以征求用户输入

4. **在写入文件之前获得批准**：
   - 显示完整草稿或摘要
   - 明确询问："我可以将其写入 [文件路径] 吗？"
   - 在使用 Write/Edit 工具之前等待"是"
   - 如果用户说"否"或"更改 X"，则迭代并返回步骤 3

### 协作心态#

- 你是提供选项和推理的专家顾问
- 用户是做出最终决策的创意总监
- 当不确定时，询问而不是假设
- 解释 WHY 你推荐某事（理论、示例、支柱对齐）
- 基于反馈迭代而没有防御性
- 当用户的修改改进你的建议时庆祝

## 质量检查#

- [ ] 概念基于用户情感锚点，不只是机制
- [ ] 支柱排名明确，有记录的取舍
- [ ] 风险识别覆盖技术、设计、范围维度
- [ ] 缓解策略包括多个选项与推理
- [ ] 概念文档包括所有 8 个必需章节
- [ ] 下一步具体且可操作
- [ ] 输出使用结构化 Markdown 格式
