# 测试证据审查技能

## 技能概述

验证测试结果，检测不稳定测试。`/smoke-check` 验证测试文件**存在**和**通过**。此技能更进一步 — 它审查这些测试和证据文档的**质量**。

存在于文件且通过的测试仍可能遗漏关键行为。存在的手动证据文档可能缺少关闭所需的签署。

**适用场景**：
- QA 移交签署（`/team-qa` 阶段 5）之前
- 任何测试质量有疑问的故事
- 作为里程碑审查的一部分用于逻辑和集成故事质量审计

**输出**：摘要报告（对话中）+ 可选的 `production/qa/evidence-review-[date].md`

## 使用方式

- 通过 Agent 触发：当用户说「测试证据审查」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill test-evidence-review [参数]`

**参数模式**：
- `/test-evidence-review [story-path]` — 审查单个故事的证据
- `/test-evidence-review sprint` — 审查当前冲刺中的所有故事
- `/test-evidence-review [system-name]` — 审查史诗/系统中的所有故事
- 无参数 — 询问范围："单个故事"、"当前冲刺"、"一个系统"

---

## 阶段 0: 解析参数

**参数**: `$ARGUMENTS[0]` (空白 = 询问用户）

从参数确定模式：

| 参数 | 模式 | 操作 |
|----------|------|----------|
| `[story-path]` | 单个故事 | 直接读取故事文件 |
| `sprint` | 当前冲刺 | 读取 `production/sprints/` 中最近修改的文件 |
| `[system-name]` | 系统 | 全局搜索 `production/epics/[system-name]/story-*.md` |
| 无参数 | 询问 | 使用 `AskUserQuestion` 询问范围 |

---

## 阶段 1: 加载范围内的故事

根据参数：

**单个故事**：直接读取故事文件。提取：故事类型、测试证据部分、故事标签、系统名称。

**冲刺**：读取 `production/sprints/` 中最近修改的文件。从冲刺计划中提取故事文件路径列表。读取每个故事文件。

**系统**：全局搜索 `production/epics/[system-name]/story-*.md`。读取每个文件。

对于每个故事，收集：
- `Type:` 字段（Logic / Integration / Visual/Feel / UI / Config/Data）
- `## Test Evidence` 部分 — 陈述的预期测试文件路径或证据文档
- 故事标签（从文件名）
- 系统名称（从目录路径）
- 验收标准列表（所有复选框项目）

---

## 阶段 2: 定位证据文件

对于每个故事，查找证据：

**逻辑故事**：全局搜索 `tests/unit/[system]/[story-slug]_test.*`
  - 如果未找到， also try：在 `tests/unit/[system]/` 中 Grep 包含故事标签的文件

**集成故事**：全局搜索 `tests/integration/[system]/[story-slug]_test.*`
  - Also check `production/session-logs/` 中提及故事的试玩记录

**Visual/Feel 和 UI 故事**：全局搜索 `production/qa/evidence/[story-slug]-evidence.*`

**Config/Data 故事**：全局搜索 `production/qa/smoke-*.md`（任何冒烟检查报告）

**注意**：为每个故事记录找到的内容（路径）或未找到（缺口）。

---

## 阶段 3: 审查自动化测试质量（Logic / Integration）

对于每个找到的测试文件，读取并评估：

### 断言覆盖

计算不同断言的数量（包含 assert、expect、check、verify 或引擎特定断言模式的行）。低断言计数是质量信号 — 每个测试函数仅进行 1 次断言的测试可能未覆盖预期行为的范围。

**阈值**：
- **每个测试函数 3+ 断言** → 正常
- **每个测试函数 1-2 断言** → 注意为潜在薄弱
- **0 断言**（测试存在但无断言）→ 标记为阻止 — 测试空洞地通过并证明不了什么

### 边缘情况覆盖

对于故事中包含数字、阈值或"当 X 发生时"条件的每个验收标准：检查测试函数名称或测试正文是否引用该特定情况。

**启发式**：
- Grep 测试文件中的 "zero"、"max"、"null"、"empty"、"min"、"invalid"、"boundary"、"edge" — 任何存在都是积极信号
- 如果故事在 Formulas 部分有特定边界：检查测试是否在最小值/最大值处执行

### 命名质量

测试函数名称应描述：场景 + 预期结果。模式：`test_[scenario]_[expected_outcome]`

将函数命名为通用名（`test_1`、`test_run`、`testBasic`）标记为**命名问题** — 它们使失败更难诊断。

### 公式可追溯性

对于 GDD 有 Formulas 部分的 Logic 故事：检查测试文件是否包含至少一个其名称或注释引用公式名称或公式值的测试。在公式中练习但未按名称提及它的测试在公式更改时更难维护。

---

## 阶段 4: 审查手动证据质量（Visual/Feel / UI）

对于每个找到的证据文档，读取并评估：

### 标准链接

证据文档应引用故事中的每个验收标准。检查：证据文档是否包含每个标准（或清晰的重述）？

缺失的标准意味着标准从未被验证。

### 签署完整性

检查三个签署行（或等效字段）：
- 开发者签署
- 设计师 / 美术负责人签署（对于 Visual/Feel）
- QA 负责人签署

如果任何缺失或空白：标记为 INCOMPLETE — 故事无法在所有所需签署完成之前完全关闭。

### 屏幕截图 / 工件完整性

对于 Visual/Feel 故事：检查证据文档是否引用屏幕截图文件路径。如果引用，全局搜索它们以确认它们存在。

对于 UI 故事：检查是否存在遍历序列（逐步交互日志）。

### 日期覆盖

证据文档应有日期。如果日期早于故事的最后一次重大更改（启发式：与冲刺开始日期从冲刺计划比较），标记为可能过期 — 证据可能未覆盖最终实施。

---

## 阶段 5: 构建审查报告

对于每个故事，分配判定：

| 判定 | 含义 |
|---------|---------|
| **ADEQUATE** | 测试/证据存在，通过质量检查，所有标准已覆盖 |
| **INCOMPLETE** | 测试/证据存在但有质量缺口（薄弱断言、缺失签署） |
| **MISSING** | 未找到需要它的故事类型的测试或证据 |

整体冲刺/系统判定是存在的故事判定的最差情况。

```markdown
## 测试证据审查

> **日期**: [日期]
> **范围**: [单个故事路径 | 冲刺 [N] | [系统名称]]

> **已审查的故事**: [N]

> **整体判定**: ADEQUATE / INCOMPLETE / MISSING

---

### 逐故事结果

#### [故事标题] — [类型] — [ADEQUATE/INCOMPLETE/MISSING]

**测试/证据路径**: `[路径]` (找到) / (未找到)

**自动化测试质量** *(仅 Logic/Integration)*:
- 断言覆盖：[每个函数平均 N] — [足够 / 薄弱 / 无]
- 边缘情况：[已覆盖 / 部分 / 未找到]
- 命名：[一致 / [N] 个通用名称已标记]
- 公式可追溯性：[是 / 否 — 未引用公式名称的测试]

**手动证据质量** *(仅 Visual/Feel/UI)*:
- 标准链接：[N/M 标准已引用]
- 签署：[开发者 ✓ | 设计师 ✗ | QA 负责人 ✗]
- 工件：[屏幕截图存在 / 缺失 / N/A]
- 新鲜度：[日期为 [日期] — 当前 / 可能过期]

**问题**:
- 阻止项：[描述] *(防止故事完成)*
- 建议项：[描述] *(应在发布前处理)*
```

### 摘要

| 故事 | 类型 | 判定 | 问题 |
|-------|------|---------|--------|
| [标题] | Logic | ADEQUATE | 无 |
| [标题] | Integration | INCOMPLETE | 薄弱断言（平均每个函数 1.2） |
| [标题] | Visual/Feel | INCOMPLETE | QA 负责人签署缺失 |
| [标题] | Logic | MISSING | 未找到测试文件 |

**阻止项**（在故事可以关闭之前必须解决）：[N]
**建议项**（应在发布之前解决）：[N]

---

## 阶段 6: 写入输出（可选）

在对话中展示报告。

询问："我可以将此测试证据审查写入 `production/qa/evidence-review-[date].md` 吗？"

这是可选的 — 报告作为独立项是有用的。仅在用户批准后写入。

**写入后**：

- 对于阻止项："在 `/story-done` 可以将故事标记为完成之前，必须解决这些。您想现在处理其中的任何吗？"
- 对于薄弱断言："考虑运行 `/test-helpers [system]` 以查看是否为常见情况搭建了断言模式。"
- 对于缺失的签署："需要与 [角色] 共享 `[证据路径]` 以完成签署。"

判定：**完成** — 证据审查已完成。如果找到阻止项，使用 CONCERNS。

---

## 阶段 7: 协作协议

- **报告质量问题，不要修复它们** — 此技能读取和评估；它不修改测试文件或证据文档
- **ADEQUATE 意味着足够发布，不是完美** — 避免吹毛求疵通过且足够全面以给予信心的测试
- **阻止 vs. 建议区分很重要** — 仅当缺口使故事标准真正未验证时才标记阻止
- **在写入之前询问** — 报告文件是可选的；始终在写入之前确认
