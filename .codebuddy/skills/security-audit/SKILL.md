# 安全审计技能

## 技能概述

安全不是可选的。即使是单人游戏也有存档篡改向量。多人游戏有作弊表面、数据暴露风险和拒绝服务可能性。此技能系统性审计代码库中最常见的游戏安全失败，并生成优先修复计划。

**运行此技能：**
- 在任何公开发布前（Polish → Release 门控必需）
- 在启用任何在线/多人功能之前
- 实现从磁盘或网络读取的任何系统后
- 当报告安全相关的 Bug 时

**输出：** `production/security/security-audit-[date].md`

---

## 使用方式

- **通过 Agent 触发**：当用户说「安全审计」或相关需求时，Agent 应自动加载此 Skill
- **手动触发**：`/skill security-audit [参数]`

**模式：**
- `full` — 所有类别（发布前推荐）
- `network` — 仅网络/多人
- `save` — 仅存档文件和序列化
- `input` — 仅输入验证和注入
- `quick` — 仅高严重性检查（最快，用于迭代使用）
- 无参数 — 运行 `full`

---

## Phase 1：解析参数和范围

读取 `.claude/docs/technical-references.md` 以确定：
- 引擎和语言（影响要搜索的模式）
- 目标平台（影响哪些攻击表面适用）
- 多人/网络是否在范围内

如果没有参数，运行 `full` 模式。

---

## Phase 2：生成安全工程师

通过 Task 生成 `security-engineer`。传递：
- 审计范围/模式
- 来自技术偏好的引擎和语言
- 所有源目录的清单：`src/`、`assets/data/`、`any config files`

安全工程师跨 6 个类别运行审计（参见 Phase 3）。在继续之前收集他们的完整发现。

---

## Phase 3：审计类别

安全工程师评估以下每一项。跳过不适用于项目范围的类别。

### 类别 1：存档文件和序列化安全

- 存档文件在加载前是否经过验证？（无盲目反序列化）
- 存档文件路径是否从用户输入构造？（路径遍历风险）
- 存档文件是否有校验和或签名？（篡改检测）
- 游戏是否在没有边界检查的情况下信任来自存档文件的数值？
- 在存档加载附近是否有任何 eval() 或动态代码执行调用？

**Grep 模式**：`File.open`、`load`、`deserialize`、`JSON.parse`、`from_json`、`read_file` — 检查每个验证。

### 类别 2：网络和多人安全（仅单人游戏跳过）

- 游戏状态是否在服务器上权威，还是客户端决定结果？
- 传入网络数据包是否针对大小、类型和值范围进行验证？
- 玩家位置和状态更改是否在服务器端验证？
- 任何网络调用是否有速率限制？
- 身份验证令牌是否正确处理（永远不以明文发送）？
- 游戏是否在发布版本中暴露任何调试端点？

**Grep 模式**：`recv`、`receive`、`PacketPeer`、`socket`、`NetworkedMultiplayerPeer`、`rpc`、`rpc_id` — 检查每个调用站点的验证。

### 类别 3：输入验证

- 任何玩家提供的字符串是否用于文件路径？（路径遍历）
- 任何玩家提供的字符串是否在未经清理的情况下记录？（日志注入）
- 数值输入（例如，物品数量、角色属性）是否在使用前进行边界检查？
- 成就/统计值在写入任何后端之前是否经过检查？

**Grep 模式**：`get_input`、`Input.get_`、`input_map`、用户面向文本字段 — 检查验证。

### 类别 4：数据暴露

- 任何 API 密钥、凭据或秘密是否硬编码在 `src/` 或 `assets/` 中？
- 发布版本中是否包含调试符号或详细错误消息？
- 游戏是否将敏感玩家数据记录到磁盘或控制台？
- 任何内部文件路径或系统信息是否暴露给玩家？

**Grep 模式**：`api_key`、`secret`、`password`、`token`、`private_key`、`DEBUG`、`print(` 在面向发布的代码中。

### 类别 5：作弊和反篡改向量

- 游戏性关键值是否仅存储在内存中，而不是在易于编辑的文件中？
- 任何关键游戏进度标志（例如，"已支付 DLC"）是否在服务器端验证？
- 是否有针对多人游戏的内存编辑工具（Cheat Engine 等）的保护？
- 排行榜/分数提交在接受前是否经过验证？

**注意**：客户端反作弊在很大程度上是不可执行的。专注于服务器端验证任何竞争或货币化内容。

### 类别 6：依赖关系和供应链

- 是否使用任何第三方插件或库？列出它们。
- 正在使用的版本中是否有任何已知的 CVE？
- 插件来源是否经过验证（官方市场、审查的存储库）？

**Glob 模式**：`addons/`、`plugins/`、`third_party/`、`vendor/` — 列出所有外部依赖关系。

---

## Phase 4：分类发现

对于每个发现，分配：

**严重性：**

| 级别 | 定义 |
|-------|-----------|
| **严重性** | 远程代码执行、数据泄露或轻易可利用的作弊，破坏多人游戏完整性 |
| **高** | 绕过进度的存档篡改、凭据暴露或服务器端权限绕过 |
| **中** | 客户端作弊启用、信息披露或影响有限的输入验证差距 |
| **低** | 深度防御改进 — 减少攻击表面但没有直接利用 |

**状态：** 开放 / 已接受风险 / 超出范围

## Phase 7：门集成

此报告是 **Polish → Release 门控** 的必需制品。

修复发现后，重新运行：`/security-audit quick` 以在运行 `/gate-check release` 之前确认严重性/高项目已解决。

如果存在严重性发现：
> "⛔ 严重性安全发现必须在任何公开发布之前解决。在解决这些问题之前，不要继续到 `/launch-checklist`。"

如果没有严重性/高发现：
> "✅ 没有阻塞安全发现。写入 `production/security/` 的报告。运行 `/gate-check release` 时包含此路径。"

---

## 协作协议

- **永远不要假设模式是安全的** — 标记它并让用户决定
- **已接受风险是有效的结果** — 一些低发现是可以接受的权衡；记录决策
- **多人游戏有更高的标准** — 多人游戏上下文中的任何高发现都应被视为严重性
- **这不是渗透测试** — 此审计涵盖常见模式；在实际竞争或货币化多人游戏发布之前，推荐由人类安全专业人员进行真正的渗透测试
