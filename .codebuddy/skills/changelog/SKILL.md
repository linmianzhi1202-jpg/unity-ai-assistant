# 变更日志技能#

## 技能概述#

从提交历史自动生成 CHANGELOG。

## 使用方式#

- 通过 Agent 触发：当用户说「变更日志」或相关需求时，Agent 应自动加载此 Skill#
- 手动触发：`/skill changelog [参数]`

## 功能说明#

此技能从 git 提交历史生成结构化的 CHANGELOG 文件。

**输出：** `CHANGELOG.md` 或 `docs/changelog-[version].md`#

### 参数模式#

**版本模式：** `$ARGUMENTS[0]`（空白 = 最新标签到 HEAD`）：

- **版本号**（例如，`1.2.0`）— 生成该版本的变更日志`
- **`since [date]`** — 从指定日期生成`
- **`sprint [N]`** — 生成指定 sprint 的变更日志`
- **无参数** — 从最新标签到 HEAD 生成`

**示例**：
```
/skill changelog 1.2.0`
/skill changelog since 2026-01-01`
/skill changelog sprint 15`
/skill changelog`
```

## 工作流程#

### 阶段 1：解析参数#

确定目标范围：

1. 如果提供版本号，使用相应的 git 标签`
2. 如果提供日期，使用 `--since` 过滤提交`
3. 如果提供 sprint 编号，读取 sprint 报告以获取日期范围`
4. 如果无参数，使用最新标签到 HEAD`
5. 验证 git 可用：`git rev-parse --is-inside-work-tree`

### 阶段 2：收集变更数据#

读取 git 日志以获取目标范围：

```
git log [last-tag]..HEAD --pretty=format:"%H|%an|%ae|%ad|%s" --date=short
```

读取 sprint 报告（如果适用）以获取上下文。

对于每个提交，提取：
- **提交哈希**`
- **作者**`
- **日期**`
- **提交消息**`
- **任务/故事引用**（如果存在于提交消息中）`

输出：`ChangeData { commits[], task_refs[], context }`

### 阶段 3：分类变更#

将每个提交分类为这些类别之一：

1. **新特性**：全新的游戏性系统、模式或内容`
2. **改进**：对现有特性的增强、UX 改进、性能提升`
3. **Bug 修复**：对损坏行为的修正`
4. **平衡更改**：游戏性数值调整、难度变化、经济调整`
5. **已知问题**：团队知道但尚未解决 issues`
6. **杂项**：不适合上述类别的变更，或消息太模糊而无法自信分类`

对于每个提交，检查消息是否包含任务 ID 或故事引用（例如，`[STORY-123]`、`TR-`、`#NNN`）。计算缺少任务引用的提交数，并在阶段 4 指标部分中包含此计数作为：`Commits without task reference: [N]`。

### 阶段 4：生成变更日志#

创建 `CHANGELOG.md`（或 `docs/changelog-[version].md`）：

1. **标题**：版本号和日期`
2. **摘要**：变更计数按类别`
3. **新特性**：带描述性提交的列表`
4. **改进**：带描述性提交的列表`
5. **Bug 修复**：带描述性提交的列表`
6. **平衡更改**：带描述性提交的列表`
7. **已知问题**：已知但未修复的问题列表`
8. **杂项**：其他变更的列表`
9. **指标**：`
   - 提交总数`
   - 按类别分布`
   - 缺少任务引用的提交数`
   - 贡献者计数`

### 阶段 5：验证和批准#

1. 显示完整的变更日志草稿`
2. 询问用户："我可以将其写入 [文件路径] 吗？"`
3. 等待"是"再写入文件`
4. 如果"否"，迭代并优化`

## 协作协议#

**你是协作实现者，不是自主代码生成器。** 用户做出所有决策。

### 问题优先工作流#

在提出任何建议之前：

1. **提出澄清问题：**`
   - 目标版本或日期范围是什么？`
   - 是否有特定类别要强调？`
   - 变更日志的格式偏好是什么？`
   - 是否包含指标和贡献者统计？`

2. **提出 2-4 个选项及推理：**`
   - 解释每个选项的优缺点`
   - 参考变更管理最佳实践`
   - 将每个选项与用户陈述的目标对齐`
   - 做出推荐，但明确将最终决策推迟给用户`

3. **基于用户选择起草：**`
   - 迭代地创建变更日志（显示一个部分，获取反馈，优化）`
   - 关于歧义进行询问而不是假设`
   - 标记潜在问题或边缘情况以征求用户输入`

4. **在写入文件之前获得批准：**`
   - 显示完整草稿或摘要`
   - 明确询问："我可以将其写入 [文件路径] 吗？"`
   - 在使用 Write/Edit 工具之前等待"是"`
   - 如果用户说"否"或"更改 X"，则迭代并返回步骤 3`

### 协作心态#

- 你是提供选项和推理的专家顾问`
- 用户是做出最终决策的变更经理`
- 当不确定时，询问而不是假设`
- 解释 WHY 你推荐某事（理论、示例、标准对齐）`
- 基于反馈迭代而没有防御性`
- 当用户的修改改进你的建议时庆祝`
