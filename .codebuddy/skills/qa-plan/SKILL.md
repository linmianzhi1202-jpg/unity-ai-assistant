# QA 计划技能#

## 技能概述#

制定测试策略，定义测试覆盖范围。此技能提供结构化的 QA 计划生成工作流程，包括解析范围、加载输入、分类每个故事、生成测试计划、编写输出和协作协议。

## 使用方式#

- 通过 Agent 触发：当用户说「QA 计划」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill qa-plan [参数]`

---

## Phase 1: 解析范围#

**参数**：`$ARGUMENTS`（空白 = 通过 AskUserQuestion 询问用户）

从参数确定范围：

- **`sprint`** — 读取 `production/sprints/` 中最新的文件，提取每个引用的故事文件路径。如果 `production/sprint-status.yaml` 存在，使用它作为主要的故事列表，并回退到冲刺计划以获取故事元数据。
- **`feature: [system-name]`** — 扫描 `production/epics/*/story-*.md`，过滤故事，其文件路径或标题包含系统名称。也检查该系统目录中的史诗索引文件（`EPIC.md`）。
- **`story: [path]`** — 验证路径存在并加载该单个文件。
- **无参数** — 使用 `AskUserQuestion`：
  - "此 QA 计划的范围是什么？"
  - 选项："当前冲刺"、"特定功能（输入系统名称）"、"特定故事（输入路径）"、"完整史诗"

解析范围后，报告："正在为 [范围] 中的 [N] 个故事构建 QA 计划。"

如果引用了故事文件路径但文件不存在，将其记为缺失并继续处理剩余的故事。不要因为一个缺失的文件而使整个计划失败。

---

## Phase 2: 加载输入#

对于每个范围内的故事文件，读取完整文件并提取：

- **故事标题**和故事 ID（从文件名或标题）
- **故事类型**字段（如果文件头中存在，例如 `Type: Logic`）
- **验收标准** — 完整的编号/项目符号列表
- **实现文件** — 在"要创建/修改的文件"或类似部分下列出
- **引擎注释** — 任何引擎 API 警告或版本特定注释
- **GDD 引用** — 引用的 GDD 路径
- **ADR 引用** — 引用的 ADR
- **估算** — 小时或故事点数（如果存在）
- **依赖关系** — 此故事依赖的其他故事

读取故事后，一次加载支持上下文（不是每个故事）：

- `design/gdd/systems-index.md` — 了解系统优先级和哪些 GDD 已批准
- 对于所有在故事中唯一引用的 GDD：仅读取**验收标准**和**公式**部分。不要加载完整的 GDD 文本 — 这两个部分包含可测试的需求和要验证的数学。
- `docs/architecture/control-manifest.md` — 扫描自动化测试应该防范的禁止模式（如果文件存在）

如果故事中没有引用 GDD，将其记为差距但不要阻止计划。故事将仅使用验收标准进行分类。

---

## Phase 3: 分类每个故事#

对于每个故事，分配故事类型。如果故事的头中已经有一个 `Type:` 字段，使用其值并根据下面的标准验证它。如果该字段缺失或模糊，从验收标准推断类型。

| 故事类型 | 分类指示器 |
|---|---|
| **逻辑** | 验收标准引用计算、公式、数字阈值、状态转换、AI 决策、数据验证、增益/减益堆叠、经济交易，或任何可测试的计算 |
| **集成** | 标准涉及两个或更多系统交互、跨系统边界传播的信号或事件、保存/加载往返、网络同步或持久性 |
| **视觉/感觉** | 标准引用动画行为、VFX、着色器输出、"感觉响应"、"感知时序"、屏幕震动、粒子效果、音频同步或视觉反馈质量 |
| **UI** | 标准引用菜单、HUD 元素、按钮、屏幕、对话、库存面板、工具提示或任何面向玩家的界面元素 |
| **配置/数据** | 更改仅限于平衡调优值、数据文件或配置 — 不涉及新代码逻辑 |

**混合故事**（例如，同时添加公式和 UI 显示的故事）：
基于哪些验收标准带来最高实现风险分配主要类型，并注意次要类型。逻辑+集成或视觉+UI 组合是最常见的。

分类所有故事后，在继续 Phase 4 之前，在对话中生成分类摘要表。这让用户看到测试将如何分配。

---

## Phase 4: 生成测试计划#

组装完整的 QA 计划文档。使用此结构：

```markdown
# QA 计划：[冲刺/功能名称]

**日期**：[日期]
**生成者**：/qa-plan
**范围**：[N 个故事，跨越 N 个系统]
**引擎**：[来自 .claude/docs/technical-preferences.md 的引擎名称，或"未配置"]

---

## 测试摘要#

| 故事 | 类型 | 需要自动化测试 | 需要手动验证 |
|-------|------|------------------------|------------------------------|
| [故事标题] | 逻辑 | 单元测试 — `tests/unit/[system]/` | 无 |
| [故事标题] | 集成 | 集成测试 — `tests/integration/[system]/` | 冒烟检查 |
| [故事标题] | 视觉/感觉 | 无（不可自动化） | 屏幕截图 + 负责人签署 |
| [故事标题] | UI | 交互演练 | 手动逐步检查 |
| [故事标题] | 配置/数据 | 数据验证测试 | 游戏中值抽查 |

## 自动化测试必需#

### [故事标题] — [类型]

**测试文件路径**：`tests/[unit|integration]/[system]/[story-slug]_test.[ext]`

**要测试什么**：
- [来自 GDD 公式部分的特定公式或规则]
- [每个命名的状态转换或决策分支]
- [应该或不应该发生的每个副作用]

**要覆盖的边缘情况**：
- 零/最小输入值（例如，0 伤害，空库存）
- 最大/边界输入值（例如，最大等级，状态上限）
- 无效或空输入（例如，缺失目标，死亡实体）
- [GDD 边缘情况部分中明确调用的任何边缘情况]

**估算的测试计数**：~[N] 个单元测试

[如果未找到此故事的 GDD 公式引用：]
*未在引用的 GDD 中找到公式 — 测试案例必须直接从验收标准派生。在编写测试之前审查 GDD 公式部分。*

## 手动 QA 检查清单#

### [故事标题] — [类型]

**验证方法**：[屏幕截图 + 设计师签署 | 试玩会话 | 手动逐步检查 | 与参考镜头比较]

**谁必须签署**：[设计师 / 主程序员 / QA 负责人 / 美术负责人]

**要捕获的证据**：[屏幕截图 X | 视频剪辑 Y | 书面试玩笔记 | 并排比较]

检查清单：
- [ ] [具体的可观察条件 — 具体且可证伪]
- [ ] [另一个条件]
- [ ] [每个验收标准转换为手动检查项]

*如果任何标准使用主观语言（"感觉"、"看起来"、"似乎"），必须补充具体的基准或试玩协议。*

---

## 冒烟测试范围#

冲刺 QA 移交之前要验证的关键路径：

1. 游戏启动到主菜单无崩溃
2. 可以开始新游戏 / 新会话
3. [此冲刺引入或更改的主要机制]
4. [此冲刺的更改有回归风险的任何系统]
5. 保存 / 加载循环完成无数据丢失（如果存在保存系统）
6. 目标硬件上的性能在预算内（无新帧峰值）

*冒烟测试由开发者使用 `/smoke-check` 验证。运行该技能时引用此列表。*

---

## 试玩要求#

| 故事 | 试玩目标 | 最小时长 | 目标玩家类型 |
|-------|--------------|--------------|-------------------|
| [故事] | [此会话必须回答什么问题？] | [N] | [新玩家 / 有经验的] |

**签署要求**：试玩笔记必须写入 `production/session-logs/playtest-[sprint]-[story-slug].md`，并且故事可以标记为完成之前，必须由 [设计师 / QA 负责人] 审查。

[如果没有故事需要试玩验证：]
*此冲刺不需要试玩会话。*

---

## 完成定义 — 此冲刺#

当 ALL 以下条件为真时，故事是**完成**的：

- [ ] 所有验收标准已验证 — 通过自动化测试结果 OR 记录的手动证据（屏幕截图、视频或带有签署的试玩笔记）
- [ ] 测试文件存在于所有逻辑和集成故事的指名路径
- [ ] 所有视觉/感觉和 UI 故事的手动证据文档存在
- [ ] 冒烟检查通过（在 QA 移交之前运行 `/smoke-check sprint`）
- [ ] 无回归引入
- [ ] 代码已审查（通过 `/code-review` 或记录的同级审查）
- [ ] 故事文件已更新为 `状态：完成`（通过 `/story-done`）
```

生成内容时，使用 Phase 2 中提取的实际故事标题、GDD 公式文本和验收标准。不要使用占位符文本 — 每个测试条目应该反映这些特定故事的真实需求。

---

## Phase 5: 编写输出#

在对话中展示完整计划（或如果计划非常长，展示摘要），然后询问：

"我可以将此 QA 计划写入 `production/qa/qa-plan-[sprint-slug]-[date].md` 吗？"

完全像生成的那样写入计划 — 不要截断。

写入后：

"QA 计划已写入 `production/qa/qa-plan-[sprint-slug]-[date].md`。"

下一步：
- 在冲刺实施开始之前，与团队分享此计划
- 在所有故事实施完后运行 `/smoke-check sprint` 以门控 QA 移交
- 对于逻辑/集成故事，在标记故事完成之前 — `/story-done` 检查它们（`/smoke-check` 作为门控）

---

## 协作协议#

- **没有询问绝对不要写入计划** — Phase 5 需要明确批准。
- **保守分类**：当故事在逻辑和集成之间模糊时，将其分类为集成 — 它需要单元和集成测试。
- **不要发明测试用例**超出验收标准和 GDD 公式支持。如果 GDD 中缺少公式，标记它而不是猜测。
- **试玩要求是咨询性的**：用户决定是否值得为边界视觉/感觉故事进行试玩。标记案例；不要强制。
- 如果未提供参数，使用 `AskUserQuestion` 进行范围选择。
- 保持所有其他阶段非交互式 — 展示发现，然后询问一次以批准写入。
