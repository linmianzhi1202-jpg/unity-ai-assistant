# 创建架构技能

## 技能概述

此技能生成 `docs/architecture/architecture.md` — 主架构文档，将所有已批准的 GDD 转换为具体技术蓝图。它位于设计和实现之间，必须在 Sprint 规划开始前存在。

**与 `/architecture-decision` 的区别**：ADR 记录单个决策点。此技能创建整个系统蓝图，为 ADR 提供上下文。

在运行前解析审查模式（一次，为此运行的所有网关生成存储）：
1. 如果传递了 `--review [full|lean|solo]` → 使用那个值
2. 否则读取 `production/review-mode.txt` → 使用那个值
3. 否则 → 默认 `lean`

参阅 `.claude/docs/director-gates.md` 了解完整检查模式。

**参数模式：**
- **无参数 / `full`**：完整引导演练 — 所有部分，从头到尾
- **`layers`**：仅关注系统层图表
- **`data-flow`**：仅关注模块间数据流
- **`api-boundaries`**：仅关注 API 边界定义
- **`adr-audit`**：仅审计现有 ADR 的引擎兼容性差距

---

## 阶段 0：加载所有上下文

在做任何其他事情之前，按此顺序加载完整项目上下文：

### 0a. 引擎上下文（关键）

完整读取引擎参考库：

1. `docs/engine-reference/[engine]/VERSION.md`
   → 提取：引擎名称、版本、LLM 截止日期、截止后风险级别
2. `docs/engine-reference/[engine]/breaking-changes.md`
   → 提取：所有 HIGH 和 MEDIUM 风险变更
3. `docs/engine-reference/[engine]/deprecated-apis.md`
   → 提取：要避免的 API
4. `docs/engine-reference/[engine]/current-best-practices.md`
   → 提取：与训练数据不同的、截止后最佳实践
5. `docs/engine-reference/[engine]/modules/` 中的所有文件
   → 提取：每个域的当前 API 模式

如果没有配置引擎，停止并提示：
> "没有配置引擎。首先运行 `/setup-engine`。在知道目标引擎和版本之前，无法编写架构。"

### 0b. 设计上下文 + 技术需求提取

读取所有已批准的设计文档，并从每个文档中提取技术需求：

1. `design/gdd/game-concept.md` — 游戏支柱、类型、核心循环
2. `design/gdd/systems-index.md` — 所有系统、依赖关系、优先级层级
3. `.claude/docs/technical-preferences.md` — 命名约定、性能预算、允许的库、禁止模式
4. `design/gdd/` 中的**每个 GDD** — 对于每个，提取技术需求：
   - 游戏规则隐含的数据结构
   - 所述或隐含的性能约束
   - 系统所需的引擎功能
   - 跨系统通信模式（什么与什么对话，如何对话）
   - 必须持久化的状态（保存/加载影响）
   - 线程或时序需求

构建**技术需求基线** — 从所有 GDD 提取的、编号的平面需求列表，格式为 `TR-[gdd-slug]-[NNN]`。这是架构必须覆盖的完整集合。将其展示为：

```
## 技术需求基线
从 [N] 个 GDD 提取 | [X] 个总需求数

| 需求 ID | GDD | 系统 | 需求 | 域 |
|--------|-----|--------|-------------|--------|
| TR-combat-001 | combat.md | Combat | 每帧命中框检测 | Physics |
| TR-combat-002 | combat.md | Combat | 连击状态机 | Core |
| TR-inventory-001 | inventory.md | Inventory | 物品持久化 | Save/Load |
```

此基线输入到后续每个阶段。在本次会议结束前，不应让 GDD 需求没有架构决策来支持它。

### 0c. 现有架构决策

读取 `docs/architecture/` 中的所有文件以了解已决定的内容。列出找到的任何 ADR 及其域。

### 0d. 生成知识差距清单

在继续之前，展示结构化摘要：

```
## 引擎知识差距清单
引擎：[名称 + 版本]
LLM 训练覆盖：大约至 [版本]
截止后版本：[列表]

### HIGH RISK 域（在继续之前必须根据引擎参考验证）
- [域]：[关键变更]

### MEDIUM RISK 域（验证关键 API）
- [域]：[关键变更]

### LOW RISK 域（在训练数据中，可能可靠）
- [域]：[无显著截止后变更]

### GDD 中触及 HIGH/MEDIUM 风险域的系统：
- [GDD 系统名称] → [域] → [风险级别]
```

询问："此清单识别出 [N] 个系统处于 HIGH RISK 引擎域。是否继续构建架构并在整个过程中标记这些警告？"

## 阶段 1：系统层映射

将 `systems-index.md` 中的每个系统映射到一个架构层。标准游戏架构层为：

```
┌─────────────────────────────────────┐
│  PRESENTATION LAYER                         │  ← UI、HUD、菜单、VFX、音频
├─────────────────────────────────────┤
│  FEATURE LAYER                              │  ← 游戏性系统、AI、任务
├─────────────────────────────────────┤
│  CORE LAYER                                 │  ← 物理、输入、战斗、移动
├─────────────────────────────────────┤
│  FOUNDATION LAYER                           │  ← 引擎集成、保存/加载、
│                                             │    场景管理、事件总线
├─────────────────────────────────────┤
│  PLATFORM LAYER                             │  ← 操作系统、硬件、引擎 API 表面
└─────────────────────────────────────┘
```

对于每个 GDD 系统，询问：
- 它属于哪个层？
- 它的模块边界是什么？
- 它独占什么（数据、状态、行为）？

展示提议的层分配，并在继续下一部分之前请求批准。立即将批准的层映射写入骨架文件。

**引擎感知检查**：对于分配到 Core 和 Foundation 层的每个系统，标记它是否触及 HIGH 或 MEDIUM 风险引擎域。内联显示相关引擎参考摘录。

---

## 阶段 2：模块所有权映射

为阶段 1 中定义的每个模块定义所有权：

- **拥有**：此模块单独负责的数据和状态
- **暴露**：其他模块可以读取或调用的内容
- **消耗**：它从其他模块读取的内容
- **使用的引擎 API**：此模块直接调用的特定引擎类/节点/信号（带有版本和风险级别注释）

按层格式化为表格，然后格式化为 ASCII 依赖关系图。

**引擎感知检查**：对于每个列出的引擎 API，根据相关模块参考文档进行验证。如果 API 是截止后的，标记它：

```
⚠️  [ClassName.method()] — Godot 4.6（截止后，HIGH 风险）
    根据验证：docs/engine-reference/godot/modules/[domain].md
    行为已确认：[是 / 需要验证]
```

在写入之前获取用户对所有权映射的批准。

---

## 阶段 3：数据流

定义关键游戏场景期间数据如何在模块之间移动。至少涵盖：

1. **帧更新路径**：输入 → 核心系统 → 状态 → 渲染
2. **事件/信号路径**：系统如何在不紧密耦合的情况下通信
3. **保存/加载路径**：什么状态被序列化，哪个模块拥有序列化
4. **初始化顺序**：哪些模块必须在其他模块之前启动

在有帮助的地方使用 ASCII 序列图。对于每个数据流：
- 命名正在传输的数据
- 识别生产者和消费者
- 声明这是同步调用、信号/事件还是共享状态
- 标记任何跨越线程边界的数据流

在写入之前获取用户对每个场景的批准。

---

## 阶段 4：API 边界

定义模块之间的公共契约。对于每个边界：

- 模块暴露给系统其余部分的接口是什么？
- 入口点（函数/信号/属性）是什么？
- 调用者必须遵守什么不变量？
- 模块必须向调用者保证什么？

用伪代码或项目的实际语言（来自技术偏好）编写。这些成为程序员针对实现的契约。

**引擎感知检查**：如果任何接口使用引擎特定类型（例如，Godot 中的 `Node`、`Resource`、`Signal`），标记版本并验证类型存在且在目标引擎版本中没有更改签名。

---

## 阶段 5：ADR 审计 + 可追溯性检查

根据阶段 1-4 构建的架构和阶段 0b 中的技术需求基线，审查所有现有 ADR：

### ADR 质量检查

对于每个 ADR：
- [ ] 是否有引擎兼容性部分？
- [ ] 是否记录了引擎版本？
- [ ] 是否标记了截止后 API？
- [ ] 是否有"GDD 需求覆盖"部分？
- [ ] 它是否与本次会议中的层/所有权决策冲突？
- [ ] 它对固定引擎版本是否有效？

| ADR | 引擎兼容性 | 版本 | GDD 链接 | 冲突 | 有效 |
|-----|--------------|---------|-------------|-----------|-------|
| ADR-0001: [标题] | ✅/❌ | ✅/❌ | ✅/❌ | 无/[冲突] | ✅/⚠️ |

### 可追溯性覆盖检查

将技术需求基线中的每个需求映射到现有 ADR。对于每个需求，检查任何 ADR 的"GDD 需求覆盖"部分或决策文本是否覆盖它：

| 需求 ID | 需求 | ADR 覆盖 | 状态 |
|--------|-------------|--------------|--------|
| TR-combat-001 | 每帧命中框检测 | ADR-0003 | ✅ |
| TR-combat-002 | 连击状态机 | — | ❌ 差距 |

计数：X 覆盖，Y 差距。对于每个差距，它成为**必需的新的 ADR**。

### 必需的新的 ADR

列出在此架构会议期间（阶段 1-4）做出的、尚未有相应 ADR 的所有决策，再加上所有未覆盖的技术需求。按层分组 — Foundation 优先：

**Foundation 层（在编码开始之前必须创建）：**
- `/architecture-decision [标题]` → 覆盖：TR-[id], TR-[id]

**Core 层：**
- `/architecture-decision [标题]` → 覆盖：TR-[id]

## 阶段 6：缺失的 ADR 列表

基于完整架构，生成应该存在但尚未存在的 ADR 的完整列表。按优先级分组：

**编码开始之前必须有（Foundation & Core 决策）：**
- [例如"场景管理和场景加载策略"]
- [例如"事件总线 vs 直接信号架构"]

**在相关系统构建之前应该有（Should have before the relevant system is built）：**
- [例如"清单序列化格式"]

**可以推迟到实现（Can defer to implementation）：**
- [例如"水的具体着色器技术"]

## 阶段 7：编写主架构文档

所有部分获得批准后，将完整文档写入 `docs/architecture/architecture.md`：

询问："我可以将主架构文档写入 `docs/architecture/architecture.md` 吗？"

文档结构：

```markdown
# [游戏名称] — 主架构

## 文档状态
- 版本：[N]
- 最后更新：[日期]
- 引擎：[名称 + 版本]
- 覆盖的 GDD：[列表]
- 引用的 ADR：[列表]

## 引擎知识差距摘要
[从阶段 0d 清单精简 — HIGH/MEDIUM 风险域及其影响]

## 系统层映射
[来自阶段 1]

## 模块所有权
[来自阶段 2]

## 数据流
[来自阶段 3]

## API 边界
[来自阶段 4]

## ADR 审计
[来自阶段 5]

## 必需的 ADR
[来自阶段 6]

## 架构原则
[3-5 个关键原则，管理此项目的所有技术决策，
派生自游戏概念、GDD 和技术偏好]

## 开放问题
[推迟的决策 — 在相关层构建之前必须解决]
```

## 阶段 7b：技术总监签署 + 主程序员可行性审查

编写主架构文档后，在移交之前执行显式签署。

**步骤 1 — 技术总监自我审查**（此技能作为 technical-director 运行）：

应用网关 **TD-ARCHITECTURE**（`.claude/docs/director-gates.md`）作为自我审查。根据该网关定义的所有四个标准检查完整文档。

**审查模式检查** — 在生成 LP-FEASIBILITY 之前应用：
- `solo` → 跳过。注意："LP-FEASIBILITY 跳过 — 单独模式。" 继续阶段 8 移交。
- `lean` → 跳过（不是 PHASE-GATE）。注意："LP-FEASIBILITY 跳过 — Lean 模式。" 继续阶段 8 移交。
- `full` → 正常生成。

**步骤 2 — 通过 Task 使用网关 LP-FEASIBILITY（`.claude/docs/director-gates.md`）生成 `lead-programmer`：**

传递：架构文档路径、技术需求基线摘要、ADR 列表。

**步骤 3 — 向用户展示两个评估：**

并排展示技术总监评估和主程序员裁决。

使用询问用户 — "技术总监和主程序员已审查架构。您希望如何继续？"
选项：`接受 — 继续移交` / `修订标记的条目优先` / `讨论特定问题`

**步骤 4 — 在架构文档中记录签署：**

更新文档状态部分：
```
- 技术总监签署：[日期] — 批准 / 有条件批准
- 主程序员可行性：可行 / 接受关切 / 已修订
```

询问："我可以在 `docs/architecture/architecture.md` 中更新文档状态部分并签署吗？"

## 阶段 8：移交

编写文档后，提供清晰的移交：

1. **接下来首先运行这些 ADR**（来自阶段 6，优先级排序）：列出前 3 个
2. **网关检查**："主架构文档已完成。在编写所需的 ADR 时，所有必需的 ADR 都写入后，运行 `/gate-check pre-production`。"
3. **更新会话状态**：将摘要写入 `production/session-state/active.md`

## 协作协议

此技能在每个阶段都遵循协作设计原则：

1. **静默加载上下文** — 不要叙述文件读取
2. **展示发现** — 展示知识差距清单和层提议
3. **在决策之前询问** — 为每个架构选择展示选项
4. **在写入之前获取批准** — 每个部分仅在用户批准内容后才写入
5. **增量写入** — 立即写入每个批准的部分；不要积累所有内容并在最后写入。这会在会话崩溃中幸存。

不要在没有用户输入的情况下做出约束性架构决策。如果用户不确定，在要求他们决定之前，展示 2-4 个选项及利弊。

## 推荐后续步骤

- 为阶段 6 中列出的每个必需 ADR 运行 `/architecture-decision [标题]` — Foundation 层 ADR 优先
- 所需的 ADR 写入后，运行 `/create-control-manifest` 以生成层规则清单
- 所有必需的 ADR 写入并架构签署后，运行 `/gate-check pre-production`
