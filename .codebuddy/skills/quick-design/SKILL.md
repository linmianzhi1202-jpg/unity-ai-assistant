# 快速设计技能#

## 技能概述#

轻量级设计文档，快速捕捉想法。此技能提供结构化的快速设计工作流程，包括分类更改、上下文扫描、起草快速设计规格、批准和归档、移交。

**何时运行**：每当更改对 `/design-system` 来说太小，但如果没有书面理由就实施得too meaningful 时。

## 使用方式#

- 通过 Agent 触发：当用户说「快速设计」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill quick-design [更改描述]`

---

## 1. 分类更改#

首先，读取参数并确定此更改属于哪个类别：

- **调优** — 更改现有系统中的数字或平衡值，无行为更改（最最小路径）。示例："将跳跃高度从 5 增加到 6 单位"、"将敌人巡逻速度降低 10%"。
- **微调** — 对现有系统进行小的行为更改，不引入新状态、分支或系统。示例："使 dash 在第 1 帧无敌"、"允许连击取消翻滚"。
- **新增** — 向现有系统添加小机制，可能引入 1-2 个新状态或交互。示例："向格挡机制添加招架窗口"、"向基础攻击添加蓄力变体"。
- **新小系统** — 独立功能足够小，没有 GDD 且实施工作量约为一周。示例："成就弹出系统"、"简单的昼夜视觉循环"。

如果更改**不符合**这些类别 — 它引入了具有重大跨系统依赖关系的新系统、需要超过一周的实施工作，或从根本上改变了现有系统的核心规则 — 停止并重定向到 `/design-system`。

向用户展示分类并在继续之前确认它是正确的。如果没有参数，询问用户描述更改。

---

## 2. 上下文扫描#

在起草任何内容之前，读取相关上下文：

- 搜索 `design/gdd/` 以获取与此更改最相关的 GDD。读取此更改会影响的部分。
- 检查 `design/gdd/systems-index.md` 是否存在。如果存在，读取它以了解此系统在依赖关系图中的位置以及它属于哪个层。如果不存在，注意"未找到系统索引 — 跳过依赖关系层检查。"并继续。
- 检查 `design/quick-specs/` 以获取任何先前触及此系统的快速规格 — 避免与它们矛盾。
- 如果这是调优更改，还要检查 `assets/data/` 以获取保存相关值的数据文件。

报告找到了什么："在 [路径] 找到 GDD。相关部分：[部分名称]。未找到冲突的快速规格。"（或注意找到的任何冲突。）

## 3. 起草快速设计规格#

使用适当的规格格式用于更改类别。

### 对于调优更改#

生成单个表格：

```markdown
# 快速设计规格：[标题]

**类型**：调优
**系统**：[系统名称]
**GDD 引用**：`design/gdd/[filename].md` — 调优参数部分
**日期**：[今天]

## 更改#

| 参数 | 旧值 | 新值 | 理由 |
|-----------|-----------|-----------|----------|
| [参数]   | [旧值]     | [新值]     | [为什么]     |

## 调优参数映射#

映射到 GDD 调优参数： [参数名称和其记录的范围]。
新值 [在 / 在边缘 / 超出] 记录的范围。
[如果超出：解释为什么应该扩展范围。]

## 验收标准#

- [ ] [参数] 从 `assets/data/[file]` 读取 [新值]
- [ ] 在 [特定上下文] 中可观察行为差异
- [ ] 无回归 [相关行为]
```

### 对于微调和新增更改#

```markdown
# 快速设计规格：[标题]

**类型**：[微调 / 新增]
**系统**：[系统名称]
**GDD 引用**：`design/gdd/[filename].md`
**日期**：[今天]

## 更改摘要#

[1-2 句话描述更改内容和原因。]
[为什么需要此更改？它解决了什么玩家体验问题？]
[如果适用，参考相关的 MDA 美学或玩家反馈。]

## 设计增量#

当前 GDD 说（引用 `design/gdd/[filename].md`，[部分]）：
> [相关规则或描述的精确引用]

此规格将其更改为：
> [新规则或描述，以与 GDD 详细规则部分相同的精度编写。程序员应该能够从此文本单独实施。]

## 新规则 / 值#

[替换内容的完整明确语句。如果这引入了新状态，列出它们。如果引入了新参数，定义它们的范围。]

## 受影响的系统#

| 系统 | 影响 | 所需操作 |
|--------|--------|-----------------|
| [系统] | [它如何受影响] | [更新 GDD / 更新数据文件 / 无操作] |

## 验收标准#

- [ ] [特定、可测试的准则 1]
- [ ] [特定、可测试的准则 2]
- [ ] [特定、可测试的准则 3]
- [ ] 无回归：[此更改不得中断的原始行为]

## GDD 更新必需？#

[是 / 否]
[如果是：哪个文件、哪个部分，以及更新应该说什么。]
```

### 对于新小系统更改#

使用精简的 GDD 结构。仅包括直接必要的部分 — 跳过玩家幻想、完整公式和边缘情况，除非系统特别需要它们。

```markdown
# 快速设计规格：[标题]

**类型**：新小系统
**范围**：[1-2 句描述此系统做什么和不做什么]
**日期**：[今天]
**估计实施**：[小时]

## 概述#

[新团队成员能够理解的段落。此系统做什么，它何时激活，以及它产生什么？]

## 核心规则#

[系统的明确规则。对顺序行为使用编号列表，对条件使用项目符号列表。足够精确，程序员可以在不询问问题的情况下实施。]

## 调优参数#

| 参数 | 默认值 | 范围 | 类别 | 理由 |
|------|---------|-------|----------|----------|
| [名称] | [值] | [最小–最大] | [感觉/曲线/门控] | [为什么此默认值] |

所有值必须存在于 `assets/data/[appropriate-file].json` 中，而不是硬编码。

## 验收标准#

- [ ] [功能准则：做正确的事]
- [ ] [功能准则：处理边缘情况]
- [ ] [体验准则：感觉正确 — 试玩验证什么]
- [ ] [回归准则：不中断相邻系统]

## 系统索引#

此系统当前不在 `design/gdd/systems-index.md` 中。
[如果应该添加：建议哪个层和优先级。]
[如果太小而无法跟踪：注意"此系统低于系统索引跟踪阈值 — 快速规格足够。"]
```

## 4. 批准和归档#

在对话中展示完整计划（或如果计划非常长，则展示摘要），然后询问：

"我可以将此快速设计规格写入 `design/quick-specs/[kebab-case-title]-[YYYY-MM-DD].md` 吗？"

使用今天的日期在文件名中。标题应该是更改的 kebab-case 描述（例如，`jump-height-tuning-2026-03-10`、`parry-window-addition-2026-03-10`。）

如果可以，创建 `design/quick-specs/` 目录（如果不存在），然后写入文件。

如果需要 GDD 更新（在规格中标记），在写入快速规格后单独询问：
"此规格修改 [系统名称]。我可以更新 `design/gdd/[filename].md` — 特别是 [部分名称] 部分吗？"

在询问之前显示将更改的确切文本（旧 vs. 新）。不要在没有明确批准的情况下进行 GDD 编辑。

---

## 5. 移交#

写入文件后，输出：

```
快速设计规格写入至：design/quick-specs/[filename].md
类型：[调优 / 微调 / 新增 / 新小系统]
系统：[系统名称]
GDD 更新：[必需 — 待批准 / 已应用 / 不需要]
下一步：此规格在实施前已准备好用于 `/story-readiness` 验证。
在故事 GDD 引用字段中引用此规格。
```

### 流程注释#

结论：**完成** — 快速设计规格已写入并准备好实施。

快速设计规格**绕过** `/design-review` 和 `/review-all-gdds` 设计。它们用于小的、低风险、范围明确的更改，其中审查流程的成本超过更改本身的风险。

如果任何以下内容为真，重定向到完整流程：
- 更改添加了属于系统索引的新系统
- 更改显著改变了跨系统行为或系统之间的契约
- 更改引入了影响游戏 MDA 美学平衡的新玩家面向机制
- 实施可能超过一周的工作

在这些情况下："此更改已超出快速规格范围。我建议使用 `/design-system` 为此编写完整的 GDD。"

---

## 推荐下一步#

- 在实施开始前运行 `/story-readiness [story-path]` 以验证故事 — 在故事 GDD 引用字段中引用此规格
- 实施后运行 `/dev-story [story-path]` 以实施
- 如果更改大于预期，运行 `/design-system [system-name]` 以改为编写完整的 GDD
