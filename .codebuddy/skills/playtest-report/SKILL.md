# 试玩报告技能

## 技能概述

分析玩家反馈，提取可操作见解，生成结构化试玩报告。

## 使用方式

- 通过 Agent 触发：当用户说「试玩报告」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：```/skill playtest-report [参数]```

## 工作流

### 阶段 1：解析参数

解析审查模式（一次性，为本次运行中的所有门控生成存储）：
1. 如果传递了 `--review [full|lean|solo]` → 使用其值
2. 否则读取 `production/review-mode.txt` → 使用其值
3. 否则 → 默认为 `lean`

确定模式：

- `new` → 生成空白试玩报告模板
- `analyze [path]` → 读取原始笔记并用结构化发现填充模板

---

### 阶段 2A：新模板模式

生成此模板并输出给用户：

```markdown
# 试玩报告

## 会话信息

- **日期**：[日期]
- **构建**：[版本/提交]
- **持续时间**：[游戏时间]
- **测试者**：[姓名/ID]
- **平台**：[PC/主机/移动端]
- **输入方式**：[键盘+鼠标 / 手柄 / 触摸]
- **会话类型**：[首次 / 回访 / 定向测试]

## 测试焦点

[测试了什么特定功能或流程]

## 第一印象（前 5 分钟）

- **理解目标？** [是/否/部分]
- **理解控制？** [是/否/部分]
- **情绪反应**：[投入/困惑/无聊/沮丧/兴奋]
- **笔记**：[观察]

## 游戏流程

### 哪些工作良好

- [观察 1]

### 痛点

- [问题 1 -- 严重性：高/中/低]

### 困惑点

- [玩家在哪里困惑以及为什么]

### 愉悦时刻

- [让玩家惊讶或高兴什么]

## 遇到的 Bug

| # | 描述 | 严重性 | 可复现 |
|---|-------|--------|---------|

## 功能特定反馈

### [功能 1]

- **理解目的？** [是/否]
- **发现吸引人？** [是/否]
- **建议**：[测试者建议]

## 定量数据（如果可用）

- **死亡次数**：[计数和位置]
- **每个区域时间**：[分解]
- **使用的物品**：[什么和什么时候]
- **发现 vs 错过的功能**：[列表]

## 总体评估

- **会再玩吗？** [是/否/也许]
- **难度**：[太简单 / 刚好 / 太难]
- **节奏**：[太慢 / 好 / 太快]
- **会话长度偏好**：[更短 / 好 / 更长]

## 此会话的前 3 优先级

1. [最重要的发现]
2. [第二优先级]
3. [第三优先级]
```

---

### 阶段 2B：分析模式

读取提供路径的的原始笔记。与设计文档交叉引用。用结构化发现填充上面的模板。标记任何与设计意图冲突的试玩观察。

---

### 阶段 3：操作路由

将所有发现分类为四个桶：

- **需要的设计更改** — 趣味问题、玩家困惑、破坏的机制、与设计文档预期体验冲突的观察
- **平衡调整** — 数字感觉错误、难度太峰值或太平坦
- **Bug 报告** — 可复现的清晰实现缺陷
- **打磨项目** — 不阻止进度，但摩擦或感觉问题供以后使用

展示分类列表，然后路由：

- **设计更改：** "在进行更改之前，对受影响的设计文档运行 `/propagate-design-change [path]` 以找到下游影响。"
- **平衡调整：** "在调整值之前，运行 `/balance-check [system]` 以验证完整平衡图片。"
- **Bug：** "使用 `/bug-report` 正式跟踪这些。"
- **打磨项目：** "当团队到达该阶段时，添加到 `production/` 中的打磨待办事项。"

---

### 阶段 3b：创意主管玩家体验审查

**审查模式检查** — 在生成 CD-PLAYTEST 之前应用：
- `solo` → 跳过。注意："CD-PLAYTEST 已跳过 — 单人模式。" 继续阶段 4（保存报告）。
- `lean` → 跳过（不是阶段门控）。注意："CD-PLAYTEST 已跳过 — 精简模式。" 继续阶段 4（保存报告）。
- `full` → 正常生成。

分类发现后，通过 Task 使用门 **CD-PLAYTEST** (`.claude/docs/director-gates.md`) 生成 `creative-director`。

传递：结构化报告内容、游戏支柱和核心幻想（来自 `design/gdd/game-concept.md`）、正在测试的特定假设。

在保存报告之前展示创意主管的评估。如果 CONCERNS 或 REJECT，在报告中添加 `## Creative Director Assessment` 部分以捕获判定和反馈。如果 APPROVE，在报告中注意批准。

---

### 阶段 4：保存报告

询问："我可以将此试玩报告写入 `production/qa/playtests/playtest-[date]-[tester].md` 吗？"

如果是，写入文件，根据需要创建目录。

---

### 阶段 5：下一步

判定：**COMPLETE** — 试玩报告已生成。

- 首先操作最高优先级的发现类别。
- 处理设计更改后：在更新的 GDD 上重新运行 `/design-review`。
- 修复 Bug 后：重新运行 `/bug-triage` 以更新优先级。
