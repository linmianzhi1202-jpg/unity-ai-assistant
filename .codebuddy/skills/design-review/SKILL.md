# 设计审查技能

## 技能概述

本技能验证游戏设计文档（GDD）的完整性、一致性和可实施性，并产出结构化审查报告。

**与 `/project-stage-detect` 的区别：**
- `/project-stage-detect` 是诊断性的（"我们在哪里？"）。
- 本技能是规范性的（"是否准备好推进？"），带有正式的判定结论。

**审查深度参数：**
- `--depth full`：完整审查 — 所有阶段 + 专家代理委派（阶段 3b）
- `--depth lean`：所有阶段，无专家代理 — 更快，单会话分析
- `--depth solo`：仅阶段 1-4，无委派，无阶段 5 下一步提示 — 从另一个技能内调用时使用

---

## 阶段 0：解析参数

提取 `--depth [full|lean|solo]`（如果存在）。默认值为 `full`（当没有标志时）。

> **注意**：`--depth` 控制*本技能分析文档的彻底程度*（将生成多少专家代理）。它独立于 `production/review-mode.txt` 中的全局审查模式，后者控制总监门控生成。这是两个不同的概念 — `--depth` 是关于*本*技能如何分析文档。

**审查模式解析**（一次性，为此运行中的所有门控生成存储）：
1. 如果传递了 `--review [full|lean|solo]` → 使用那个值
2. 否则读取 `production/review-mode.txt` → 使用那个值
3. 否则 → 默认为 `lean`

参阅 `.claude/docs/director-gates.md` 了解完整检查模式。

---

## 阶段 1：加载文档

读取目标设计文档（完整读取）。读取 CLAUDE.md 以了解项目上下文和标准。读取 `design/gdd/` 中相关的设计文档（如果目标文档引用或暗示了它们）。

**依赖关系图验证：** 对于依赖关系部分中列出的每个系统，使用 search_file 检查其 GDD 文件是否存在于 `design/gdd/`。标记任何还不存在的文件 — 这些是下游作者将会遇到的破坏引用。

**传说/叙事对齐：** 如果 `design/gdd/game-concept.md` 或 `design/narrative/` 中有任何文件，请读取它。注意此 GDD 中的任何机械选择与上述世界规则、基调或设计支柱相矛盾。将此上下文传递给阶段 3b 中的 `game-designer`。

**先前审查检查：** 检查 `design/gdd/reviews/[doc-name]-review-log.md` 是否存在。如果存在，读取最近的条目 — 注意给出了什么判定以及列出了什么阻塞项。此会话是重新审查；跟踪先前的问题是否已解决。

---

## 阶段 2：完整性检查

根据设计文档标准清单进行评估：

- [ ] 有概述部分（一段摘要）
- [ ] 有玩家幻想部分（预期感觉）
- [ ] 有详细规则部分（明确的机制）
- [ ] 有公式部分（所有数学都用变量定义）
- [ ] 有边缘情况部分（处理不寻常情况）
- [ ] 有依赖关系部分（列出其他系统）
- [ ] 有调优旋钮部分（已识别可配置值）
- [ ] 有验收标准部分（可测试的成功条件）

---

## 阶段 3：一致性和可实施性

**内部一致性：**
- 公式产生的值是否与描述的行为匹配？
- 边缘情况是否与主要规则矛盾？
- 依赖关系是否是双向的（其他系统是否知道这一个？）？

**可实施性：**
- 规则是否足够精确，让程序员可以在没有问题的情况下实施？
- 是否有任何"留白"部分细节缺失？
- 是否考虑了性能影响？

**跨系统一致性：**
- 这与任何现有机制有冲突吗？
- 这是否与其他系统创建非预期的交互？
- 这是否与游戏的已确立基调和支柱一致？

---

## 阶段 3b：对抗性专家审查（仅 full 模式）

**在 `lean` 或 `solo` 模式下跳过此阶段。**

**此阶段在 full 模式下是强制性的。** 不要跳过它。

在生成最终判定之前，使用 `.claude/docs/director-gates.md` 中的并行门控协议，将所有四个总监作为**并行子代理**通过 Task 生成：

**并行生成：**

1. **`creative-director`** — 门控 **CD-PHASE-GATE**（`.claude/docs/director-gates.md`）
2. **`technical-director`** — 门控 **TD-PHASE-GATE**（`.claude/docs/director-gates.md`）
3. **`producer`** — 门控 **PR-PHASE-GATE**（`.claude/docs/director-gates.md`）
4. **`art-director`** — 门控 **AD-PHASE-GATE**（`.claude/docs/director-gates.md`）

向每个传递：目标阶段名称、当前完成百分比、阻塞的故事计数、来自冲刺报告（如果可用）的速度数据、候选列表。

同时发出所有四个 Task 调用 — 在启动下一个之前不要等待一个。

**收集合四个响应**，然后在最终判定中呈现**总监面板摘要**：

```
## 总监面板评估

创意总监：[READY / CONCERNS / NOT READY]
  [反馈]

技术总监：[READY / CONCERNS / NOT READY]
  [反馈]

制作人：           [READY / CONCERNS / NOT READY]
  [反馈]

艺术总监：       [READY / CONCERNS / NOT READY]
  [反馈]
```

**应用到判定：**
- 任何总监返回 NOT READY → 判定至小为 FAIL（用户可以显式确认覆盖）
- 任何总监返回 CONCERNS → 判定至小为 CONCERNS
- 所有四个 READY → 有资格获得 PASS（仍受第 3 阶段中文档和质量检查约束）

---

## 阶段 4：输出判定

```markdown
## 审查：[目标文档名称]

**日期**：[日期]
**审查者**：design-review 技能
**审查深度**：[full|lean|solo]

### 完整性：[X/Y 个部分存在]
- [x] 概述部分存在，2.4KB
- [ ] 公式部分缺失
- [x] 验收标准存在，3 个条件

### 质量检查：[X/Y 通过]
- [x] GDD 有 8/8 个必需部分
- [ ] 测试 — 失败（tests/unit/ 中有 3 个失败）
- [?] 核心循环已进行试玩测试 — 需要手动检查

### 阻塞项
1. **无架构决策记录** — 在进入生产之前运行 `/architecture-decision` 创建一个涵盖核心系统架构
2. **3 个测试失败** — 在前进之前修复 tests/unit/ 中的失败测试

### 建议
- [解决阻塞项的优先操作]
- [可选改进，不阻塞]

### 判定：[PASS / CONCERNS / FAIL]
- **PASS**：所有必需制品存在，所有质量检查通过
- **CONCERNS**：存在次要缺口，但可以在下一阶段解决
- **FAIL**：必须解决关键阻塞项才能前进
```

---

## 阶段 4b：验证链

在阶段 4 中起草判定后，在最终确定之前挑战它。

**第 1 步 — 生成 5 个挑战问题**，旨在反驳判定：

对于 **PASS** 草案：
- "我通过实际读取文件验证了哪些质量检查，而不是推断它们通过了？"
- "我是否将需要用户确认的手动检查项标记为 PASS？"
- "我是否确认所有列出的制品都有真实内容，而不仅仅是空标头？"
- "我是否忽略了可能阻止阶段成功的任何阻塞项？"
- "我最不自信的检查是哪个，为什么？"

对于 **CONCERNS** 草案：
- "考虑到项目的当前状态，任何列出的 CONCERN 是否可以提升为阻塞项？"
- "此疑虑是否可以解决在下一阶段内，还是会随着时间的推移而复合？"
- "我是否将任何 FAIL 条件淡化为 CONCERN 以避免更难的判定？"
- "是否有我没有检查的可能揭示其他阻塞项的制品？"
- "所有 CONCERNS 一起是否会创建一个阻塞问题，即使每个单独来看都是次要的？"

对于 **FAIL** 草案：
- "我是否准准分离了硬阻塞项和强建议？"
- "是否有任何 PASS 项目我过于宽松？"
- "我是否遗漏了用户应该知道的任何其他阻塞项？"
- "我能否提供一条通往 PASS 的最小路径 — 必须更改的 3 个具体事项？"
- "失败条件是可解决的，还是表明更深层次的设计问题？"

**第 2 步 — 独立回答每个问题。**
不要引用草案判定文本 — 重新检查特定文件或询问用户。

**第 3 步 — 如果需要则修订：**
- 如果任何回答揭示了错过的阻塞项 → 升级判定（PASS→CONCERNS 或 CONCERNS→FAIL）
- 如果任何回答揭示了过度陈述的阻塞项 → 仅在使用特定证据时降级
- 如果回答一致 → 确认判定不变

**第 4 步 — 在最终报告输出中注意验证**：
`验证链：[N] 个问题已检查 — 判定 [不变 | 从 X 修订为 Y]`

---

## 阶段 5：保存审查

向用户呈现审查结果。

询问："我可以将此写入 `design/gdd/reviews/[doc-name]-review.md` 吗？"

如果"是"，写入文件，如果需要则创建目录。判定：如果获得批准，**COMPLETE** — 审查报告已保存。
如果"否"，在此停止。判定：**BLOCKED** — 用户拒绝写入。

---

## 阶段 6：下一步

- 如果判定为 PASS：建议接下来的步骤
- 如果判定为 CONCERNS：列出建议的改进
- 如果判定为 FAIL：标记必须解决才能前进的阻塞项

**推荐工作流程：**

```
/design-review [文件路径]            # 审查特定 GDD
/design-review all                 # 审查所有 GDD（批量）
/review-all-gdds                      # 跨 GDD 一致性检查
/gate-check [阶段]                 # 为特定阶段运行门控检查
```

---

## 协作协议

本技能遵循协作设计原则：

1. **首先扫描** — 检查所有制品和质量门控
2. **询问未知事项** — 不要为您无法验证的事项假设 PASS
3. **呈现发现** — 显示带状态的完整检查清单
4. **用户决定** — 判定是建议性的 — 用户做出最终决定
5. **获得批准** — "我可以将此审查报告写入 design/gdd/reviews/ 吗？"

**永远不要**阻止用户前进 — 判定是建议性的。记录风险并让用户决定尽管有顾虑仍继续。
