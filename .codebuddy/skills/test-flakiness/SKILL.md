# 测试抖动技能#

## 技能概述#

检测不稳定测试，分析失败模式。不稳定测试是有时通过、有时失败而没有任何代码更改的测试。此技能识别它们，解释可能的原因，并建议是隔离还是修复每个测试。

**适用场景**：
- 打磨阶段（测试已运行多次；统计信号可靠）
- 当开发者开始将 CI 失败视为"可能是不稳定的"时
- 在 `/regression-suite` 识别需要诊断的已隔离测试后

**输出**：更新的 `tests/regression-suite.md` 隔离部分 + 可选的 `production/qa/flakiness-report-[date].md`

## 使用方式#

- 通过 Agent 触发：当用户说「测试抖动」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill test-flakiness [参数]`

**参数模式**：
- `/test-flakiness [ci-log-path]` — 分析特定的 CI 运行日志文件
- `/test-flakiness scan` — 扫描 `.github/` 或标准日志输出目录中的所有可用 CI 日志
- `/test-flakiness registry` — 读取现有的 regression-suite.md 隔离部分，并为已已知的不稳定测试提供修复指导
- 无参数 — 自动检测：如果可访问 CI 日志则运行 `scan`，否则运行 `registry`

## 阶段 0: 解析参数#

**参数**: `$ARGUMENTS[0]` (空白 = 智能默认）

从参数确定模式：

| 参数 | 模式 | 操作 |
|----------|------|----------|
| `[ci-log-path]` | 特定日志分析 | 直接读取该日志文件 |
| `scan` | 扫描所有日志 | 扫描 `.github/` 和 `test-results/` |
| `registry` | 注册表审查 | 读取 `tests/regression-suite.md` |
| 无参数 | 自动检测 | 如果 CI 日志可访问则 `scan`，否则 `registry` |

## 阶段 1: 定位 CI 日志数据#

### 选项 A — GitHub Actions（首选）

检查测试结果工件：

```bash
ls -t .github/ 2>/dev/null
ls -t test-results/ 2>/dev/null
```

对于 Godot 项目：GdUnit4 输出兼容 JUnit 格式的 XML。检查 `test-results/` 中的 `.xml` 文件。

对于 Unity 项目：game-ci 测试运行器默认将 NUnit XML 输出到 `test-results/`。

对于 Unreal 项目：自动化日志转到 `Saved/Logs/`。Grep 用于 `Result: Success` 和 `Result: Fail` 模式。

### 选项 B — 本地日志文件#

如果提供了路径参数，直接读取该文件。

### 选项 C — 无日志数据可用#

如果未找到日志：
> "未找到 CI 日志数据。要检测不稳定测试，此技能需要多次运行的测试结果历史。选项：
> 1. 至少运行测试套件 3 次并收集输出日志
> 2. 检查 CI 管道输出并将日志保存到 `test-results/`
> 3. 运行 `/test-flakiness registry` 以审查已在 `tests/regression-suite.md` 中标记为不稳定的测试"

停止并询问用户追求哪个选项。

## 阶段 2: 解析测试结果#

对于找到的每个 CI 日志或结果文件，解析：

**JUnit XML 格式**（GdUnit4 / Unity）：

- Grep 用于 `<testcase name=` 以获取测试名称
- Grep 用于 `<failure` 或 `<error` 以识别失败
- 解析 `classname` 和 `name` 属性以获取完整测试标识符

**纯文本日志**：

- Grep 用于通过/失败模式：
  - Godot: `PASSED` / `FAILED` 相邻测试名称
  - Unreal: `Result: Success` / `Result: Fail`
  - Unity: `Test passed` / `Test failed`

构建表：`test_id → [run1_result, run2_result, run3_result, ...]`

---

## 阶段 3: 识别不稳定测试#

如果测试在结果历史中同时出现通过和失败结果，并且它们之间没有代码更改，则测试是**不稳定的**。

**不稳定阈值**：
- **高不稳定性**：在 >25% 的运行中失败 — 立即隔离
- **中等不稳定性**：在 5–25% 的运行中失败 — 调查并尽快修复
- **低/疑似不稳定性**：在 1–5% 的运行中失败 — 监控；可能是真正罕见的失败

对于每个不稳定测试，分类可能的原因：

### 原因分类#

| 原因 | 症状 | 修复方向 |
|-------|----------|---------------|
| **时序 / 异步** | 在等待信号或计时器后失败；通过率与系统负载相关 | 添加显式等待/同步；避免基于时间的延迟 |
| **顺序依赖** | 在特定其他测试后失败时失败；在隔离中通过 | 添加适当的设置/拆卸；确保测试隔离 |
| **随机种子** | 无模式地间歇失败；涉及 RNG | 传递显式种子；不要在测试中使用 `randf()` |
| **资源泄漏** | 在测试运行后期更常失败 | 修复拆卸中的清理；检查孤立节点（Godot）或对象处置（Unity） |
| **外部状态** | 当来自先前测试的文件、场景或全局存在时失败 | 将测试与文件系统隔离；使用内存中模拟 |
| **浮点** | 在像 `== 0.5` 这样的比较上失败 | 使用 epsilon 比较（`is_equal_approx`、`Assert.AreApproximately`） |
| **场景/预制件加载竞争** | 在场景尚未准备好时失败 | 实例化后等待一帧；使用 `await get_tree().process_frame` |

使用 Grep 检查测试文件以查找时序调用、randf、全局状态访问或浮点数上的相等比较，以缩小原因范围。

---

## 阶段 4: 建议操作#

对于每个不稳定测试：

**隔离（高不稳定性）**：
> "立即隔离此测试。通过在 CI 中添加以下注释来禁用它：
> - Godot: `GdUnitSkip` 注释
> - Unity: `[Ignore]` 或 `[Fact(Skip="reason")]`
> - Unreal: `Auto Test -> Skip Test`
> 在 `tests/regression-suite.md` 隔离部分中记录它。
> 在修复根本原因之前，测试现在是选择加入的。
> 在移除隔离之前修复根本原因。"

**调查和修复（中等）**：
> "此测试间歇性不可靠。根本原因似乎是 [原因]。
> 建议的修复：[基于原因分类的具体修复]。尚不隔离 — 直接修复测试。"

**监控（低/疑似）**：
> "此测试显示疑似不稳定性。在隔离之前收集更多运行数据。
> 在回归套件中将其标记为'疑似'。"

## 阶段 5: 生成报告#

### 对话中摘要#

```markdown
## 不稳定检测结题 #

**已分析的运行**: [N]
**已跟踪的测试**: [N]

### 发现的不稳定测试#

| 测试 | 系统 | 失败率 | 可能的原因 | 建议 |
|------|--------|-----------|--------------|----------------|
| [test_name] | [system] | [N]% | 时序 | 隔离 + 修复异步 |
| [test_name] | [system] | [N]% | 浮点比较 | 修复：使用 epsilon 比较 |
| [test_name] | [system] | [N]% | 顺序依赖 | 调查拆卸 |

### 干净测试（未检测到不稳定性）#

[N] 个测试在 [N] 次运行中具有一致的结果 — 未检测到不稳定性。

### 数据限制#

[注意如果可用运行少于 5 次 — 运行越少 = 统计置信度越低]
```

## 阶段 6: 更新回归套件 + 可选报告文件#

询问："我可以更新 `tests/regression-suite.md` 的隔离部分以包含发现的不稳定测试吗？"

如果是：使用 `Edit` 将条目附加到隔离测试表。
永远不要删除现有的隔离条目 — 仅添加新条目。

询问（单独）："我可以将完整的不稳定报告写入 `production/qa/flakiness-report-[date].md` 吗？"

完整报告包括：
- 每个测试的分析，包含原因详情
- 引擎特定的修复代码片段
- 统计置信度评估

**写入后**：

- 对于每个隔离的测试："在 CI 中添加引擎特定的跳过注释以禁用此测试。在修复根本原因后重新启用。"
- 对于可修复的测试："[test] 的修复很简单 — 将第 [N] 行的相等比较更改为使用 `is_equal_approx`。"
- 摘要："一旦应用了所有隔离注释，CI 应该绿色运行。
  在发布门控之前安排 [N] 个隔离测试的修复工作。"

---

## 阶段 7: 协作协议#

- **永远不要删除测试文件** — 隔离意味着注释 + 列出，而不是删除
- **统计置信度很重要** — 对于 < 3 次运行，将发现标记为"疑似"而不是"已确认"；询问是否有更多运行数据可用
- **修复始终是目标** — 隔离是暂时的；即使在建议隔离时也要提出修复方向
- **在写入之前询问** — 回归套件更新和报告文件都需要明确批准。
  - 在写入时：判定：**完成** — 不稳定报告已写入。
  - 在拒绝时：判定：**已阻止** — 用户拒绝写入。
- **CI 中的不稳定是团队问题** — 清楚地提出列表和建议的操作；不要在没有团队知情的情况下静默隔离
