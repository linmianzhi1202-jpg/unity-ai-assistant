# 冒烟测试技能

## 技能概述

验证基本功能，检测关键故障。此技能是"实现完成"和"准备 QA 交接"之间的门控。它运行自动化测试套件，检查测试覆盖差距，与开发者批量验证关键路径，并生成 PASS/FAIL 报告。

规则很简单：**未通过冒烟测试的构建不能交给 QA。** 将损坏的构建交给 QA 会浪费他们的时间并打击团队士气。

**输出:** `production/qa/smoke-[date].md`

## 使用方式

- 通过 Agent 触发：当用户说「冒烟测试」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：```/skill smoke-check [参数]```

**参数**: 可以组合使用：`/smoke-check sprint --platform console`

**基础模式**（第一个参数，默认：`sprint`）：
- `sprint` — 针对当前冲刺的故事运行完整冒烟测试
- `quick` — 跳过覆盖扫描（阶段 3）和批次 3；用于快速重新检查

**平台标志** (`--platform`，默认：无)：
- `--platform pc` — 添加 PC 特定检查（键盘、鼠标、窗口模式）
- `--platform console` — 添加主机特定检查（手柄、电视安全区、平台认证要求）
- `--platform mobile` — 添加移动特定检查（触摸、竖屏/横屏、电池/散热行为）
- `--platform all` — 添加所有平台变体；输出每平台判定表

如果提供了 `--platform`，阶段 4 会添加平台特定批次，阶段 5 除了总体判定外还会输出每平台判定表。

## 阶段 1: 检测测试设置

在运行任何内容之前，了解环境：

1. **测试框架检查**：验证 `tests/` 目录存在。
   如果不存在："在 `tests/` 未找到测试目录。运行 `/test-setup` 搭建测试基础设施，或者如果测试位于其他地方，手动创建目录。"然后停止。

2. **CI 检查**：检查 `.github/workflows/` 是否包含引用测试的工文件。
   在报告中注明是否配置了 CI。

3. **引擎检测**：读取 `.claude/docs/technical-preferences.md` 并提取 `Engine:` 值。存储此值用于阶段 2 的测试命令选择。

4. **冒烟测试列表**：检查是否存在 `production/qa/smoke-tests.md` 或 `tests/smoke/`。如果找到冒烟测试列表，加载它用于阶段 4。如果都不存在，冒烟测试将从当前 QA 计划中抽取（阶段 4 回退）。

5. **QA 计划检查**：glob `production/qa/qa-plan-*.md` 并获取最近修改的文件。如果找到，注意路径——它将在阶段 3 和阶段 4 中使用。如果未找到，注意："未找到 QA 计划。为了最佳结果，在冒烟测试前运行 `/qa-plan sprint`。"

在继续之前报告发现："环境：[引擎]。测试目录：[找到/未找到]。CI 已配置：[是/否]。QA 计划：[路径/未找到]。"

---

## 阶段 2: 运行自动化测试

尝试通过 Bash 运行测试套件。根据阶段 1 检测的引擎选择命令：

**Godot 4:**
```bash
godot --headless --script tests/gdunit4_runner.gd 2>&1
```
如果该路径不存在 GDUnit4 运行器脚本，尝试：
```bash
godot --headless -s addons/gdunit4/GdUnitRunner.gd 2>&1
```
如果两个路径都不存在，注意："未找到 GDUnit4 运行器——确认测试框架的运行器路径。"

**Unity:**
Unity 测试需要编辑器，在大多数环境中无法通过 shell 无头运行。检查最近的测试结果工件：
```bash
ls -t test-results/ 2>/dev/null | head -5
```
如果测试结果文件存在（XML 或 JSON），读取最近的一个并解析 PASS/FAIL 计数。如果没有工件："Unity 测试必须从编辑器或 CI 管道运行。在继续之前请手动确认测试状态。"

**Unreal Engine:**
```bash
ls -t Saved/Logs/ 2>/dev/null | grep -i "test\|automation" | head -5
```
如果未找到匹配的日志："UE 自动化测试必须通过会话前端或 CI 管道运行。请手动确认测试状态。"

**未知引擎 / 未配置：**
"在 `.claude/docs/technical-preferences.md` 中未配置引擎。运行 `/setup-engine` 指定引擎，然后重新运行 `/smoke-check`。"

**如果在此环境中测试运行器不可用**（引擎二进制文件不在 PATH 上、运行器脚本未找到等），清楚地报告：

"无法执行自动化测试——在 PATH 上未找到引擎二进制文件。状态将记录为未运行。请从本地 IDE 或 CI 管道确认测试结果。未确认的未运行被视为带警告的通过，而不是失败——开发者必须在阶段 4 中手动确认结果。"

不要将未运行视为自动失败。将其记录为警告。开发者在阶段 4 中的手动确认可以解决它。

解析运行器输出并提取：
- 运行的总测试数
- 通过计数
- 失败计数
- 任何失败测试的名称（最多 10 个；如果更多，注意计数）
- 运行器本身的任何崩溃或错误输出

---

## 阶段 3: 检查测试覆盖

按优先级顺序，从以下位置抽取故事列表：
1. 阶段 1 找到的 QA 计划（其测试摘要表列出每个故事的预期测试文件路径）
2. 来自 `production/sprints/` 的当前冲刺计划（最近修改的文件）
3. 如果传递了 `quick` 参数，完全跳过此阶段并说明："覆盖扫描已跳过——运行 `/smoke-check sprint` 进行完整覆盖分析。"

对于范围内的每个故事：

1. 从故事的文件路径提取系统别名（例如，`production/epics/combat/story-001.md` → `combat`）
2. Glob `tests/unit/[system]/` 和 `tests/integration/[system]/` 查找名称包含故事别名或密切相关术语的文件
3. 检查故事文件本身是否有 `Test file:` 标头字段或"测试证据"部分

为每个故事分配覆盖状态：

| 状态 | 含义 |
|--------|---------|
| **已覆盖** | 找到匹配此故事系统和范围的测试文件 |
| **手动** | 故事类型是视觉/感觉或 UI；找到了测试证据文档 |
| **缺失** | 逻辑或集成故事没有匹配的测试文件 |
| **预期** | 配置/数据故事——不需要测试文件；抽查就足够了 |
| **未知** | 故事文件缺失或不可读 |

缺失条目是建议性差距。它们不会导致失败判定，但必须在报告中突出显示，并且必须在 `/story-done` 可以完全关闭这些故事之前解决。

## 阶段 4: 运行手动冒烟检查

按优先级顺序，从以下位置抽取冒烟测试清单：
1. QA 计划的"冒烟测试范围"部分（如果在阶段 1 找到了 QA 计划）
2. `production/qa/smoke-tests.md`（如果存在）
3. `tests/smoke/` 目录内容（如果存在）
4. 下面的标准回退列表（仅当上述都不存在时使用）

根据从冲刺或 QA 计划实际识别的系统定制批次 2 和 3。用当前冲刺故事中的真实机制名称替换带括号的占位符。

使用 `AskUserQuestion` 批量验证。保持最多 3 次调用。

**批次 1 — 核心稳定性（始终运行）：**
```
question: "冒烟检查 — 批次 1：核心稳定性。请验证每项："
options:
  - "游戏启动到主菜单无崩溃 — 通过"
  - "游戏启动到主菜单无崩溃 — 失败"
  - "新游戏/会话成功启动 — 通过"
  - "新游戏/会话成功启动 — 失败"
  - "主菜单响应所有输入 — 通过"
  - "主菜单响应所有输入 — 失败"
```

**批次 2 — 冲刺机制和回归（始终运行）：**
```
question: "冒烟检查 — 批次 2：本次冲刺的变更和回归检查："
options:
  - "[本次冲刺的主要机制] — 通过"
  - "[本次冲刺的主要机制] — 失败：[描述损坏内容]"
  - "[本次冲刺的第二个显著变更（如果有）] — 通过"
  - "[本次冲刺的第二个显著变更] — 失败"
  - "之前冲刺的功能仍正常工作（无回归）— 通过"
  - "之前冲刺的功能 — 发现回归：[简要描述]"
```

**批次 3 — 数据完整性和性能（除非传递 `quick` 参数，否则运行）：**
```
question: "冒烟检查 — 批次 3：数据完整性和性能："
options:
  - "保存/加载完成无数据丢失 — 通过"
  - "保存/加载 — 失败：[描述损坏内容]"
  - "保存/加载 — 不适用（保存系统尚未实现）"
  - "未观察到新的帧率下降或卡顿 — 通过"
  - "发现帧率下降或卡顿 — 失败：[位置]"
  - "性能 — 本次会话未检查"
```

逐字记录每个响应用于阶段 5 报告。

**平台批次**（仅当提供了 `--platform` 参数时运行）：

**PC 平台** (`--platform pc` 或 `--platform all`)：
```
question: "冒烟检查 — PC 平台：验证平台特定行为："
options:
  - "键盘控制在所有菜单和游戏玩法中正常工作 — 通过"
  - "键盘控制 — 失败：[描述问题]"
  - "鼠标输入和光标可见性在所有状态中正确 — 通过"
  - "鼠标输入 — 失败：[描述问题]"
  - "窗口和全屏模式功能无图形问题 — 通过"
  - "窗口/全屏 — 失败：[描述问题]"
  - "分辨率更改正确应用 — 通过"
  - "分辨率更改 — 失败：[描述问题]"
```

**主机平台** (`--platform console` 或 `--platform all`)：
```
question: "冒烟检查 — 主机平台：验证平台特定行为："
options:
  - "手柄输入对所有动作正常工作 — 通过"
  - "手柄输入 — 失败：[描述问题]"
  - "UI 适配在电视安全区边距内（无文本被裁剪）— 通过"
  - "电视安全区 — 失败：[描述被裁剪的内容]"
  - "不向手柄用户显示键盘/鼠标专用回退 — 通过"
  - "输入提示不一致 — 失败：[描述]"
  - "游戏从冷启动正确启动（无先前保存）— 通过"
  - "冷启动 — 失败：[描述问题]"
```

**移动平台** (`--platform mobile` 或 `--platform all`)：
```
question: "冒烟检查 — 移动平台：验证平台特定行为："
options:
  - "触摸控制对所有主要动作正常工作 — 通过"
  - "触摸控制 — 失败：[描述问题]"
  - "游戏正确处理方向更改（竖屏 ↔ 横屏）— 通过"
  - "方向更改 — 失败：[描述损坏内容]"
  - "后台/前台转换（主页按钮）被优雅地处理 — 通过"
  - "后台/前台 — 失败：[描述问题]"
  - "在目标设备上无可见性能问题（无散热节流迹象）— 通过"
  - "移动性能 — 失败：[描述问题]"
```

## 阶段 5: 生成报告

组装完整的冒烟检查报告：

```markdown
## 冒烟检查报告
**日期**: [日期]
**冲刺**: [冲刺名称/编号，或"未识别"]
**引擎**: [引擎]
**QA 计划**: [路径，或"未找到——首先运行 /qa-plan"]
**参数**: [sprint | quick | 空白]

---

### 自动化测试

**状态**: [通过（[N] 个测试，[N] 通过）| 失败（[N] 个失败）| 未运行（[原因]）]

[如果失败，列出失败测试：]
- `[测试名称]` — [来自运行器输出的简要失败描述]

[如果未运行：]
"需要手动确认：测试是否在本地 IDE 或 CI 中通过？这将决定自动化测试行是否有助于失败判定。"

---

### 测试覆盖

| 故事 | 类型 | 测试文件 | 覆盖状态 |
|-------|------|-----------|----------------|
| [标题] | 逻辑 | `tests/unit/[system]/[slug]_test.[ext]` | 已覆盖 |
| [标题] | 视觉/感觉 | `tests/evidence/[slug]-screenshots.md` | 手动 |
| [标题] | 逻辑 | — | 缺失 ⚠ |
| [标题] | 配置/数据 | — | 预期 |

**摘要**: [N] 已覆盖，[N] 手动，[N] 缺失，[N] 预期。

---

### 手动冒烟检查

- [x] 游戏启动无崩溃 — 通过
- [x] 新游戏启动 — 通过
- [x] [核心机制] — 通过
- [ ] [其他检查] — 失败：[用户描述]
- [x] 保存/加载 — 通过
- [-] 性能 — 本次会话未检查

---

### 缺失测试证据

在可以通过 `/story-done` 标记为完成之前，必须具有测试证据的故事：

- **[故事标题]** (`[路径]`) — 逻辑故事没有测试文件。
  预期位置：`tests/unit/[system]/[story-slug]_test.[ext]`

[如果没有：]"所有逻辑和集成故事都有测试覆盖。"

---

### 平台特定结果（仅当提供了 `--platform` 时）

| 平台 | 运行检查 | 通过 | 失败 | 平台判定 |
|----------|-----------|--------|--------|-----------------|
| PC | [N] | [N] | [N] | 通过 / 失败 |
| 主机 | [N] | [N] | [N] | 通过 / 失败 |
| 移动 | [N] | [N] | [N] | 通过 / 失败 |

**平台注释**: [任何未在通过/失败中捕获的平台特定观察]

有任何一个或多个失败检查的任何平台都会导致总体失败判定。

---

### 判定: [通过 | 带警告通过 | 失败]

[判定规则——第一个匹配的规则生效：]

**失败** 如果任何以下条件为真：
- 自动化测试套件运行并报告了一个或多个测试失败
- 任何批次 1（核心稳定性）检查返回失败
- 任何批次 2（主要冲刺机制或回归检查）返回失败

**带警告通过** 如果所有以下条件为真：
- 自动化测试通过或未运行（开发者尚未确认）
- 所有批次 1 和批次 2 冒烟检查通过
- 一个或多个逻辑/集成故事有缺失测试证据

**通过** 如果所有以下条件为真：
- 自动化测试通过
- 所有批次中的所有冒烟检查通过或不适用
- 没有缺失测试证据条目
```

## 阶段 6: 写入和门控

在对话中展示完整报告，然后询问：

"我可以将此冒烟检查报告写入 `production/qa/smoke-[date].md` 吗？"

仅在批准后写入。

写入后，交付门控判定：

**如果判定是失败：**

"冒烟检查失败。在解决这些失败之前，不要交给 QA：

[列出每个失败的自动化测试或冒烟检查及一行描述]

修复失败并再次运行 `/smoke-check` 在 QA 交接前重新门控。"

**如果判定是带警告通过：**

"冒烟检查带警告通过。构建已准备好进行手动 QA。

在受影响的视频故事上运行 `/story-done` 之前要解决的建议项：
[列出缺失测试证据条目]

QA 交接：与 qa-tester 代理共享 `production/qa/qa-plan-[sprint].md` 以开始手动验证。"

**如果判定是通过：**

"冒烟检查干净通过。构建已准备好进行手动 QA。

QA 交接：与 qa-tester 代理共享 `production/qa/qa-plan-[sprint].md` 以开始手动验证。"

## 协作协议

- **永远不要将未运行视为自动失败**——将其记录为未运行，让开发者手动确认状态。未确认的未运行有助于带警告的通过，而不是失败。
- **永远不要自动修复失败**——报告它们并说明必须解决什么。不要尝试编辑源代码或测试文件。
- **带警告通过不会阻止 QA 交接**——它记录建议性差距供 `/story-done` 跟进。
- **`quick` 参数**跳过阶段 3（覆盖扫描）和阶段 4 批次 3。用于修复特定失败后的快速重新检查。
- 所有手动冒烟检查验证都使用 `AskUserQuestion`。
- **未经询问永远不要写入报告**——阶段 6 在创建任何文件之前需要明确批准。
