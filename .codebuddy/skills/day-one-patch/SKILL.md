# 首日补丁技能

## 技能概述

为发布后问题创建紧急补丁。

每个发布的游戏都有首日补丁。在发布日之前规划它可以防止混乱。此技能将补丁范围限定为仅安全且必要的内容，通过轻量级 QA 检查对其进行门控，并确保在任何内容发布之前存在回滚计划。这是一个迷你冲刺 —— 不是热修复，不是完整冲刺。

**首日补丁范围规则：**
- 仅 P1/P2 Bug，且修复安全快速
- 无新功能 —— 仅修复
- 无重构 —— 最小可行变更
- 任何需要超过 4 小时开发时间的修复属于 patch 1.1，不是首日

**何时运行：**
- 在黄金母版构建锁定后（认证批准或发布候选标记）
- 当存在风险太高无法在黄金母版中处理的已知 Bug
- 当认证反馈要求在提交后 Minor 修复
- 当发布门控通过后，发布前试玩发现必须修复的问题

**输出：** `production/releases/day-one-patch-[version].md`

## 使用方式

- 通过 Agent 触发：当用户说「首日补丁」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill day-one-patch [参数]`

## 阶段 1：加载发布上下文

读取：

- `production/stage.txt` — 确认项目处于 Release 阶段
- `production/gate-checks/` 中最近的文件 — 读取发布门控裁决
- `production/qa/bugs/*.md` — 加载所有状态为 Open 或 Fixed — Pending Verification 的 Bug
- `production/sprints/` 最近的 — 了解发布了什么
- `production/security/security-audit-*.md` 最近的 — 检查任何开放安全项目

如果 `production/stage.txt` 不是 `Release` 或 `Polish`：

> "首日补丁准备适用于 Release 阶段的项目。当前阶段：[stage]。在接近发布之前，此技能不适用。"

---

## 阶段 2：范围界定补丁

### 步骤 2a — 分类开放 Bug 以包含在补丁中

对于每个开放 Bug，评估：

| 标准 | 包含在首⽇中？ |
|-----------|-------------------|
| S1 或 S2 严重性 | 是 — 如果修复安全则必须包含 |
| P1 优先级 | 是 |
| 修复估计 < 4 小时 | 是 |
| 修复需要架构变更 | 否 — 推迟到 1.1 |
| 修复引入新代码路径 | 否 — 风险太高 |
| 修复仅是数据/配置（无代码变更） | 是 — 风险非常低 |
| 认证反馈要求 | 是 — 平台批准需要 |
| S3/S4 严重性 | 仅限简单配置修复；否则推迟 |

### 步骤 2b — 向用户展示补丁范围

使用询问用户：

- 提示："基于开放 Bug 和认证反馈，这是提议的首日补丁范围。看起来正确吗？"
- 展示：包含的 Bug 表格（ID、严重性、描述、估计工作量）
- 展示：推迟的 Bug 表格（ID、严重性、推迟原因）
- 选项：`[A] 批准此范围` / `[B] 调整 — 我想添加或移除项目` / `[C] 不需要首日补丁`

如果 [C]：输出"不需要首日补丁。继续进行 `/launch-checklist`。" 停止。

### 步骤 2c — 检查总范围

合计估计工作量。如果总计超过 1 天的工作：

> "⚠️ 补丁范围是 [N 小时] — 这超过了安全的首日窗口。考虑将低优先级项目推迟到 patch 1.1。膨胀的首日补丁引入的风险比它移除的更多。"

使用询问用户确认继续或缩小范围。

---

## 阶段 3：回滚计划

在编写任何代码之前，定义回滚程序。这是不可协商的。

通过 Task 生成 `release-manager`：

要求他们产生回滚计划，涵盖：
- 如何在每个目标平台上回滚到黄金母版构建
- 平台特定的回滚约束（某些平台无法回滚认证构建）
- 谁负责触发回滚
- 如果发生回滚，需要什么玩家沟通

展示回滚计划。询问："我可以将此回滚计划写入 `production/releases/rollback-plan-[version].md` 吗？"

在回滚计划写入之前，不要继续到阶段 4。

---

## 阶段 4：实施修复

对于批准范围中的每个 Bug，生成专注的实施循环：

1. 通过 Task 生成 `lead-programmer`，包含：
   - Bug 报告（确切的重现步骤和根本原因（如果已知））
   - 约束：仅最小可行修复，无清理
   - 受影响的文件（来自 Bug 报告的 technical Context 部分）

2. 主程序员实施并运行目标测试。

3. 通过 Task 生成 `qa-tester` 以验证：修复后 Bug 是否重现？

对于仅配置/数据修复：直接进行变更（不需要程序员 Agent）。确认值已更改并重新运行任何相关冒烟测试。

---

## 阶段 5：补丁 QA 门控

这是轻量级 QA 检查 —— 不是完整的 `/team-qa`。补丁已经通过发布门控的 QA 批准；我们仅重新验证变更区域。

通过 Task 生成 `qa-lead`，包含：
- 所有已变更文件的列表
- 已修复 Bug 的列表（来自阶段 4 的验证状态）
- 受影响系统的冒烟检查范围

要求 qa-lead 确定：**目标冒烟检查是否足够，或者是否有任何修复触及需要更广泛回归的系统？**

运行所需的 QA 范围：
- **目标冒烟检查** — 运行 `/smoke-check [affected-systems]`
- **更广泛的回归** — 为受影响系统运行 `tests/unit/` 和 `tests/integration/` 中的目标测试

QA 裁决必须是 PASS 或 PASS WITH WARNINGS 才能继续。如果 FAIL：将失败的修复排除在首日补丁之外，推迟到 1.1。

```markdown

**目标发布**：[发布日期或"发布日"]
**基础构建**：[黄金母版标签或提交]
**补丁构建**：[补丁标签或提交]

|--------|----------|-------------|-------------|
| BUG-NNN | S[1-4] | [描述] | [一行修复] |

### 推迟到 1.1

| BUG-ID | 严重性 | 描述 | 推迟原因 |

---

## QA 签署

参见：`production/releases/rollback-plan-[version].md`

**触发条件**：如果发布后 [X] 小时内报告 [N] 个或更多 S1 Bug，执行回滚。
**回滚负责人**：[用户 / 制作人]

## 部署前需要的批准

- [ ] 主程序员：所有修复已审查
- [ ] qa-lead：QA 门控 PASS 确认
- [ ] 制作人：部署时机批准
- [ ] 发布经理：平台提交确认

---

## 玩家面向的补丁说明

[供社区经理在发布前审查的草稿]

[以简明语言列出玩家面向的变更]
```

询问："我可以将此补丁记录写入 `production/releases/day-one-patch-[version].md` 吗？"

## 阶段 7：后续步骤

补丁记录写入后：

1. 运行 `/patch-notes` 以生成补钉说明的玩家面向版本
2. 补丁上线后，运行 `/bug-report verify [BUG-ID]` 对于每个已修复的 Bug
3. 运行 `/bug-report close [BUG-ID]` 对于每个已验证的修复
4. 使用 `/retrospective launch` 在发布后 48-72 小时安排发布后回顾

**如果补丁后任何 S1 Bug 仍保持开放：**

> "⚠️ S1 Bug 仍保持开放且未被修补。这些是可接受的风险。在回滚计划触发条件中记录它们 —— 如果它们大规模发生，回滚可能比后续补丁更可取。"

---

## 协作协议

- **范围纪律是一切** —— 抵制范围蔓延；每个添加都增加风险
- **始终首先制定回滚计划** —— 没有回滚计划的补丁是不负责任的
- **推迟不是遗忘** —— 每个推迟的 Bug 自动获得 1.1 ticket
- **玩家沟通是补丁的一部分** —— `/patch-notes` 是必需的输出，不是可选的
