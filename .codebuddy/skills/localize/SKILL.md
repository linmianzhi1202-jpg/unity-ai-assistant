# 本地化技能

## 技能概述

准备多语言支持，管理翻译记忆库。本地化不仅仅是翻译 — 它是让游戏在每个语言和地区都感觉原生的完整流程。糟糕的本地化会破坏沉浸感、混淆玩家，并阻碍平台认证。此技能涵盖从字符串提取到文化审查、VO 录制、RTL 布局测试和本地化 QA 签署的完整管线。

**模式：**
- `scan` — 查找硬编码字符串和本地化反模式（只读）
- `extract` — 提取字符串并生成可翻译表格
- `validate` — 检查翻译的完整性、占位符和长度
- `status` — 所有区域的覆盖矩阵
- `brief` — 为外部团队生成翻译员上下文简报文档
- `cultural-review` — 标记文化敏感内容、符号、颜色、习语
- `vo-pipeline` — 管理语音本地化：脚本、录制规范、集成
- `rtl-check` — 验证 RTL 语言布局、镜像和字体支持
- `freeze` — 强制执行字符串冻结；在翻译开始前锁定源字符串
- `qa` — 在发布前运行完整的本地化 QA 周期

如果没有提供子命令，输出用法并停止。结论：**失败** — 缺少必需的子命令。

## 使用方式

- 通过 Agent 触发：当用户说「本地化」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill localize [子命令] [参数]`

## Phase 2A：扫描模式

搜索 `src/` 中的硬编码面向用户的字符串：

- UI 代码中未包装在本地化函数中的字符串字面量（`tr()`、`Tr()`、`NSLocalizedString`、`GetText` 等）
- 应该参数化的连接字符串
- 带有位置占位符（`%s`、`%d`）而不是命名占位符（`{playerName}`）的字符串
- 混合区域设置敏感数据（数字、日期、货币）而不使用区域识别格式的格式化字符串

搜索本地化反模式：

- 未使用区域识别函数的日期/时间格式化
- 无区域识别的数字格式化（`1,000` vs `1.000`）
- 嵌入图像或纹理中的文本（标记 `assets/` 中的资源文件）
- 假设从左到右文本方向的文本（位置布局、字符串组装顺序）
- 烘焙到字符串逻辑中的性别/复数假设（必须使用复数形式或性别令牌）
- 硬编码标点符号（例如 `"You won!"` — 感叹号样式因区域而异）

报告所有发现，包括文件路径和行号。此模式是只读的 — 不写入文件。

## Phase 2B：提取模式

- 扫描所有源文件以查找本地化的字符串引用
- 与 `assets/data/strings/` 中的现有字符串表进行比较
- 为尚未键化的字符串生成新条目
- 建议遵循约定的键名：`[category].[subcategory].[description]`
  - 示例：`ui.hud.health_label`、`dialogue.npc.merchant.greeting`、`menu.main.play_button`
- 每个新条目必须包含 `context` 字段 — 解释以下内容的翻译员注释：
  - 它出现在哪里（哪个屏幕、哪个场景）
  - 最大字符长度
  - 任何占位符含义（`{playerName}` = 玩家选择的显示名称）
  - 性别/复数上下文（如果适用）

输出要添加到字符串表的新字符串的差异。

向用户展示差异。询问："我可以将这些新条目写入 `assets/data/strings/strings-en.json` 吗？"

如果可以，仅写入差异（新条目），而不是完全替换。结论：**完成** — 字符串已提取并写入。

## Phase 2C：验证模式

读取 `assets/data/strings/` 中的所有字符串表文件。对于每个区域设置，检查：

- **完整性** — 源（en）中存在键但此区域设置没有翻译
- **占位符不匹配** — 源有 `{name}` 但翻译省略了它或添加了额外内容
- **字符串长度违规** — 翻译超过源 `context` 字段中记录的字符限制
- **复数形式计数** — 区域设置需要 N 种复数形式；翻译提供的更少
- **孤立键** — 翻译存在但 `src/` 中没有引用该键
- **过期翻译** — 翻译写入后源字符串已更改（标记为重新翻译）
- **编码** — 存在非 ASCII 字符且字体图集支持它们（如果不确定则标记）

报告按区域设置和严重性分组的验证结果。此模式是只读的 — 不写入文件。

## Phase 2D：状态模式

- 计算源表中的可本地化字符串总数
- 每个区域设置：计算已翻译、未翻译、过期（翻译后源已更改）的数量
- 生成覆盖矩阵：

```markdown
## 本地化状态
生成日期：[日期]
字符串冻结：[活跃 / 尚未调用 / 已解除]

| 区域设置 | 总数 | 已翻译 | 缺失 | 过期 | 覆盖率 |
|--------|-------|-----------|---------|-------|----------|
| en (源) | [N] | [N] | 0 | 0 | 100% |
| [区域设置] | [N] | [N] | [N] | [N] | [X]% |

### 问题
- [N] 源代码中找到的硬编码字符串（运行 /localize scan）
- [N] 超过字符限制的字符串
- [N] 占位符不匹配
- [N] 孤立键
- [N] 调用冻结后添加的字符（冻结违规）
```

此模式是只读的 — 不写入文件。

## Phase 2E：简报模式

生成翻译员上下文简报文档。此文档与字符串表导出一起发送给外部翻译团队或本地化供应商。

读取：
- `design/gdd/` — 提取游戏类型、基调、设定、角色名称
- `assets/data/strings/strings-en.json` — 源字符串表
- `design/narrative/` 中的任何现有传说或叙事文档

生成 `production/localization/translator-brief-[locale]-[date].md`：

```markdown
# 翻译员简报 — [游戏名称] — [区域设置]

## 游戏概述
[2-3 段游戏摘要、类型、基调和目标受众]

## 基调和声音
- **整体基调**：[例如"黑暗喜剧，不是闹剧 — 想想 Terry Pratchett，不是 Looney Tunes"]
- **玩家称呼**：[例如"第二人称，非正式。永远不要正式 'vous' — 总是法语用 'tu'"]
- **亵渎政策**：[例如"温和 — 相当于 PG-13。匹配源的强度，不要软化或升级"]
- **幽默**：[例如"存在文字游戏 — 如果双关语无法翻译，发明一个等效的本地笑话；不要字面翻译"]

## 角色词汇表
| 名称 | 角色 | 个性 | 注释 |
|------|------|-------------|-------|
| [名称] | [角色] | [个性] | [不要翻译 / 音译为 X] |

## 世界词汇表
| 术语 | 含义 | 注释 |
|------|---------|-------|
| [术语] | [含义] | [保留英文 / 翻译为 X] |

## 不要翻译列表
以下内容必须逐字出现在所有区域设置中：
- [游戏名称]
- [匹配引擎内标签的 UI 术语]
- [品牌或商标名称]

## 占位符参考
| 占位符 | 表示的内容 | 示例 |
|-------------|-------------------|---------|
| `{playerName}` | 玩家选择的显示名称 | "Shadowblade" |
| `{count}` | 整数数量 | "3" |

## 字符限制
在字符串表 `context` 字段中标记了严格限制的严格 UI 字段。
在没有说明限制的地方，以 ±30% 的英文长度为目标作为指南。

## 联系方式
问题直接联系：[用户/团队联系占位符]
交付格式：JSON，与 strings-en.json 相同的模式
```

询问："我可以将此翻译员简报写入 `production/localization/translator-brief-[locale]-[date].md` 吗？"

## Phase 2F：文化审查模式

通过 Task 生成 `localization-lead`。要求他们审计以下内容，以审查目标区域设置的文化敏感性（从 `assets/data/strings/` 和 `assets/` 读取）：

### 要审查的内容领域

**符号和手势**
- 竖起大拇指、OK 手势、和平手势 — 含义因地区而异
- 美术、UI 或音频中的宗教或精神符号
- 国旗、地图表示、争议领土

**颜色**
- 白色（在一些亚洲文化中为哀悼）、绿色（在一些地区有政治关联）、红色（运气 vs 危险）
- 与文化关联冲突的警报/警告颜色

**数字**
- 4（日语/中文中的死亡）、13、666 — 标记在 UI 中的使用（房间号、物品计数、价格）

**幽默和习语**
- 在其他区域设置中翻译为冒犯性的习语
- 在一些市场（特别是日本、德国、中东）不适当的厕所/身体幽默
- 在特定地区文化敏感的黑暗幽默话题

**暴力和内容分级**
- 在 DE（德国）、AU（澳大利亚）、CN（中国）或 AE（阿联酋）需要分级更改的内容
- 血液颜色、血腥程度、药物参考 — 如果需要，标记所有区域特定的资源变体

**名称和表示**
- 在目标区域设置中具有冒犯性、亵渎性或带有负面含义的角色名称
- 国籍、宗教或族裔群体的刻板印象表示

将发现呈现为表格：

| 发现 | 受影响的区域设置 | 严重性 | 建议操作 |
|---------|--------------------|----------|--------------------|
| [描述] | [区域设置] | [阻塞 / 建议 / 注释] | [更改 / 标记审查 / 接受] |

阻塞 = 必须在发布该区域设置之前修复。建议 = 建议更改。注释 = 仅用于提供信息。

询问："我可以将此文化审查报告写入 `production/localization/cultural-review-[date].md` 吗？"

## Phase 2G：VO 管线模式

管理语音本地化流程。从参数确定子任务：

- `vo-pipeline scan` — 识别需要 VO 录制的所有对话行
- `vo-pipeline script` — 生成带有导演注释的录制脚本
- `vo-pipeline validate` — 检查所有录制的 VO 文件是否存在并正确命名
- `vo-pipeline integrate` — 验证 VO 文件在代码/资源中是否正确引用

### VO 管线：扫描

读取 `assets/data/strings/` 和 `design/narrative/`。识别：
- 所有对话行（匹配 `dialogue.*` 的键）及其源文本
- 已录制的行（音频文件存在于 `assets/audio/vo/` 中）
- 尚未录制的行

输出录制清单：

```
## VO 录制清单 — [日期]

| 键 | 角色 | 源行 | 状态 |
|-----|-----------|-------------|--------|
| dialogue.npc.merchant.greeting | Merchant | "Welcome, traveller." | 已录制 |
| dialogue.npc.merchant.haggle | Merchant | "That's my final offer." | 需要录制 |
```

### VO 管线：脚本

为每个角色生成录制脚本文档，按场景分组。包括：

- 角色名称和简短个性注释
- 带有不寻常专有名词发音指南的完整对话行
- 每行的情感/方向注释（`[温暖，欢迎]`、`[烦恼，简短]`）
- 对话中任何响应的行（提供上下文："玩家刚刚说了 X"）

询问："我可以将 VO 录制脚本写入 `production/localization/vo-scripts-[locale]-[date].md` 吗？"

### VO 管线：验证

扫描 `assets/audio/vo/[locale]/` 中的所有 `.wav`/`.ogg` 文件。对照 VO 清单交叉引用。报告：
- 缺失文件（脚本中的行，无音频文件）
- 额外文件（音频文件存在，无匹配的字符串键）
- 命名约定违规

### VO 管线：集成

在 `src/` 中 Grep VO 音频引用。验证每个引用的路径存在于 `assets/audio/vo/[locale]/` 中。报告损坏的引用。

## Phase 2H：RTL 检查模式

从右到左的语言（阿拉伯语、希伯来语、波斯语、乌尔都语）需要布局镜像，而不仅仅是翻译文本。此模式验证实施。

读取 `.claude/docs/technical-preferences.md` 以确定引擎。然后检查：

**布局镜像**
- RTL 布局是否在引擎中启用？（Godot：`Control.layout_direction`，Unity：`RTL Support` 包，Unreal：文本方向标志）
- 所有 UI 容器是否设置为自动镜像，还是位置硬编码？
- 进度条、生命条和方向指示器是否正确镜像？

**文本渲染**
- 是否加载了支持阿拉伯语/希伯来语字符集的字体？
- 阿拉伯语文本是否以正确的连字（连接的脚本）渲染？
- 是否根据要求将数字显示为东阿拉伯数字？

**字符串组装**
- 是否有任何假设从左到右读取顺序的字符串连接？
- 句子结构反转时，句子中的 `{placeholder}` 位置是否正常工作？

**资源审查**
- 是否有带方向箭头或非对称设计的 UI 图标需要镜像变体？
- 是否存在需要 RTL 版本的图像中的文本资源？

Grep 模式检查：
- 场景/预制件文件中的引擎特定 RTL 标志
- 任何 `HBoxContainer`、`LinearLayout`、`HorizontalBox` 节点 — 验证 layout_direction 设置
- 对话或 UI 代码附近的带有 `+` 的字符串连接

报告发现。标记阻塞问题（不修复则内容不可读）与建议（外观改进）。

询问："我可以将此 RTL 检查报告写入 `production/localization/rtl-check-[date].md` 吗？"

## Phase 2I：冻结模式

字符串冻结锁定源（英文）字符串表，以便翻译可以在翻译员不变的情况下进行。

### 冻结调用

检查 `production/localization/freeze-status.md` 中的当前冻结状态（如果存在）。

如果已冻结：
> "字符串冻结当前为**活跃**（于 [日期] 调用）。[N] 个字符串在冻结后已添加或修改。这些是冻结违规 — 它们需要重新翻译或批准的冻结解除。"

如果未冻结，展示冻结前检查清单：

```
冻结前检查清单
[ ] 所有计划的 UI 屏幕都已实施
[ ] 所有对话行都是最终的（没有进一步的叙事修订计划）
[ ] 所有系统字符串（错误消息、教程文本）都已完成
[ ] /localize scan 显示零个硬编码字符串
[ ] /localize validate 显示源 (en) 中没有占位符不匹配
[ ] 营销字符串（商店描述、成就）是最终的
```

使用 `AskUserQuestion`：
- 提示："以上所有项目都确认了吗？调用字符串冻结会锁定源表。"
- 选项：`[A] 是 — 现在调用字符串冻结` / `[B] 否 — 我还有字符串要添加`

如果 [A]：写入 `production/localization/freeze-status.md`：

```markdown
# 字符串冻结状态

**状态**：活跃
**调用**：[日期]
**调用者**：[用户]
**冻结时的字符串总数**：[N]

## 冻结后更改
[冻结后添加或修改的任何字符串都通过 /localize extract 自动列在此处]
```

### 冻结解除

如果参数包含 `lift`：将 `freeze-status.md` 状态更新为 `LIFTED`，记录原因和日期。警告："解除冻结需要重新翻译所有修改的字符串。在继续之前通知本地化供应商。"

### 冻结检查（自动集成到提取中）

当 `extract` 模式找到新或修改的字符串且 `freeze-status.md` 显示状态：活跃 — 将新键附加到 `## 冻结后更改` 并警告：
> "⚠️ 字符串冻结处于活跃状态。[N] 个新/修改的字符串已添加。这些是冻结违规。在继续之前通知您的本地化供应商。"

## Phase 2J：QA 模式

本地化 QA 是在翻译交付后但在任何区域设置发布之前运行的专用传递。这与 `/validate`（检查完整性）不同 — 这是基于结构化通关的质量检查。

通过 Task 生成 `localization-lead`，包含：
- 要 QA 的目标区域设置
- 游戏中的所有屏幕/流程列表（来自 `design/gdd/` 或 `/content-audit` 输出）
- 当前的 `/localize validate` 报告
- 文化审查报告（如果存在）

要求 localization-lead 生成涵盖以下内容的 QA 计划：

1. **功能字符串检查** — 每个字符串在游戏中显示时没有截断、占位符错误或编码损坏
2. **UI 溢出检查** — 翻译超过 UI 边界的翻译字符串（即使在字符限制内，某些语言也会扩展）
3. **上下文准确性** — 游戏中审查 10% 的字符串样本以检查翻译准确性和自然措辞
4. **文化审查项目** — 验证文化审查中的所有阻塞项目都已解决
5. **VO 同步检查** — 如果存在 VO，验证翻译后口型同步或字幕时机是否可接受
6. **平台认证要求** — 检查特定于平台的本地化要求（年龄分级文本、法律通知、ESRB/PEGI/CERO 文本）

每个区域设置输出 QA 判定：

```
## 本地化 QA 判定 — [区域设置]

**状态**：通过 / 有条件通过 / 失败
**审查者**：localization-lead
**日期**：[日期]

### 发现
| ID | 领域 | 描述 | 严重性 | 状态 |
|----|------|-------------|----------|--------|
| LOC-001 | UI 溢出 | "设置"按钮文本在 [屏幕] 上溢出 | 阻塞 | 打开 |
| LOC-002 | 翻译 | [键] 翻译是字面的 — 听起来不自然 | 建议 | 打开 |

### 条件（如果有条件通过）
- [条件 1 — 必须在发布前解决]

### 签署
[ ] 所有阻塞发现都已解决
[ ] 制作人批准发布 [区域设置]
```

询问："我可以将此本地化 QA 报告写入 `production/localization/loc-qa-[locale]-[date].md` 吗？"

**门控集成**：打磨 → 发布门控要求每个要发布的区域设置都有通过或有条件通过判定。失败仅阻止该区域设置的发布 — 如果它们的 QA 通过，其他区域设置仍可以继续。

## Phase 3：规则和下一步

### 规则
- 英语 (en) 始终是源区域设置
- 每个字符串表条目必须包含带有翻译员注释、字符限制和占位符含义的 `context` 字段
- 永远不要直接修改翻译文件 — 生成差异以供审查
- 必须为每个 UI 元素定义字符限制并在验证模式中强制执行
- 在将字符串发送给翻译员之前必须调用字符串冻结 — 永远不要翻译移动目标
- 必须从一开始就设计 RTL 支持 — 改造 RTL 布局是昂贵的
- 游戏将商业销售的任何区域设置都需要文化审查
- VO 脚本必须包含导演注释 — 原始对话行产生平淡的录制

### 推荐工作流程

```
/localize scan            → 查找硬编码字符串
/localize extract         → 构建字符串表
/localize freeze          → 在发送给翻译员之前锁定源
/localize brief           → 生成翻译员简报文档
[发送给翻译员]
/localize validate        → 检查返回的翻译
/localize cultural-review → 标记文化敏感内容
/localize rtl-check       → 如果发布阿拉伯语 / 希伯来语 / 波斯语
/localize vo-pipeline     → 如果发布配音 VO
/localize qa              → 完整的本地化 QA 传递
```

在所有发布区域设置的 `qa` 返回通过之后，在运行 `/gate-check release` 时包含 QA 报告路径。
