# 回归测试套件技能#

## 技能概述#

维护回归测试集合，检测意外后果。此技能确保每次错误修复都有相应的回归测试支持，并在游戏演进过程中保持回归套件的最新状态。它还会检测何时添加了新功能而没有相应的回归覆盖。

回归测试套件不是新的测试类别 — 它**是 `tests/` 中已有的测试的**策展列表，共同覆盖游戏的关键路径和已知失败点。此技能维护该列表。

**何时运行**：
- 修复错误后（确认已编写回归测试或识别差距）
- 发布门控之前（`/gate-check polish` 需要回归套件存在）
- 作为冲刺关闭的一部分以检测覆盖漂移

---

## 使用方式#

- 通过 Agent 触发：当用户说「回归测试套件」或相关需求时，Agent 应自动加载此 Skill
- 手动触发：`/skill regression-suite [参数]`

---

## 1. 解析参数#

**模式**：`$ARGUMENTS`（空白 = 通过 AskUserQuestion 询问用户）

从参数确定模式：

- **`update`** — 扫描此冲刺中新的错误修复并检查回归测试存在性；将新测试添加到套件清单
- **`audit`** — 所有 GDD 关键路径与现有测试覆盖的全审计；标记没有回归测试的路径
- **`report`** — 只读状态报告（无写入）；适用于冲刺审查
- **无参数** — 如果冲刺处于活跃状态，运行 `update`，否则运行 `audit`

解析范围后，报告："正在为 [范围] 构建回归测试套件。[N] 个故事在范围内。"

如果引用了故事文件路径但文件不存在，将其记为缺失并继续处理剩余的故事。不要因为一个缺失的文件而使整个计划失败。

---

## 2. 加载上下文#

### 步骤 2a — 加载现有回归套件#

读取 `tests/regression-suite.md`（如果存在）。提取：
- 注册的总回归测试数
- 最后更新日期
- 任何标记为 `STALE` 或 `QUARANTINED` 的测试

如果不存在：注意"未找到回归套件 — 将创建一个。"

### 步骤 2b — 加载测试清单#

扫描所有测试文件：

```
tests/unit/**/*_test.*
tests/integration/**/*_test.*
tests/regression/**/*
```

对于每个文件，注意系统（从目录路径）和文件名。

除非需要名称到测试的映射，否则不要读取测试文件内容。

### 步骤 2c — 加载 GDD 关键路径#

对于 `audit` 模式：读取 `design/gdd/systems-index.md` 以获取所有系统。

对于每个 MVP 层系统，读取其 GDD 并提取：
- 验收标准（这些定义了关键路径）
- 公式部分（公式必须有回归测试）
- 边缘情况部分（已知的边缘情况应该有回归测试）

对于 `update` 模式：跳过完整的 GDD 扫描。而是读取当前冲刺计划和故事文件以查找此冲刺完成的故事。

### 步骤 2d — 加载已关闭的错误#

扫描 `production/qa/bugs/*.md` 并过滤带有 `状态：已关闭` 或 `状态：已修复` 字段的错误。注意：
- 错误所在的系统或故事
- 错误修复描述中是否提到了回归测试

---

## 3. 映射覆盖 — 关键路径#

仅适用于 `audit` 模式：

对于每个 GDD 验收标准，确定测试是否存在：

1. Grep `tests/unit/[system]/` 和 `tests/integration/[system]/` 以获取与标准的关键名词/动词相关的文件名和功能名称
2. 分配覆盖：
   | 状态 | 含义 |
   |--------|---------|
   | **已覆盖** | 存在针对此标准逻辑的测试文件 |
   | **部分** | 存在测试但不覆盖所有情况（例如，仅快乐路径）|
   | **缺失** | 未找到此关键路径的测试 |
   | **例外** | 视觉/感觉标准 — 按设计不可自动化 |

3. 将对应的 MISSING 项目（对应于公式或状态机）提升为**高优先级**差距 — 这些是最可能的回归来源。

---

## 4. 映射覆盖 — 已修复错误#

对于每个已关闭的错误：

1. 从错误的元数据中提取系统 slug
2. Grep `tests/unit/[system]/` 和 `tests/integration/[system]/` 以获取引用错误 ID 或特定失败场景的测试
3. 分配：
   - **有回归测试** — 找到了会捕获此错误的测试
   - **缺失回归测试** — 错误已修复但没有测试防范复发

对于**缺失回归测试**项目：
- 将其标记为回归差距
- 建议测试文件路径：`tests/unit/[system]/[bug-slug]_regression_test.[ext]`
- 注意："没有此测试，此错误可能在未来的冲刺中悄悄返回。"

---

## 5. 检测覆盖漂移#

当游戏增长但回归套件没有增长时，就会发生覆盖漂移。

检查漂移指标：
- 此冲刺完成的故事在 `tests/` 中没有相应测试文件
- 自上次回归套件更新以来，添加到 `systems-index.md` 的新系统
- 自回归套件上次更新以来，GDD 部分添加或修订
- `tests/regression-suite.md` 最后更新日期与当前日期 — 如果差距 > 2 个冲刺，标记为可能过时

---

## 6. 生成报告和套件清单#

组装完整的回归套件文档。使用此结构：

```markdown
# 回归测试套件清单

> 最后更新：[日期]
> 注册测试总数：[N]
> 覆盖：[N]% 的 GDD 关键路径

## 如何运行#
[引擎特定的运行所有回归测试的命令]

## 注册回归测试#

### [系统名称]#

| 测试文件 | 测试功能（如果已知） | 覆盖 | 添加 |
|-----------|--------------------------|--------|-------|
| `tests/[unit|integration]/[system]/[file]_test.[ext]` | `test_[scenario]` | AC-N / BUG-NNN | [日期] |

## 已知差距#

尚不存在的测试：

| 优先级 | 系统 | 建议路径 | 覆盖 | 尚未编写的原因 |
|----------|--------|---------------------|--------|------------------------|
| HIGH | [系统] | `tests/unit/[system]/[path]` | BUG-NNN | 错误修复没有测试 |

## 隔离测试#

已隔离（不在 CI 中运行）的测试：

| 测试文件 | 功能 | 原因 | 自何时隔离 |
|-----------|----------|--------|--------------|
| （无) |  |  |  |
```

## 7. 写入输出#

在对话中展示完整计划（或如果计划非常长，则展示摘要），然后询问：

"我可以将此回归套件写入 `tests/regression-suite.md` 吗？"

完全像生成的那样写入套件 — 不要截断。

写入后：

"回归套件已写入 `tests/regression-suite.md`。"

下一步：
- 在冲刺实施开始前与团队分享此计划
- 所有故事实施后运行 `/smoke-check sprint` 以门控 QA 移交
- 对于逻辑/集成故事，在标记故事完成之前创建列出路径的测试文件 — `/story-done` 检查它们"

---

## 协作协议#

- **没有询问绝对不要写入计划** — Phase 5 需要明确批准。
- **保守分类**：当故事在逻辑和集成之间模糊时，将其分类为集成 — 它需要单元和集成测试。
- **不要发明超出验收标准和 GDD 公式支持的测试用例**。如果 GDD 中缺少公式，标记它而不是猜测。
- **试玩要求是咨询性的**：用户决定是否值得为有边界的视觉/感觉故事进行试玩。标记案例；不要强制。
- 如果未提供参数，使用 `AskUserQuestion` 进行范围选择。
- 保持所有其他阶段非交互式 — 展示发现，然后询问一次以批准写入。
